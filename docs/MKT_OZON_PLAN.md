# MKT · Ozon: юнит-экономика и глобальный план

Аналог `MKT_WB_UNIT_ECONOMICS.md` для Ozon. Порядок разделов = порядок работ:
юнит-экономика → контроль маржи → ставки → анализ спроса.
Составлен 07.08.2026, все цифры проверены по нашей БД, источник указан у каждой.

---

## 0. Golden rules

1. **`payout` и `commission_amount` в постингах — суммы НА СТРОКУ, `price` — НА ШТУКУ.**
   Считать только по строкам `quantity = 1` либо делить на количество. Иначе получишь
   комиссию 64 % и выплату 92 % — проверено, первый прогон был именно такой.
2. **`qty` у Ozon в `margin_by_sku` не заполнен** (только суммы). Всё считать в рублях.
3. **Мост к продажам:** `ozon_price_index.offer_id → ozon_product.sku → margin_by_sku.article`.
   Прямого совпадения `price_index.sku` с `margin_by_sku.article` НЕТ (0 строк, проверено).
   В постингах `financial_data.products[].product_id` = `ozon_product.sku`, НЕ offer_id.
4. **`financial_data.products[].actions` — массив строк**, а не объектов с `action_name`.
5. Запись на площадку — только по отдельной прямой команде (CLAUDE.md, правило 7 габаритов
   распространяется на все потоки).

## 1. Юнит-экономика: из чего складывается рубль (июль 2026, оба аккаунта)

### 1.1 Цепочка цены

```
old_price (зачёркнутая)
   ↓  наша скидка
price = НАША цена  ──────────────────── от неё считаются комиссия и выплата
   ↓  скидка за счёт Озона (баллы, кредитка Озон Банка, AI benefit system)
customer_price = что платит покупатель  ── от неё считается ИНДЕКС ЦЕН
```

Факт июля, строки `quantity = 1`, доставленные:

| | acc1 | acc2 |
|---|---|---|
| наша цена | 7 986 238 ₽ | 1 931 392 ₽ |
| заплатил покупатель | 4 567 410 ₽ (**57 %**) | 1 661 653 ₽ (86 %) |
| доплатил Озон | **3 418 828 ₽** | 269 739 ₽ |
| выплата нам | **59 % от нашей цены** | **59 % от нашей цены** |

**Вывод:** выплата не зависит от того, сколько заплатил покупатель. Механика тождественна
СПП на ВБ: скидку покупателю финансирует площадка, наша база — наша цена.

### 1.3 Баллы — как считаются (ПРОВЕРЕНО 07.08)

- Приходят **отдельной транзакцией**, а не строкой внутри продажи. Сервис
  `ItemAgentServiceStarsMembership` («Звёздные товары»), привязка к продаже — по
  `posting.posting_number` и `items[].sku`.
- **Ставка ровно 1.5 % от суммы продажи, на 100 % отправлений** (1464 из 1467 = 1.5 %,
  3 отправления = 0.8 %). Не 20 %.
- **От зоны индекса НЕ зависят** — проверено по всем зонам:

| Зона | SKU | Выручка | Баллы | % от выручки |
|---|---|---|---|---|
| SUPER | 405 | 9 306 188 | 140 023 | **1.5 %** |
| YELLOW | 108 | 4 775 538 | 71 649 | **1.5 %** |
| RED | 162 | 3 112 670 | 46 883 | **1.5 %** |
| GREEN | 107 | 2 737 897 | 41 377 | **1.5 %** |
| WITHOUT_INDEX | 52 | 1 984 960 | 29 775 | **1.5 %** |

**Вывод: баллы — плоский налог на оборот, а не рычаг.** Зелёный индекс баллами не
«оплачивается» и на их размер не влияет. 20 % на тарифе Premium — это кэшбэк
на стороне ПОКУПАТЕЛЯ, его платит Озон; в наших транзакциях этой суммы нет вовсе.

### 1.4 Цена покупателя — ЗАКРЫТО 07.08 (шаг 1 выполнен)

**Прямого источника в Seller API нет.** Проверены пять эндпоинтов, все отклонены:

| Источник | Что отдаёт | Вердикт |
|---|---|---|
| `/v5/product/info/prices` | поля `marketing_price` в схеме больше нет; `marketing_seller_price` = 0.969 × `price` | наша же скидка |
| `/v3/product/info/list` | тот же блок `price` | цены покупателя нет |
| отчёт по товарам (async) | «Текущая цена с учетом скидки» = 1.049 × наша; «Цена Premium» пуста у всех 22 389 строк | не то |
| `/v1/actions/products` | `action_price` ≈ 0.90 × наша | цена в акции, не витрина |
| `/v1/product/info/discounted` | пусто | только уценённые |

**Восстанавливаем по факту продаж:** `buyer = our_price × k`, где
`k = customer_price / price` из `raw_ozon_posting.financial_data`. Точная цена покупателя
есть в постингах и закрывает **92 % выручки acc1 / 87 % acc2** за июль — остальному
каталогу k присваивается по медиане аккаунта.

**Почему модель законна (замеры 07.08):**
* субсидия Озона — **процент, а не фиксированная сумма**: корреляция суммы субсидии
  с ценой **+0.97**, корреляция k с уровнем цены **−0.09** (k ≈ 0.54…0.62 во всех корзинах);
* k устойчив во времени: `|k(июль) − k(июнь)|` медиана **0.032**, у 91 % SKU < 0.10;
* **снижение нашей цены доходит до покупателя**: на 59 SKU с изменением цены июнь→июль
  передача Δ медиана **1.17** (p25 0.96), корреляция **+0.76**.

**Следствие — заморозка списка 285 SKU СНЯТА.** Прежний вывод «снижение нашей цены
не обязано двигать индекс» опровергнут: Озон свою скидку в ответ не убирает, формула
`скидка = 1 − 1.05/индекс` рабочая и скорее консервативная. Условие применения теперь
одно — проверка по марже (KPI 25 %, шаг 2) и пилот, а не отсутствие данных.

**Витрина:** `mkt_ozon_buyer_price` (миграция 113, `reports/ozon_buyer_price.py`),
журнал прогонов `mkt_ozon_buyer_price_run`. Снимок 06.08: acc1 22 413 строк (415 с k
по своему SKU), медиана k 0.572; acc2 13 456 (141), медиана k 0.549.

**Честная точность (holdout: k по продажам старше 14 дней → проверка на свежих):**

| | n | медиана предсказ./факт | в ±10 % |
|---|---|---|---|
| k по своему SKU (acc1) | 142 | 0.999 | 66 % |
| k = медиана аккаунта (acc1) | 89 | 0.949 | 49 % |
| k по своему SKU (acc2) | 30 | 0.958 | 53 % |
| k = медиана аккаунта (acc2) | 42 | 0.916 | 45 % |

Смещения нет (медиана ≈ 1.0), но попадание в ±10 % ограничено сверху **самой природой
цены**: при ОДНОЙ и той же нашей цене у одного SKU разные покупатели видят разные цены —
размах k внутри пары (SKU, цена) медиана **0.080**, коэффициент вариации 5.5 %, совпадают
все продажи лишь у 3 % пар. То есть цена покупателя — не число, а распределение
(Premium, кредитка Озон Банка, персональные скидки). Точность на уровне медианы —
предел, а не недоработка; для управления ценой этого достаточно.

## 2. Контроль маржи (не начато)

Аналог `mkt_margin_control` для ВБ: KPI — чистая ≥ 25 % от НАШЕЙ цены до скидок.
Что нужно:
1. витрина `mkt_ozon_margin_control`: наша цена → комиссия (`commission_fbo_pct`
   из `ozon_price_index`, уже собирается) → логистика → реклама → баллы 1.5 %
   → подписка → COGS (`oz_cogs_demand`) → чистая и % от нашей цены;
2. предел снижения цены = где маржа падает до 25 %, а не до нуля (на ВБ этот
   guardrail называется `promo_limit_25`);
3. пересечь с индексом: SKU, где выход в GREEN укладывается в guardrail — можно
   снижать; где не укладывается — не скидка, а смена поставщика/вывод.

## 3. Реклама: что мы видим и чего не видим

### 3.1 Два вида кампаний, июль

| Аккаунт | Тип | Кампаний | Расход | Приписанная выручка | ДРР |
|---|---|---|---|---|---|
| acc1 | Трафареты (`SKU`) | 14 | 246 511 ₽ | 15 224 690 ₽ | 1.6 % |
| acc1 | Оплата за заказ (`ALL_SKU_PROMO`) | 2 | 649 609 ₽ | **не собирается** | — |
| acc2 | Трафареты | 10 | 110 384 ₽ | 4 098 358 ₽ | 2.7 % |
| acc2 | Оплата за заказ | 2 | 157 029 ₽ | **не собирается** | — |

**Дырка №1: у 70 % рекламного бюджета нет выручки в наших данных.** «Оплата за заказ»
работает по ставке 7 % с заказа, значит приписанная выручка ≈ расход / 0.07 —
для acc1 это ≈ 4.4 млн ₽ (43 % месячной выручки). Это оценка, не факт: нужный
эндпоинт Performance API не подключён.

**Дырка №2: органику посчитать нельзя.** Трафареты приписывают 63 % выручки,
«Оплата за заказ» ещё ~43 % — в сумме 106 %, то есть атрибуции пересекаются
и один заказ считают обе кампании. Пока не разведём, «сколько продаём без рекламы»
достоверно не ответить.

### 3.2 Покрытие ассортимента

Снимок ставок `ozon_bids` от 17.07 (устарел на 3 недели), покрывает 7 из 8 кампаний
acc1 и 5 из 6 acc2 — не собрана ровно «Оплата за заказ», у неё нет ставок по SKU
(она по определению на весь каталог).

| | карточек | продавалось в июле | SKU в Трафаретах | из них продавались |
|---|---|---|---|---|
| acc1 | 77 268 | 587 | 209 | 19 |
| acc2 | 13 604 | 219 | 145 | 21 |

**Открытое противоречие:** Трафареты приписывают 63 % выручки, но продавались всего
19 их SKU. Либо снимок ставок неполный (собирается не весь список SKU кампании),
либо атрибуция Озона считает ассоциированные заказы. **Проверить до любых решений
по ставкам** — тест: снять ставки заново и сверить число SKU в кампании с ЛК.

## 4. Поисковые фразы: что они дают и чего не дают

Собрано: `ozon_search_query` — 842 435 строк, недели 22.06–03.08, acc1 113 028
уникальных фраз / 12 345 SKU, acc2 86 329 фраз / 9 083 SKU.

**Что видим:** фразы, которые Озон привязал к НАШИМ карточкам, с позицией, показами,
конверсией в просмотр, заказами и GMV. В том числе строки с `position = 0` —
7 % acc1, 12 % acc2: фраза к карточке привязана, но мы по ней не ранжируемся.
Это и есть ближайший к «где нас нет» слой, который у нас есть.

**Чего НЕ видим:**
- фразы, по которым наш товар Озон вообще не привязал к выдаче — то есть спрос,
  где нас нет как класса. Эндпоинт отдаёт запросы **по нашим товарам**, не рынок целиком;
- **по каким фразам ранжируются конкуренты** — таких данных Ozon Seller API не отдаёт
  ни на одном тарифе. Косвенно: наш `position = 0` при живом спросе = там кто-то другой;
- связки «фраза → расход рекламы». В Трафаретах нет отчёта по фразам, поэтому
  «мусорные фразы, которые едят бюджет» **напрямую не видны**. Реконструкция возможна
  только через `position`/`order_count` из поиска против расхода кампании — грубо.

**Ловушка (проверено):** наивный отчёт «спрос есть — показов нет» даёт мусор,
топ фраз — «товары за 1 рубль», «для», «дождевик». Нужен фильтр релевантности профилю
до любых выводов.

## 6. План работ (порядок обязателен)

### Шаг 1. Юнит-экономика — цена покупателя ✅ СДЕЛАНО 07.08
Прямого источника в API нет (пять эндпоинтов проверены), цена восстановлена
из фактических продаж: `mkt_ozon_buyer_price`, миграция 113,
`reports/ozon_buyer_price.py`. Подробности и точность — раздел 1.4.
**Заморозка списка 285 SKU снята**: субсидия Озона процентная и наши снижения цены
не гасит (передача Δ 1.17, корреляция +0.76).

### Шаг 2. Контроль маржи
Витрина `mkt_ozon_margin_control` + `promo_limit_25` (раздел 2). Даёт ответ
«на сколько реально можем упасть» — по каждому SKU, от KPI 25 %, а не от нуля.

### Шаг 3. Реклама — закрыть дырки измерения
1. подключить выручку/заказы «Оплаты за заказ» (70 % бюджета вслепую);
2. развести пересекающуюся атрибуцию, посчитать органику;
3. перезабрать `ozon_bids` и снять противоречие из 3.2;
4. поставить `ozon_ads` + `ozon_bids` на cron — сейчас руками.

### Шаг 4. Ставки
Только после шага 3. Логика как на ВБ: поднимать там, где маржа после рекламы
держит 25 %, резать там, где ДРР съедает guardrail. Ставки — расчёт и предложение;
**отправка на площадку — по отдельной команде.**

### Шаг 5. Спрос и видимость
Витрина Б: `position = 0` + живой спрос + релевантность профилю → список
«где нас нет, а спрос есть». После шага 4, потому что часть таких дыр закрывается
ставкой, а не контентом.
