# wb4c: единая актуальная база расходов Ozon для сторожей

20.10.2026, прямое поручение пользователя: «базу для расходов Озона надо починить,
отдай wb4c задачу (он кстати финансовые показатели перевел на новые методы,
все работает?)».

Это поручение исправить базу и довести прежнюю API-миграцию до проверенного
рабочего состояния, сохраняя чужие изменения. Работа в собственном worktree.
Наш worktree fin-shipment-guard не редактировать; изменения общих функций
и контрактов передавать отдельными коммитами для интеграции.

## Найденный дефект

Сторож заказов использует ms_shipment_rules, первоначально заполненную
shipment_guard.bootstrap.seed_rules. Для Ozon там жёстко выбран август,
чтение reports/data/mp_ozon_hist.json и ON CONFLICT DO NOTHING.
При смене месяца правило не обновляется. У oz_acc2 сейчас:

- retention = 0.5543316670175045133485603517;
- base_from/to = 01–31.08.2026, valid_until = 30.10.2026;
- version = promo-absolute-300-or-10pct-v1:7314386e46d8.

Действующий сторож акций использует ops.ozon_stock_action.keep_ratio:
предыдущий календарный месяц, reports.ozon_mp_report.balance и EXP_SVC,
с округлением keep до четырёх знаков. Это другой механизм и другая база.
Проверка 20.10 для сентября oz_acc2: sales 2 811 459 ₽,
сумма abs(EXP_SVC) 1 709 146,67 ₽, keep 0.3921, retention 60.79%.
Это воспроизведение текущего алгоритма, не подтверждение корректности всех
его экономических допущений.

Контрольный заказ 10879561-0077-1: Ozon=МС=728 ₽, 1 шт., FIFO 69,28 ₽.
При августовской базе пол 828,60 ₽, gap −100,60 ₽;
при keep=0.3921 по текущему сторожу акций пол 941,80 ₽, gap −213,80 ₽.
Расхождение нельзя устранять подгонкой результата или сменой целевой прибыли.

## Что исправить

1. Один общий источник/механизм базы по account и периоду для:
   - сторожа акций/лестницы Ozon;
   - сторожа отгрузок;
   - customer-order пилота.
   Найти остальные потребители расчёта доли расходов, не оставлять независимые
   правила месяца/округления/фолбэков.
2. Выбирать последний подтверждённо полный закрытый месяц. Предыдущий
   календарный месяц не становится полным только потому, что наступило первое число.
   Учитывать полноту источников/закрытие/известные сбои сборщика.
   Нет подтверждённой базы — явный статус, без тихой подстановки константы
   или устаревшего августа. Последнюю пригодную базу можно показывать с её датой
   и причиной отсутствия новой, не выдавая за актуальную.
3. Сверить числитель/знаменатель с проверенными финансовыми источниками:
   продажи, комиссия, доставка, партнёры, FBO, продвижение, штрафы,
   неклассифицированное; отдельно проверить знаки корректировок, возвраты,
   компенсации и отсутствие двойного счёта.
   Не выводить revenue/points split из posting. Не менять финансовые витрины
   ради совпадения контрольного пола.
4. Проверить применимость общей доли кабинета к FBS: какие расходы FBO,
   реклама и общие услуги включены сейчас. Зафиксировать ограничения.
   Изменение экономического состава расходов/переход на SKU- или scheme-базу
   представить отдельно от исправления механизма актуальности.
5. Сохранять источник, период, суммы числителя/знаменателя, precision,
   полноту, время и неизменяемую версию базы. До обновления текущей строки
   сохранить прежнюю версию, чтобы исторические проверки оставались объяснимыми.
   Не исправлять прошлые результаты задним числом: пересчёт — новая проверка.
6. Обновление должно быть идемпотентным, из уже собранных данных,
   без дополнительных запросов к МС и без полного run_daily/исторической пересборки.
   Предоставить интерфейс потребителям и отдельный понятный способ обновления.
7. Не менять правило max(300 ₽ × количество продаваемых единиц,
   10% полной себестоимости). Один набор — продаваемая единица по правилам
   конкретного инструмента, не число его компонентов. Отличать нарушение
   этого целевого пола от фактического убытка.

## Проверка и внедрение

- Тесты смены месяца, неполного/пустого периода, ошибок источника, разных кабинетов,
  повторного обновления, знаков корректировок и сохранения старой версии.
- Одинаковый account/стоимость/количество/версия базы → одинаковый пол во всех
  потребителях до копейки.
- На контрольном заказе показать старый и новый расчёт с происхождением всех чисел.
- Собственные изменения коммитить отдельно; передать hash/файлы/проверки,
  точный интерфейс и порядок обновления базы владельцу customer-order.
- Подписки МС, расписания сторожей, рассылку и изменения цен на площадках не включать.
