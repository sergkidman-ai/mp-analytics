## 2. Что исправлено 2026-08-03 (коммиты `7bb88d9`, `4c688be`)

1. **`parentEntityId` / 400 на Яндексе — причина была не в коде.** Фикс `8131eff` лежал на диске
   с 30.07, а `feedback-moderation.service` работал с 28.07 без рестарта: Python держал в памяти
   старый `collectors/feedback_send.py`. Своего кода отправки Яндекса у бота нет — всё через
   `fs.post_answer()` → `send_yandex_question()`.
   **Правило: после любой правки кода rev — `systemctl restart feedback-moderation.service`.**
   `Restart=always` не помогает, процесс не падает.
2. **Потеря `final_text` при сбое.** `_do_send()` при провале не сохранял текст → правку оператора
   нельзя было дослать. Теперь `final_text` пишется и в ветке `failed`.
3. **Git-ревизия в стартовом логе бота** (`rev=<short HEAD>`) — версия исполняемого кода видна
   в `journalctl`, без раскопок по `mtime`/`ps`.
4. **Фильтр текста от оператора — `tg_moderation.clean_operator_text()`.** Маркеров нет → текст и
   есть ответ; есть «Наш ответ:» → берём всё после последнего маркера и вырезаем служебные строки;
   маркеры есть, а «Наш ответ:» нет → **не отправляем и переспрашиваем** (`PENDING_EDIT` сохраняется).
   Проверено на инциденте 069H: 575 → 342 симв.
5. **Перезаписи опубликованного (обе по прямому разрешению).** ЯМ ответ `28208817` —
   `update_yandex_answer()`, `operationType=UPDATE` + `entityId={id,"ANSWER"}` (**не**
   `parentEntityId`: с ним создастся ВТОРОЙ ответ). WB вопрос `2CIAop8BMJha5m81xsZI` — тот же
   `PATCH /api/v1/questions`, ссылка без приклеенной точки.
   **NB: после правки WB отдаёт `answer.editable=false` — второй перезаписи уже не будет.**

## 3. Открытая задача — подбор товара в каталоге (`reports/catalog.py`)

Диагноз, 4 пункта:

1. **Ищем по коду оригинала.** Покупатель называет TN-2312 / DR-2355 — ищем эту строку в наших
   названиях, а продаём совместимые под своими кодами → ноль. Кросс-таблицы
   «код оригинала → модели принтеров → наши SKU» в базе нет.
2. **Ищем только по названию** (`wb_cards.title`, `ozon_product.name`, `raw_yandex_offer→offer.name`).
   Списки совместимости в `raw_ozon_attributes` и `raw_wb_card_content.payload->>'description'`
   не читаются, хотя в название влезает 5–6 моделей, а карточка покрывает десятки.
3. **Суффиксы не нормализуются.** `DCP-7180DN` требует буквального вхождения; карточка «DCP-7180»
   не совпадёт. Нужен матч по числовому ядру + серии.
4. **`compat_cache` не используется как источник подбора.** Хранит вердикт по паре
   (наша карточка × модель принтера); обратного индекса «какая карточка подходит модели X» нет.

Контроль на Brother DCP-7180DN: по всей базе строк `DCP-7180`, `7180DN`, `HL-2260`, `TN-2312`,
`TN-2325`, `DR-2355` — **ноль**. Товара под эту модель у нас нет; Brother L2300/L2500
(TN-2335, TN-2375/2375X, DR-2335 DU) — другое поколение, в подбор идти не должно.

## 4. Правила работы потока

- **Ничего не писать на площадки без прямой команды Сергея.** Dry-run и подготовка — можно;
  запись — только по команде. Опубликованный ответ отозвать нельзя.
- Вопросы — всегда через модерацию (`route='review'`), публикация по ✅.
- Секреты только в `.env`, в чат не выводить.
- Коммитить **только файлы потока rev**: в рабочем дереве постоянно лежат незакоммиченные правки
  чужих потоков — не подхватывать. Пуш двумя отдельными командами (`origin main`, затем
  `origin main:rev/feedback-multichannel`) — склейка через `&&` отбивается классификатором.
- Гигиена контекста: в чат ≤50 строк, сырой JSON не выводить, крупные ответы API — в файл.
- После правки кода — рестарт сервиса (см. п. 2.1) и проверка `rev=` в стартовом логе.
