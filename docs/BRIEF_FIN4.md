## Чем заменять (доступ у наших ключей уже есть, все три проверены)
| Метод | Что отдаёт | Особенности |
|---|---|---|
| `POST /v1/finance/accrual/types` | справочник статей, **124 шт** (`id` → `name`/`description`) | тело `{}`; выгружен в `docs/reference/ozon_accrual_types.json` |
| `POST /v1/finance/accrual/by-day` | все начисления за **ОДИН** день | `{"date":"YYYY-MM-DD","limit":1000,"last_id":"…"}`; `last_id` — **строка**, на 1-й странице не передавать (число → 400); пустой/`"0"` = конец. `total_amount` = объект `{amount,currency}`. История есть (проверено 01.06) |
| `POST /v1/finance/accrual/postings` | начисления по номерам отправлений | обязательный `posting_numbers`, **1–200 штук** за запрос |

Форма ответа `by-day`: записи `accrual_id / date / total_amount / unit_number /
accrued_category` + блоки `item_fees`, `non_item_fee`, `container_fees`, `posting`.
`accrued_category` ∈ {`ITEM`, `NON_ITEM`, `POSTING`}. Внутри — суммы по `type_id`
из справочника (54 «Продвижение товара», 41 «Оплата за клик», 1 «Эквайринг», 29 …).

## Главный факт для миграции — это ТОТ ЖЕ поток данных
Сверка за **05.09.2026** (день есть и в старой БД, и в новом API), oz_acc1:
- новый API: **125 записей, итог 135 089 ₽** (POSTING +174 790, NON_ITEM −37 757, ITEM −1 945);
- старая `raw_ozon_transaction`: **125 операций, amount 135 089 ₽**.
Количество и итог совпали, значит реконструкция 1:1 возможна. Разложение сохранено в
`docs/reference/ozon_accrual_vs_transaction_2026-09-05.json`, образец дня — в
`docs/reference/ozon_accrual_byday_sample.json` (15.09, 202 записи, одна страница).
**Открытый вопрос:** где в новой форме лежит «начисления за продажу» (в старом
`accruals_for_sale` за 05.09 = 330 184 при amount 135 089) — смотреть
`posting.products[].commission` и `delivery.total_accrued`.
