# Запрос в Альфа-Банк: добавить скоупы `payment` и `accounts`

**Кому:** `alfa_api@alfabank.ru` · **Поток:** inv · **Составлено:** 2026-07-27 ·
**Переписано:** 2026-07-28 (после получения справочника скоупов)

## Разгадка (2026-07-28)

Двое суток мы искали расхождение внутри контура банка. Расхождения нет — **мы просили не те
скоупы**. Банковский справочник «Scopes (области применения)» (копия:
`docs/alfa/scopes_reference.txt`) даёт однозначное сопоставление:

| scope | Описание | Методы |
|---|---|---|
| `payment` | **Платёжные поручения** | `POST /jp/v2/payments`, `GET /jp/v2/payments/{externalId}`, `.../state`, `.../print-form`, `PATCH .../state` |
| `accounts` | **Счета** | `GET /pp/v1/accounts`, `.../{accountNumber}`, `.../requisites` |
| `signature` | Электронная подпись | `/jp/v3/signature/*` — выпуск/активация/отзыв **RSA-сертификатов** |
| `customer` | Профиль организации | `GET /jp/v2/customer-info` |
| `transactions` | Выписки по счетам ЮЛ | `GET /jp/v1/statement/transactions` и др. — **работает у нас** |

Выданный нам scope: `openid customer transactions signature profile email phone eio role inn`.
**`payment` и `accounts` в нём отсутствуют.** Все полученные 403 `insufficient_scope` —
корректные ответы шлюза.

Ошибка была в трактовке: `signature` мы понимали как «подпись платёжного поручения», а это
управление сертификатами ЭП. Отсюда же и `signature_rsa` в claim `scope_services` выданного
Alfa ID токена — тот же сервис ЭП под внутренним именем, к `jp/v2/payments` отношения не имеет.

Побочно: страница документации «API Key» перечисляет сервисы, доступные по ключу, — только
**выписки** (`scope=transactions`), **профиль организации**, **электронная подпись**. Платёжных
поручений там нет, поэтому платёжки в любом случае вызываем под `Authorization: Bearer` (так же
и в банковском примере из раздела «Тестирование Платёжных поручений»).

## Что просим

Добавить к доступу организации **ООО «ЦИФРОВОЙ КВАДРАТ»**, ИНН `7807355364`,
р/с `40702810432000015093` (Дисквэр в интеграцию не входит — его счёт в другом банке)
два скоупа — **и в песочнице, и в проме**:

1. **`payment`** — черновики платёжных поручений поставщикам. Создаём **БЕЗ `digestSignatures`**,
   то есть как черновик на подпись; автоподписи и автосписания в контуре нет и не планируется —
   подписывает человек в Альфа-Бизнес. Нужны также `GET /jp/v2/payments/{externalId}` и `.../state`
   для контроля состояния.
2. **`accounts`** — `GET /pp/v1/accounts`, только чтение остатка, чтобы не формировать платёж
   на сумму больше фактического остатка.

## Что проверено (для протокола заявки)

Выписка в проме работает ежедневно: `GET /jp/v1/statement/transactions`, scope `transactions`,
mTLS с боевым сертификатом; разносится в МойСклад.

Сценарий Alfa ID (OIDC) пройден ПОЛНОСТЬЮ 28.07: выпущен Client secret для песочной
H2H-интеграции, пройден `oidc/authorize` на `id-sandbox.alfabank.ru` тестовой учёткой ЮЛ из
банковской документации (`SomeDifficultLogin`, OTP `000000`, подпись согласия `111111`), получен
`code`, обменян на `access_token` (`POST https://sandbox.alfabank.ru/oidc/token`, mTLS +
`client_secret`; `Bearer`, 3600 с, `refresh_token` выдан). Claim `scope_services` =
`["signature_rsa", "transactions", "CUSTOMER_INFO"]` — ровно выданные три сервиса.

Обоими способами авторизации (`ApiKey` + mTLS и `Bearer` + mTLS), песочница и пром:

| Метод | Ответ |
|---|---|
| `POST /jp/v2/payments` | 403 `insufficient_scope` |
| `GET /jp/v2/payments/{externalId}` | 403 `insufficient_scope` |
| `GET /pp/v1/accounts` | 403 `insufficient_scope` |
| `GET /jp/v1/statement/transactions` | работает |

Версия «дело в теле запроса» исключена отдельно: `POST /jp/v2/payments` с полным телом по
банковскому примеру (тестовые БИК `044525593`/`040173745`) даёт тот же 403 — до валидации тела
запрос не доходит. Перевыпуск ключа песочницы 28.07 картину не изменил. Всё это согласуется
с разгадкой выше.
