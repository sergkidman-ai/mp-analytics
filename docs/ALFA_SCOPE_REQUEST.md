# Запрос в Альфа-Банк: расширение скоупов API (черновики платежей + остатки)

**Кому:** `alfa_api@alfabank.ru` · **Поток:** inv · **Составлено:** 2026-07-27
**Статус:** готово к отправке (отправляет Сергей). Ответ банка → сюда же и в `docs/HANDOFF.md`.

## Зачем

Наша сторона интеграции готова полностью: черновики платёжек формируются автоматически из графика
оплаты поставщикам, остаётся только подписать их человеком в Альфа-Бизнес. Упираемся ровно в права
доступа ключа — **ни один из двух нужных методов не открыт ни в проме, ни в песочнице**, хотя в
выданном нам описании доступа scope эти права содержит.

## Проверено 2026-07-27 (оба контура, один и тот же ключ-схема `ApiKey` + mTLS)

| Метод | Назначение | Prod (`baas.alfabank.ru`) | Sandbox (`sandbox.alfabank.ru`) |
|---|---|---|---|
| `GET /api/jp/v1/statement/transactions` | выписка (используем ежедневно) | **200 OK** | **200 OK** |
| `GET /api/pp/v1/accounts` | остаток на р/с | **403 `insufficient_scope`** | **403 `insufficient_scope`** |
| `POST /api/jp/v2/payments` | создание НЕПОДПИСАННОГО черновика платёжки | **403 `insufficient_scope`** | **403 `insufficient_scope`** |

Тело ответа в обоих случаях:
`{"error":"insufficient_scope","error_description":"The request requires higher privileges than provided by the access token"}`

Важно: в песочнице поведение идентичное прому, поэтому **отладить сценарий на тестовом контуре
тоже нельзя** — это не вопрос перехода в бой, а вопрос прав ключа.

## Проверено повторно 2026-07-28 — по просьбе поддержки, вне Портала разработчика

Поддержка предложила «протестировать данный скоуп вне Портала разработчика по стандартному
сценарию». Сделали это **обоими** способами авторизации.

**1. Упрощённая авторизация (`Authorization: ApiKey` + mTLS).** Картина та же, что 27.07:
`GET`/`POST /api/jp/v2/payments*` → **403 `insufficient_scope`** и в песочнице, и в проме;
тем же ключом `GET /api/jp/v1/statement/transactions` отвечает штатно (400 по валидации
параметра, т.е. авторизация проходит). **Ключ песочницы был перевыпущен 28.07 — результат не
изменился**, те же 403.

**2. Авторизация через Alfa ID (OIDC) — «стандартный сценарий». Пройдена ПОЛНОСТЬЮ.**
Выпустили Client secret для песочной H2H-интеграции (28.07), прошли `oidc/authorize` на
`id-sandbox.alfabank.ru` тестовой учётной записью ЮЛ из вашей документации
(`SomeDifficultLogin`, OTP `000000`, подпись согласия `111111`), получили `code` и обменяли его
на `access_token` (`POST https://sandbox.alfabank.ru/oidc/token`, mTLS + `client_secret`).
Токен получен штатно: `token_type=Bearer`, `expires_in=3600`, `refresh_token` выдан.

**И вот главное.** В выданном ВАМИ access_token (JWT, `iss=https://id-sandbox.alfabank.ru/oidc`,
`aud=5052e56f-8bca-4cda-9d81-57422e0ebf93`) содержится claim:

    "scope_services": ["signature_rsa", "transactions", "CUSTOMER_INFO"]

То есть права на подпись и на данные клиента в токене **есть**. Тем не менее запросы с этим
`Authorization: Bearer …` (+ mTLS) дают:

| Метод | Ответ с Bearer-токеном |
|---|---|
| `POST /api/jp/v2/payments` | **403 `insufficient_scope`** |
| `GET /api/jp/v2/payments/{externalId}` | **403 `insufficient_scope`** |
| `GET /api/pp/v1/accounts` | **403 `insufficient_scope`** |
| `GET /api/jp/v1/statement/transactions` | 400 (валидация параметра) — т.е. **работает** |

Вывод: расхождение внутри контура банка. Alfa ID выдаёт токен с `signature_rsa` и
`CUSTOMER_INFO`, а шлюз API эти права не признаёт; при этом `transactions` из того же токена
отрабатывает. Значит вопрос не в способе авторизации и не в нашей интеграции.

**Версия «дело в теле запроса» исключена:** `POST /jp/v2/payments` отправлен с ПОЛНЫМ телом по
примеру из банковского раздела «Тестирование Платёжных поручений» (`externalId`, `amount`, `date`,
`deliveryKind`, реквизиты сторон, тестовые БИК `044525593`/`040173745`) — тот же 403
`insufficient_scope`, до валидации тела запрос не доходит. Оттуда же на будущее: платёжки в примере
вызываются именно под `Authorization: Bearer` (не ApiKey), а для ПОДПИСАННЫХ платёжек в песочнице
нужен `certificateUuid` = серийный номер тестового RSA-серта `61000366d11e143acbc03a56d70001000366d1`
(нам не нужен — создаём черновики без подписи).

## Что просим открыть

Для организации **ООО «ЦИФРОВОЙ КВАДРАТ»**, ИНН `7807355364`, р/с `40702810432000015093`
(Дисквэр в интеграцию не входит — его счёт в другом банке):

1. **`signature`** — метод `POST /api/jp/v2/payments`.
   Подчёркиваем: платёжки создаём **БЕЗ `digestSignatures`**, то есть как черновик на подпись.
   Автоматической подписи и автоматического списания в контуре нет и не планируется — подписывает
   человек в веб-интерфейсе Альфа-Бизнес. Сопутствующие методы того же блока, которые нужны для
   контроля состояния: `GET /api/jp/v2/payments/{externalId}` и `.../state`.
2. **`customer profile inn role eio`** — метод `GET /api/pp/v1/accounts` (только чтение остатка).
   Нужен, чтобы не формировать платёж на сумму больше фактического остатка на счёте.
3. **Сверить привязку продуктов к приложению на шлюзе API.** Токен с `signature_rsa` и
   `CUSTOMER_INFO` шлюзом не признаётся (см. раздел 2) — просим проверить, какие права
   фактически привязаны к приложению `9caa44f8-f64c-4dd3-baed-d14798966961` и к тестовому
   `client_id 5052e56f-8bca-4cda-9d81-57422e0ebf93` на стороне продуктов
   `jp/v2/payments` и `pp/v1/accounts`.
4. **Уточнить точное имя скоупа** для `POST /api/jp/v2/payments`. В токене Alfa ID выдаёт
   `signature_rsa`, в описании доступа нам заявлен `signature`, а поддержка ищет `payment` —
   три разных имени. Просим назвать то, которое ожидает шлюз, и открыть именно его.

Тестовый пользователь песочницы нам НЕ нужен — нашли его в вашей документации
(«Тестирование Alfa ID», раздел ЮЛ), сценарий на нём пройден.
