# Запрос в Альфа-Банк: расширение скоупов API (черновики платежей + остатки)

**Кому:** `alfa_api@alfabank.ru` · **Поток:** inv · **Составлено:** 2026-07-27
**Статус:** готово к отправке (отправляет Сергей). Ответ банка → сюда же и в `docs/HANDOFF.md`.

## Зачем

Наша сторона интеграции готова полностью: черновики платёжек формируются автоматически из графика
оплаты поставщикам, остаётся только подписать их человеком в Альфа-Бизнес. Упираемся ровно в права
доступа ключа — **ни один из двух нужных методов не открыт ни в проме, ни в песочнице**, хотя в
выданном нам описании доступа scope эти права содержит.

## Проверено 2026-07-27 (оба контура, один и тот же ключ-схема `ApiKey` + mTLS)

| Метод | Назначение | Prod (`baas.alfabank.ru`) | Sandbox (`sandbox.alfabank.ru`) |
|---|---|---|---|
| `GET /api/jp/v1/statement/transactions` | выписка (используем ежедневно) | **200 OK** | **200 OK** |
| `GET /api/pp/v1/accounts` | остаток на р/с | **403 `insufficient_scope`** | **403 `insufficient_scope`** |
| `POST /api/jp/v2/payments` | создание НЕПОДПИСАННОГО черновика платёжки | **403 `insufficient_scope`** | **403 `insufficient_scope`** |

Тело ответа в обоих случаях:
`{"error":"insufficient_scope","error_description":"The request requires higher privileges than provided by the access token"}`

Важно: в песочнице поведение идентичное прому, поэтому **отладить сценарий на тестовом контуре
тоже нельзя** — это не вопрос перехода в бой, а вопрос прав ключа.

## Проверено повторно 2026-07-28 — по просьбе поддержки, вне Портала разработчика

Поддержка предложила «протестировать данный скоуп вне Портала разработчика по стандартному
сценарию». Сделали это **обоими** способами авторизации.

**1. Упрощённая авторизация (`Authorization: ApiKey` + mTLS).** Картина та же, что 27.07:
`GET`/`POST /api/jp/v2/payments*` → **403 `insufficient_scope`** и в песочнице, и в проме;
тем же ключом `GET /api/jp/v1/statement/transactions` отвечает штатно (400 по валидации
параметра, т.е. авторизация проходит). **Ключ песочницы был перевыпущен 28.07 — результат не
изменился**, те же 403.

**2. Авторизация через Alfa ID (OIDC) — «стандартный сценарий».**
`GET https://id-sandbox.alfabank.ru/oidc/authorize?response_type=code&client_id=5052e56f-8bca-4cda-9d81-57422e0ebf93&redirect_uri=http://localhost&scope=openid customer transactions signature profile email phone eio role inn&state=…`
принимается: запрос доходит до страницы входа Alfa ID, `redirect_uri` и `state` отрабатывают
корректно (т.е. сам `client_id` и список скоупов, включая `signature`, приложением приняты).
Но вход **реальной учётной записью Alfa ID** завершается редиректом
`http://localhost/?error=login_expired&state=…` — в двух попытках подряд, вторая отработала
**за 12 секунд** (18:58:04 → 18:58:16 МСК), то есть это отказ, а не истечение сессии входа.
**Тестовый пользователь Alfa ID для песочницы нам не предоставлялся.**

Вывод: пройти сценарий до получения `access_token` мы не можем — упираемся в отсутствие
тестового пользователя, а по ключевой схеме `ApiKey` метод закрыт правами в обоих контурах.

## Что просим открыть

Для организации **ООО «ЦИФРОВОЙ КВАДРАТ»**, ИНН `7807355364`, р/с `40702810432000015093`
(Дисквэр в интеграцию не входит — его счёт в другом банке):

1. **`signature`** — метод `POST /api/jp/v2/payments`.
   Подчёркиваем: платёжки создаём **БЕЗ `digestSignatures`**, то есть как черновик на подпись.
   Автоматической подписи и автоматического списания в контуре нет и не планируется — подписывает
   человек в веб-интерфейсе Альфа-Бизнес. Сопутствующие методы того же блока, которые нужны для
   контроля состояния: `GET /api/jp/v2/payments/{externalId}` и `.../state`.
2. **`customer profile inn role eio`** — метод `GET /api/pp/v1/accounts` (только чтение остатка).
   Нужен, чтобы не формировать платёж на сумму больше фактического остатка на счёте.
3. **Тестовый пользователь Alfa ID для песочницы** — логин и пароль тестовой учётной записи,
   которой можно пройти `oidc/authorize` на `id-sandbox.alfabank.ru`. Без него сценарий с
   OIDC-авторизацией недоступен: реальная учётная запись в песочницу не пускает (см. раздел выше).

Отдельно уточним: скоупа с именем **`payment`** в описании Alfa API мы не встречали — платёжные
поручения относятся к **`signature`**. Если проверка на вашей стороне идёт по имени `payment`,
возможно, поэтому он и не находится ни в кабинете, ни в привязке к приложению.
