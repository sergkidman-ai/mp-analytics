## Вход в сессию (шпаргалка)
```
ssh <сервер>
tmux ls                 # список сессий; каноничные имена: fin mkt rev gab inv china
tmux attach -t <имя>    # напр. tmux attach -t mkt
# внутри tmux:  Ctrl+b d — отсоединиться (сессия живёт);  tmux switch-client -t <имя> — перейти в другую
```

## Процедура переезда сессии
Переезд = чистый рестарт Claude в той же tmux-сессии (напр. при переполнении контекста). **Tmux-сессии
при переезде НЕ пересоздаются** — новый `claude` стартует в уже существующем окне того же потока.
1. **Дежурному (перед выходом):** обнови свою секцию потока в этом `HANDOFF.md` (состояние / сделанное /
   активные ветки / открытые вопросы / следующий шаг) и **закоммить всё незакоммиченное** в своей ветке.
2. `/exit` — завершить текущую сессию Claude.
3. `claude` — запустить заново в ТОЙ ЖЕ tmux-сессии (окно потока не трогаем).
4. Стартовое сообщение новой сессии:
   > «Ты сессия потока **X**, прочитай `CLAUDE.md` + свою секцию `HANDOFF` + `BRIEF`, доложи и продолжай».

**Симптом:** выписка приходит, платежи создаются, но к приёмкам не привязываются — владелец разносил руками.

состав платежа вытаскивался регэкспом из текста назначения:
- **ОДИССЕЙ** — `alfa_link.py` выбрасывал `ОД00004103` правилом «кириллический префикс без разделителя»
  (писалось против мусора `карте220015`); приёмка `ОД00004103` в МС есть;
- **Солюшнс принт** — токен `326006`, в МС приёмка `326006/И` (суффикс терялся);
- **Картридж Трейд** — счёт `КТ-00097`, в МС `КТ-000097` (разрядность на ноль больше); разворот
  сокращённых номеров (`100`→`КТ-00100`) берёт разрядность из первого токена платежа, а не из МС.

**Усилитель:** `plan()` требует раскладки без остатка → ОДИН неразобранный номер блокировал платёж целиком.
У №598377 (Одиссей, 474 950,87 ₽) нашлась 1 приёмка на 6 890,12 ₽ → не записалось ничего. Мимо автоматики
прошло ~630 тыс. ₽ (Одиссей 474 951 + Солюшнс 144 270 + К.Трейд 10 693).

**Решение Сергея 2026-08-01:** состав платежа брать **из черновика платёжки** (`payment_draft_queue.covers_po_ids`
— заказы, под которые черновик собран), разбор назначения — ЗАПАСНОЙ путь (платежи мимо очереди). Черновик
закрепляется за платежом через `ms_payment_id` (миграция 206), чтобы два одинаковых платежа одному поставщику
не разобрались одним черновиком. Остаток по черновику **не блокирует** запись (в отличие от разбора текста):
он значит «приёмку по оплаченному заказу ещё не провели» → привязываем что есть и добираем, как у аванса.

**Реплей 27–31.07 без записи:** Одиссей 1 приёмка → **20 на всю сумму**, Солюшнс 1 → **10 на всю сумму**,

**Запасной путь починен (решение Сергея 2026-08-01, коммит в этой же ветке).** Платежи БЕЗ черновика
(владелец платит из банка руками) разбираются по назначению, и здесь действует правило:
**кандидаты — ТОЛЬКО приёмки, к которым исходящий платёж ещё не привязан** (`unpaid_left(s) > 0`;
отдельного поля связи в МС нет, `payedSum` и есть «сколько денег к ней привязано»). Оплаченную приёмку
деньги второй раз не ищут — фильтр заодно снимает неоднозначность одинаковых номеров. Три правки:
1. **токенизатор**: заглавный кириллический префикс без разделителя больше не выбрасывается
   (`ОД00004103`, `КТ00097` — номера; `карте220015`, `счет1234` со строчными — по-прежнему мусор);
2. **нестрогое сравнение номера** `_numkey` — самая длинная группа цифр без ведущих нулей:
   `КТ-00097`↔`КТ-000097` → 97, `326006`↔`326006/И` → 326006, `ОД00004103` → 4103. Применяется ТОЛЬКО
   если точного имени нет, ТОЛЬКО внутри пары контрагент+юрлицо и ТОЛЬКО по неоплаченным приёмкам;
3. **неоднозначность → ручной разбор**: если под ключ подходит больше одной неоплаченной приёмки,
   номер уходит в `missed` («подходят N приёмки»), не угадываем.

  - **`invoice_bot/seed_payment_terms.py`** — идемпотентный сид условий из файла (таблица в коде + резолв
    карточки МС по ИНН/подсказке имени). 11 строк в `supplier_payment_terms`, все ИНН нашлись в МС.
    Отсрочка: Солюшнс МСК 14д/150к, КПД 5д/вся сумма, Одиссей 14д/500к, КВК 5д/150к, Тонерстор 3д/100к,
    Компания РМ 14д/вся, Картридж Трейд 4д/вся. Аванс/баланс: Колортек 50к, Тонероптторг 100к, Позитив 100к
    (все при балансе <20к). Пооплатно: Феррет.
  - **Пачка deferred теперь режется по МЕНЬШЕМУ из двух** — `payment_cap` и живой остаток на р/с; в `note`
    черновика пишем, какой ограничитель сработал, и флажок «один заказ дороже лимита» (правило «первый
    заказ включаем всегда» сохранено, иначе долг не закроется). Проверено симуляцией остатка 300к:
    Одиссей (пул 913к, кап 500к) → пачка 242к, режет остаток; Тонерстор (пул 40к) → влезло целиком.
  - **ГЕЙТ ПО ОПЛАТЕ (важно, ловило повторную оплату):** факт оплаты берём из МС — `payedSum` заказа.
    В пул попадают только недоплаченные заказы, сумма = остаток `sum − payedSum`; закрывшиеся снимаются
    в `paid`, а если у заказа уже был черновик — в него дописывается предупреждение «оплачено вне системы».
    Без гейта первый прогон запланировал **59 черновиков на 704 314 ₽**, из которых у Феррета 54 из 56
    заказов (428 505 ₽) уже были оплачены вручную. После гейта — 5 черновиков на 275 809 ₽.
  - **Песочница НЕ обходной путь — проверено 2026-07-27 живыми запросами.** `.env` сейчас на
    **проме** (`ALFA_ENV=prod`, серт `prod_2026.cer` — банк его в итоге выдал, выписка ходит 200).
    Прогнали оба контура одним и тем же способом: `GET /jp/v1/statement/transactions` → **200 в обоих**;
    `GET /pp/v1/accounts` → **403 insufficient_scope в обоих**; `POST /jp/v2/payments` (реальный payload
    из очереди, БД не трогали) → **403 insufficient_scope в обоих**. То есть песочный ключ урезан так же,
    как боевой, и отладить черновики на тесте тоже нельзя — упор строго в права ключа, не в переход в бой.
    Письмо в банк готово: **`docs/ALFA_SCOPE_REQUEST.md`** (таблица «работает/не работает», что именно
    просим открыть, реквизиты заявки; отправляет Сергей на `alfa_api@alfabank.ru`). Отдельно для банка:
    в выданном описании доступа scope УЖЕ содержит `signature` и `customer/eio/role/inn` — просим сверить
    фактическую привязку скоупов к приложению.
  - **Реквизиты плательщика — из МС, а не из `.env`** (2026-07-27). БИК/корсчёт берём из карточки
    организации по ТОМУ ЖЕ номеру счёта, с которого платим (`ALFA_ACCOUNT[_PROD]`): у ЦК счёт …5093 →
    БИК `044030786`, корсчёт `30101810600000000786` (филиал «Санкт-Петербургский» Альфа-Банка). `.env`

    четыре пустые переменные перестали быть блокером. В проме несовпадение счёта = ошибка (чужой БИК на
    реальном платеже недопустим); в песочнице номер тестовый и в МС его нет — там разрешён фолбэк на
    основной счёт организации с явным предупреждением в логе.
  - **Гейт прода ослаблен до реальной отправки:** `ALFA_PAYMENT_PROD_READY` теперь проверяется только при
    `dry_run=False`. Раньше он глушил и dry-run, из-за чего боевой payload нельзя было проверить до выдачи
    скоупа. Реальная отправка на проде по-прежнему падает с понятной ошибкой (проверено).
  - **dry-run больше не портит очередь:** при ошибке сборки payload статус `error` пишется только в
    боевом режиме. Ловилось на себе — прогон в песочнице увёл все 4 живых черновика в `error`
    (восстановлены в `planned`, 272 172.45 ₽).
  - **Письмо в банк отправлено в Telegram-бот** (2026-07-27, обоим из `TG_ALLOWED_IDS`).
  - **Убрана пометка `paid` при отправке черновика** (`alfa_payment_draft.send_planned`). Отправляется
    НЕПОДПИСАННЫЙ черновик — деньги уйдут, только когда человек подпишет, а может и не подписать. Раньше
    заказы на отправке помечались `paid` и пропадали из пула (тихая потеря долга), а прогон в песочнице
    испортил бы реальный пул. Теперь заказы остаются в пуле, а в `paid` их переводит гейт по `payedSum`
    из МС — по факту оплаты. **Хвост на потом:** маячок «черновик висит неподписанным N дней» (сейчас
    такой заказ сидит в `queued` и в новую пачку не попадёт).
  - **ТОЛЬКО «Цифровой квадрат» (решение Сергея 2026-07-27):** счета на Дисквэр в контур оплаты НЕ входят
