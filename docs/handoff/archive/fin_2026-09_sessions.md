## Сессия 11–12.09 — УПД по уведомлениям о выкупе ВБ (подтаб «📄 УПД по выкупам»)

ВБ, выкупая наш товар, выпускает **уведомление о выкупе**; продавец обязан выставить РВБ УПД
(КНД 1115131, функция СЧФДОП, версия 5.03) и отправить через ЭДО. Было ручной работой — стало
контуром: сбор → генерация XML → страница с кнопкой → еженедельная сводка Наталии.

**Данные.** Документы ВБ лежат в отдельном API `documents-api.wildberries.ru`, категория
`redeem-notification`, отдача только zip (внутри XLSX + .sig + МЧД), лимит **1 запрос в 10 с**.
Скоуп «Документы» есть в `WB_TOKEN_PRICES_ACC1`, для acc2 заведён `WB_TOKEN_DOCS_ACC2`.
Сборщик `collectors/wb_documents.py` → таблица `wb_redeem_notice` (миграция 709, `sent_at` — 710).
Собрано с 29.12.2025: acc1 37 уведомлений / 768 338,93 ₽, acc2 37 / 481 757,99 ₽.

**Две даты, не перепутать:** `creationTime` — когда ВБ выложил документ в ЛК; дата в имени файла —
дата самого уведомления. **В УПД идёт вторая.**

**Генератор `reports/upd_form.py`** собирается подстановкой в принятый эталон
`reports/upd_sample_wb.xml` (windows-1251, CRLF, БЕЗ namespace — ElementTree тут не использовать,
он всё перепишет). Главная регрессия: УПД № 764559005 выходит **побайтово равным принятому
документу**, 6656 байт, кроме `ИдФайл` (и `ДатаИнфПр`/`ВремИнфПр` — их в сверке фиксировать).
Арифметика: `СтТовУчНал` = сумма выкупа с НДС, `СтТовБезНДС` = разность, `ЦенаТов` = разность/кол-во,
`НаимТов` = наименование + пробел + артикул. КИЗ не выводим (в уведомлениях пуст).

**Ставку НДС из уведомления брать НЕЛЬЗЯ** — ВБ не знает о переходе продавца и ставит 22 %
(неверна в 55 позициях из 791). Истина — режим продавца, таблица `VAT_FROM` в `reports/upd_orgs.py`:
Цифровой квадрат 5 % с 01.01.2026 (переход был в 2025), Дисквэр «без НДС» до 31.07.2026 и
**5 % с 01.08.2026** (НДС на УСН). Налог считается сверху вниз: `НДС = сумма × ст / (100 + ст)` —
на всех 500 позициях с верной ставкой это совпало с «Суммой НДС» ВБ до копейки. При «без НДС»
в `СумНал`/`СумНалВсего` идёт элемент `<БезНДС>`, а не `0.00`: число схема 5.03 не принимает.

**Реквизиты — `reports/upd_orgs.py`.** `edi_id` (ящик Диадока, `2BM-…`) из ИНН/КПП НЕ выводится:
у Цифрового квадрата в нём вообще другой КПП (780201001 против 771701001 в реквизитах). Оба
получены от Сергея. Покупатель всегда РВБ.

**Страница** `reports/upd_page.py` → `/reports/upd`, подтаб добавлен в `reports/mp_tabs.py`.
Кнопка «⬇ Скачать УПД» собирает XML на лету (`GET /reports/upd/file/{account}/{number}.xml`),
статус «выгружен» ставится вручную (`POST /api/upd/status`). Фильтры по организации и статусу —
клиентские, выбор хранится в localStorage (иначе слетал бы после каждой отметки, которая
перезагружает страницу). Отмечено выгруженными: acc1 по 29.06.2026 включительно (28 шт).

**Рассылка `ops/upd_weekly.py`** — в `run_daily.py`, ежедневно, НЕ по расписанию «по вторникам»:
ВБ выкладывает уведомления пн-вт, но день плавает, а задание шлёт только то, чего ещё не слало
(`sent_at`). Уходит **только текстовая сводка**, файлы в бот не идут — их забирают кнопкой;
УПД всё равно собирается перед отправкой как проверка собираемости. Окно 14 дней: старый хвост
намеренно не рассылается (иначе первый запуск вывалил бы 46 файлов за полгода). Адресат —
Наталия, `TG_PRC_NATALIA_ID=1231747786`, бот `@ds_prc_bot`; в `TG_PRC_NOTIFY_ID` лежит Сергей,
и ему этот бот, кстати, писать не может — `chat not found`.

**Грабли сессии:** uvicorn держит импортированные модули отчётов — после правки любого
`reports/*_page.py` обязателен `systemctl restart mp-dashboard`, иначе POST-роут перерисует
страницу старым кодом (на этом ранее «висел» удалённый Узбекистан на странице ФТС).
Ещё: `Path.read_text` схлопывает CRLF — эталон открывать с `newline=""`.


## Сессия 02–14.09 — почему маржа Маркета ушла в ноль: потолок/пол наценок

**Вопрос Сергея:** цены исторически ставятся от доли гросс-расходов площадки («МП заберёт эту
часть»), на Ozon схема работает, по Маркету закладывали 44 % — почему маржа ~0 и надо ли
закладывать 68 %?

**Тождество, на котором всё держится:** `маржа = 1 − g − c`, где `g` = гросс-расходы МП ÷ наша
цена, `c` = себестоимость ÷ наша цена; наценка `n = 1/(1 − g − маржа)`. Сходится: Ozon июль
1−0,599−0,216 = 18,5 % при факте 18,6; ЯМ август 1−0,677−0,282 = 4,1 % при факте 3,1.

**Ответ:** 68 % закладывать не нужно — оно уже заложено (в настройках акций стоит 66 % против
фактических 67,7). Ошибка была в базе: 44 % считали от цены покупателя, а не от нашей цены.
Закладка обещала «останется 56 % нашей цены», остаётся 32 %. Настоящая ставка размещения
≈ 15,6 % от денег покупателя (264 116 / 1 696 156); медианная глубина скидки — 45 % нашей цены.
Разбор заказа 59974603650: наша цена 86 680, покупатель заплатил 42 630 (49 %), субсидия 44 050,
«размещение» гросс 42 039 (деньгами 420 + зачётом 41 619), живыми деньгами осталось 21,5 %.

**Две таблицы Сергея (скриншоты 02.09, `dropbox/20260902_0709*`):**
- Потолок — наценка по интервалу закупочной цены (ЦК: DS/OZON/WB/YM; ДИС: OZON/WB).
- Пол — «Настройки участия в акциях»: Ozon 58 %+12 %, ВБ 55 %+12 %, ЯМ 66 %+12 %,
  минимальная прибыль 300 ₽ (общая для всех МП). Правило «10 % от цены продажи» НЕ применяется.
  «Прочие расходы 12 %» — это разнесённые опер. расходы в доле от оборота (вкладка «Опер.
  расходы» в Пульте), не логистика; на дорогом товаре аллокационно корректны, менять нечего.
- Пол-наценка = `1/(1 − комиссия − прочие)`: Ozon 3,33×, ВБ 3,03×, **ЯМ 4,55×**.

**Проверено:** потолок применяется — медиана `basicPrice`/закупка по 4 157 карточкам ЦК совпала
с таблицей до сотых. `basicPrice` = зачёркнутая цена и есть потолок; фактическая цена ниже.
На Ozon и ВБ пол держится (факт 4,63× при поле 3,33× и 4,48× при 3,03×). Маркет в августе —
единственная площадка, где пол был пробит: факт 3,55× при поле 4,55×, продавали за 65 % потолка.

**Наценку Маркета подняли 31.08.** Замер по позициям заказов (закупка из `tc_buy_price_latest`,
отменённые исключены, наша цена = оплата покупателя + субсидия): 15–30.08 — 194 позиции, 4,36×;
31.08 — 4,17×; 01–04.09 — 46 позиций, **5,10×** (по дням 5,15 / 5,10 / 5,03 — не выброс).
Пол теперь соблюдён, доля потолка 65 % → 88 %, глубина скидки не изменилась (47,0 → 48,0 %),
значит подъём дошёл до покупателя: 2,31× → 2,65×. Штуки держатся (11,5 против 12,1 в день),
деньги покупателя +34 %. Ожидаемая маржа при неизменном g ≈ 12,7 % против 3,1 % факта августа.

**Предложено Сергею (не внедрено, решение за ним):**
1. Минимальную прибыль сделать не плоской: **`min(300 ₽; 8 % от цены продажи)`** — именно `min`,
   т.к. на дешёвом товаре 300 ₽ не порог, а запрет. Чинит интервалы, где акция невозможна
   в принципе (пол выше потолка): Ozon 2 → 0, ВБ 1 → 0, ЯМ 7 → 4. Почему 8, а не 10: при 10 %
   коридор в интервале 301–400 ₽ проваливается до 7 % (уже, чем у соседей), при 8 % кривая
   монотонная — 36/30/24/21/15/13 % и дальше без стыка переходит в нынешний режим 9–11 %,
   потому что с 501 ₽ закупки порог всё равно упирается в 300 ₽. Скрипт — `scratchpad/rule.py`.
2. Потолок ЯМ в четырёх верхних интервалах (от 10 001 ₽) поднять до ~5,1–5,2×: сейчас
   4,11–4,37× против пола 4,57–4,64×, коридора нет вовсе. Маржа по потолку выйдет ~13 %.
3. Порядок: до 15.09 ничего не трогать (одну переменную поменяли 31.08, нужен чистый замер),
   затем по одной — сначала правило минимальной прибыли, потом потолок дорогих интервалов.
