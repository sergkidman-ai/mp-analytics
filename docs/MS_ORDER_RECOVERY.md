# Обработка заказов МС при сбое вебхуков

Поток: inv. Основание: согласованные поручения Натальи и проверенные прогоны 22.10.2026.
Канонические правила: `/opt/mp-knowledge/memory/ms-order-outage-fulfillment.md`.

## Состояние на 22.10.2026

Работа МС восстановлена, заказы обрабатываются штатно без нашего вмешательства.
Ручной обработчик не запущен и не добавлен в cron/systemd. Следующий запуск — при новом
сбое по команде пользователя. Старые разрешения и зафиксированные ID не являются новым заданием.

## Согласованное поведение

1. Получить свежие заказы в согласованном статусе. 22.10 фактическое название —
   «Ожидает подтверждения»; пользователь называла его также «Ожидает обработки».
   Проверять metadata, не подменять фильтр на все активные заказы.
2. Склад из заказа не менять. Проверять физический остаток всех позиций именно на нём;
   приход в пути не считать наличием. Собственный резерв можно использовать, чужой — нельзя.
   Для каждой позиции нужны и `stock >= quantity`, и
   `stock - reserve + min(own_reserve, quantity) >= quantity`.
   Общий остаток не обещать нескольким заказам: единый пул либо последовательное резервирование.
3. Если исходный товар доступен — сохранить его. Если нет — выбрать товар другого
   поставщика с тем же точным `externalCode`, включая ведущие нули. Поле `code` обозначает
   карточку поставщика, не нашу номенклатуру. Другой внешний код без подтверждённого соответствия
   не является разрешённой заменой. Брак и архивные товары не использовать.
4. Наборы определять по свежему справочнику ТК `catalog/mix_data`, рекурсивно раскладывать
   по внешним кодам и количествам. Приоритет: весь набор от одного поставщика и одного бренда;
   затем один бренд у разных поставщиков; затем доступные компоненты разных брендов/поставщиков.
   Неизвестный состав, неподтверждённый бренд или неполный остаток не додумывать.
5. Не проводить частичную отгрузку. Сохранять организацию, контрагента, склад, полную сумму,
   скидки и НДС. Цены компонентов распределять с проверкой округления до копейки.
6. Готовому заказу поставить «Собирается» и плановую дату отгрузки на текущий день МСК.
   Через **не менее 5 минут** проверить связанные отгрузки. Существующую корректную не дублировать.
7. Если отгрузки нет — ещё раз проверить актуальные товары, остатки, состояние и связи;
   получить шаблон из заказа. Номер отгрузки = номер заказа, момент = текущее время МСК.
   Остальные поля брать из связанного заказа. Проверить проведение и связь свежим GET.
8. При нехватке товара оставить заказ без изменений и записать первый блокирующий код.
   Параллельные изменения, несколько/частичные отгрузки, неизвестные форматы — отдельный разбор.

## Быстрый повторный запуск

Уже есть рабочая заготовка `tools/customer_order_fresh_fulfillment_20261022.py`.
Название историческое, но новые волны получают сегодняшнюю дату МСК через `wave_config.json`.
Всегда новый каталог. **Эти команды описывают будущую процедуру, сейчас их не запускать.**

```bash
# 1. Только чтение МС/ТК; каталог задать уникальный для нового сбоя.
./venv/bin/python -m tools.customer_order_fresh_fulfillment_20261022 collect /opt/mp-analytics/docs/reports/ms_order_recovery_NEW_WAVE

# 2. После проверки состава волны и действующего поручения: резервирование,
#    при необходимости замена/разбор, статус и плановая дата. Это запись в МС.
./venv/bin/python -m tools.customer_order_fresh_fulfillment_20261022 apply /opt/mp-analytics/docs/reports/ms_order_recovery_NEW_WAVE

# 3. Не раньше shipment_check_not_before из status_result.json:
#    проверка связанных документов, создание только отсутствующих. Это запись в МС.
./venv/bin/python -m tools.customer_order_fresh_fulfillment_20261022 shipments /opt/mp-analytics/docs/reports/ms_order_recovery_NEW_WAVE
```

`collect` сохраняет metadata, исходные заказы, ответы ТК и карточки поставщиков.
`apply` заново проверяет остатки каждого заказа, резервирует выбранное количество,
сохраняет before/plan/payload intent/response/readback. `shipments` проверяет дедлайн и связи.
Если готовых заказов нет — не ждать 5 минут и не создавать отгрузки.

Перед записью разобрать ошибки ТК и смену состава. Перезапускать незавершённую волну
вслепую нельзя: наличие `*_intent.json` означает, что попытка уже была, сначала GET-сверка.
После POST-таймаута искать созданную отгрузку, повторный POST не отправлять автоматически.

## Границы готового инструмента

- Это аварийная ручная заготовка, не постоянно работающий сервис. Нет фонового расписания.
- Одна волна `apply` ограничена **24 заказами**: с отгрузками это менее 50 изменяемых сущностей.
  Для большего объёма сначала `.claude/skills/ms-mass-change/SKILL.md`, затем новая разбивка.
- Проверенные наборы были количеством 1; при большем количестве родителя стоит assert.
- Поддерживаются товарные позиции без упаковок, состав ТК без неизвестного поля количества.
- Сохранённый `status_result.json` запрещает повторить законченный apply; `*_intent.json`
  запрещает повторить ту же запись. Прерванный прогон требует сверки отдельных документов.
- Старые скрипты `batch17`, `new_wave`, `remaining_bundles`, `bundle_shipments` привязаны
  к конкретным ID/датам 22.10.2026. Их прямой повторный запуск не нужен.
- Финальный аудит: состав/количества/цены/скидки/НДС/сумма/склад/организация/контрагент,
  «Собирается», плановая дата, ровно одна корректная проведённая отгрузка и обратная связь.

## Проверенные API и защита от дублей

- Остатки: `GET /report/stock/all`, фильтры `store`, `product`, `stockMode=all`.
  Фильтр `assortment` здесь не подходит. Отсутствующая строка не подтверждает наличие.
- `PUT /entity/demand/new` с `customerOrder.meta` возвращает шаблон, не создаёт документ.
  Реальное создание — один `POST /entity/demand`.
- Сверять `customerOrder.demands` и номер отгрузки **в рамках организации**. Номер чужого
  заказа или несколько документов — остановка создания, а не ещё одна отгрузка.
- МС возвращает даты с `.000`; сравнивать нормализованное время, а не строку без миллисекунд.
- Не использовать автоматически повторяющий мутации HTTP-клиент для PUT/POST сущностей.
  Общий GET-клиент допускает ограниченные повторения чтения, шаблон `/new` не создаёт сущность.
