## Поведение и источники

ACK после транзакции inbox+все события; requestId/accountId — постоянный ключ дедупликации.
UUID/account/type/action/href проверяются; входящий URL не используется для HTTP GET.
При сбое сохранения 503, без внешних API в receiver. При недоступной БД ошибки фиксируются
без URL/секретов в journald; метрика ошибки сохраняется после ответа, когда БД доступна.
Транспорт отделён функцией store.accept с original requestId/accountId/event_at/metadata:
будущий накопитель может передавать те же события и ключи, без новой очереди.

Debounce 15 с, поколение на документ, lease 10 минут с продлением при чтениях/ожидании.
Старый lease/generation не публикует результат поверх нового задания. Читается текущий
документ даже для DELETE, поэтому поздний DELETE живого документа не снимает сигнал.
Только реальный 404 закрывает сигнал; 403/429/сеть — ошибки источников. Одинаковый
fingerprint не плодит историю/сигналы. Исправление обновляет текущий результат, история остаётся.

Один worker: session advisory lock, один одновременный запрос МС, интервал >=1 с,
снижение скорости при Remaining<10, Retry-After/429 с общей паузой. Последняя пауза
сохраняется в БД и учитывается после рестарта. Это потолок нового сервиса, а не общий
лимит остальных collectors/аккаунта. Адаптеры тоже последовательны: WB >=6 с, Ozon/Маркет >=1 с.

FIFO: byoperation.cost /100 уже для всего количества. quantity отчёта не используется.
Количество/скидки/НДС из demand positions. Повторные ms_id объединяются; стоимость по
неоднозначным строкам с разной ценой не выдумывается. Нулевой/неполный FIFO и отрицательная
товарная quantity видны как ошибки. Короткие технические повторы — максимум 3 попытки;
403/неоднозначный мост сразу видны как error. Цена МС и подтверждённая цена сохраняются отдельно.

Маркет: exact order_id, raw stats Σ prices.total BUYER+CASHBACK+MARKETPLACE;
при отсутствии сырья узкий business orders по orderIds. Ozon: точные реальные posting
или сохранённые дочерние posting, products.price×qty; на 106 реальных позициях проверено
совпадение с financial_data.products.price. WB: assembly_id → строка продажи отчёта
retail_price_withdisc_rub до СПП, иначе marketplace orders.price/100 (или подтверждённый convertedPrice/100 при convertedCurrencyCode=643).
Для частичной отгрузки заказ используется только по точному SKU и проверенной цене единицы;
разные цены частичного SKU, неоднозначные мосты и несовпадение количества — видимая ошибка.

Пол: (FIFO + max(300 руб. × проданные единицы SKU/набора, 10% FIFO)) / (1 − доля удержаний),
то есть существующая абсолютная цель промо-сторожей на проданную единицу, не 25% маржи.
Для набора проданная единица — набор; его составляющие не увеличивают цель 300 руб.
Снимки WB/Ozon — полный август 2026 отдельно по кабинетам; источник/хэш/срок 60 дней
сохранены в ms_shipment_rules. Маркет — проверенная полная база сентября 0.6700368042873839
из checks.json, а не 69.53495% старой витрины. Старые витрины и их сторожей не меняли.
Новый пол после истечения срока не применяется: «правило не настроено». Для прямых
продаж/неизвестного юрлица нет придуманной комиссии, сравнение реальной цены/FIFO сохраняется.

Сверка каждые 30 минут, первый checkpoint — 24 часа до установки (238 документов в preflight),
перекрытие 5 минут, верхняя граница now−30 с, dates МС Europe/Moscow. Страницы по 20,
order=updated,asc;id,asc проверен живым API. Между страницами обслуживается очередь.
Checkpoint продвигается после двух одинаковых полных проходов фиксированного окна:
защита от сдвига offset при изменениях. Максимум три прохода, иначе checkpoint сохранён.
Это увеличивает фактические чтения сверки; не выдавать 2–3 чтения расчёта за полную нагрузку.
Отсутствующий CREATE существующего demand восстановлен первичной сверкой.

Удаления: по одному ранее отслеживаемому live ID каждые 30 с, если давно не проверен (24 ч),
через тот же limiter. FIFO недавних 7 дней: максимум 20 старейших проверок каждые 30 минут,
не чаще 4 ч на документ. При большой истории полный обход ID занимает дольше суток;
возраст очереди и последние успешные сверки видны. Полностью пропущенный быстро созданный
и удалённый документ без известного ID не восстанавливается. Изменение старой приёмки
за пределами окна не гарантирует автоматический пересчёт далёких отгрузок.

Хранение: ежедневно очищается только payload inbox старше 90 дней, если связанные jobs done.
Ключи дедупликации/метаданные/счётчики дублей хранятся постоянно. pending/retry/error не удаляются.
Jobs, assessments и их raw сохраняются без автоматического удаления в первой версии;
завершённые jobs не удаляются, поскольку нужны для проверки пропущенного DELETE.

## Доработка по справочнику наборов ТК, 08.10.2026

Прямое поручение пользователя: использовать справочник «внешний код набора → внешние коды
состава» из ТК. Подключён set_cost.components (993 записи); cost/buyPrice/covered этой таблицы
не участвуют в FIFO или экономике. Повторения кода компонента учитываются как реальные
количества. Вложенный состав раскрывается по справочнику с проверкой циклов/глубины.

Для производных артикулов применяется существующее правило проекта кода семейства
(wb_promo_guard._base_code): точный код ТК имеет приоритет, иначе первые 4 знака при наличии
этого кода в ТК. Ведущие нули сохраняются. Явные X/Х-кратности этим правилом не раскрываются:
по суффиксу количество не угадывается. Реальные количества сверяются со всем составом
набора из ТК. Код площадки/код ТК/источник/дата/хэш сохранены в результате проверки.

При отсутствии локальной записи выполняется узкое чтение ТК mix_data; положительный,
not_mix и ответ отсутствующего кода сохраняются в собственной ms_shipment_bom на сутки,
с исходным ответом, временем и хэшем. Никаких записей в чужой set_cost/prc_tc_model.
Чтения ТК последовательны >=1 с, HTTP429 обрабатывается общей паузой этого адаптера.
Предел — 20 различных кодов заказа на расчёт. Применена собственная миграция 072.

Проверка и пол вычисляются по ПРОДАННОМУ SKU/набору: его полная цена и сумма реального
byoperation FIFO его составляющих. Физические количества компонентов сохраняются отдельно.
Цена набора по компонентам не распределяется; FIFO не умножается повторно на количество.
Разные наборы с общим компонентом образуют проверяемую группу: цена/FIFO по группе доступны,
но неизвестный FIFO отдельных наборов и пол не выдумываются, остаётся отдельная видимая ошибка.
Таким образом убыточный отдельный набор не скрывается за положительным итогом документа;
непроверяемые уровни помечаются явно.
