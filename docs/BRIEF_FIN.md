### Нагрузка на МойСклад (аудит 2026-08-05)

Проверено по просьбе Сергея: не молотит ли раздел МС лишними запросами.

Нашлась утечка, общая для WB и Ozon: `MDC.byoperation_cogs()` результат никуда не пишет, поэтому

прогоном, берётся из своей же таблицы, в МС не идём. FIFO состоявшейся отгрузки не меняется, так
что пересчитывать нечего; принудительный пересчёт — кнопка «пересчитать» в детализации (1 отгрузка
= 1 запрос) либо разморозка месяца.

Контроль: прогон после фикса — цифры бит-в-бит те же (acc1 10166 строк / 7 036 908.45 ₽ себеста,
acc2 5912 / 5 835 401.46 ₽), «из кэша без запроса в МС» 1340 + 896.

Что осталось в МС за прогон: 4 `_resolve_href` + ~17 страниц `/entity/demand` (по 1000) ≈ **21
запрос**, ~2m40s (упирается в скорость выдачи МС, не в лимит). Закрытые месяцы не листаются и не
переписываются, ручной себест не затирается. В cron/`run_daily` коллекторы себеста (ya/oz/wb) НЕ
стоят — фоновой нагрузки нет вовсе, запуск только руками. Теперь прогон достаточно дёшев, чтобы
поставить его в расписание, — решение за Сергеем.

## Себестоимость в «Отчётах МП» = только реализованный товар (2026-08-13, ветка `fin/cogs-realized`)

**Решение Сергея.** В отчётах МП строка «Себестоимость» считает себест ТОЛЬКО того товара, по
которому маркетплейс начислил выручку в этом же отчёте. Критерий — **факт начисления выручки в
отчёте**, а НЕ статус отгрузки и НЕ склад возврата. Гейты «Брак» / склад «Озон» к этой строке
отношения не имеют: они живут в разделе «Себестоимость», где брак остаётся убытком.
МП сторнировал выручку → сторнируем себест. Потерь от брака в отчётах МП быть не должно.

**Что нашли (замеры янв–июл 2026, зонды в scratchpad сессии):**

- Недосторнированный себест при старой логике (гейт `sell_budget`/склад):
  WB acc1 79 662 ₽, acc2 50 592 ₽, Ozon acc1 374 611 ₽, acc2 104 385 ₽ — **итого 609 252 ₽**
  (сторнируется лишь 35 % положенного). Маркет — отдельно ≈98,8 тыс. ₽ за один июль.
- «Товарные» возвраты Озона без денежного сторно — **артефакт помесячной нарезки**: из 172 таких
  отправлений (acc1, продажа в отчётах есть) у 164 денежное сторно ЕСТЬ, у 30 — в более раннем
  месяце. Вывод: триггер сторно = ТОЛЬКО денежная операция (`accruals_for_sale < 0`), товарная
  (`OperationReturnGoodsFBSofRMS`) как триггер не нужна, дублирует. Сторно ложится в месяц
  денежного сторно. 8 отправлений без денег нигде — себест остаётся в COGS (выручку не вернули).
- **Рассинхрон `status='done'` ↔ выручка (фев–июл):** WB 0; **Ozon acc1 204 отгрузки / 404 662 ₽,
  acc2 61 / 74 950 ₽** (2,9 % и 2,5 % себеста без единого рубля выручки); Яндекс 5 CANCELLED +
  2 PICKUP / 8 624 ₽. Поэтому берём выручку отчёта, а не статус.
- Витрина Яндекса фев–июл: cogs 2 850 024 ₽ против 2 426 617 ₽ по отгрузкам с выручкой → −423 407 ₽.

**Схема (согласована):**

1. Себест отчёта = `Σ cogs` отгрузок из `wb_/oz_/ya_cogs_demand`, у которых в ЭТОМ отчёте есть
   начисление выручки, **+ FBO-импутация** (только WB: FBO ~11–12,5 % оборота, документа
   «Отгрузка» в МС не создаёт). Разрыв 11–12,5 % во всех месяцах — это ровно FBO, не возвраты.
2. Сторно — по строкам возврата САМОГО отчёта (WB `supplier_oper_name='Возврат'`,
   Ozon `accruals_for_sale < 0`), без гейта склада и без требования документа `salesreturn` в МС.
3. Клик по строке «Себестоимость» → таблица отгрузок отчёта (отгрузка / дата / штуки / наша цена /
   себест / метод / статус, фильтр по статусу) — тем же рендером, что `/reports/cost`
   (`reports/mp_cogs_page.py`), но выборка по месяцу ОТЧЁТА, а не по месяцу отгрузки.
4. Возвраты без моста к себесту отгрузки (187 шт) — фолбэк «себест/шт по истории SKU» (ОК Сергея).

**Мосты `demand_name` (проверены):** WB = `assembly_id` строк финотчёта; Ozon = постинг, первые
