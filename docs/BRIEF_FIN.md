## Себестоимость в «Отчётах МП» = только реализованный товар (2026-08-13, ветка `fin/cogs-realized`)

**Решение Сергея.** В отчётах МП строка «Себестоимость» считает себест ТОЛЬКО того товара, по
которому маркетплейс начислил выручку в этом же отчёте. Критерий — **факт начисления выручки в
отчёте**, а НЕ статус отгрузки и НЕ склад возврата. Гейты «Брак» / склад «Озон» к этой строке
отношения не имеют: они живут в разделе «Себестоимость», где брак остаётся убытком.
МП сторнировал выручку → сторнируем себест. Потерь от брака в отчётах МП быть не должно.

**Что нашли (замеры янв–июл 2026, зонды в scratchpad сессии):**

- Недосторнированный себест при старой логике (гейт `sell_budget`/склад):
  WB acc1 79 662 ₽, acc2 50 592 ₽, Ozon acc1 374 611 ₽, acc2 104 385 ₽ — **итого 609 252 ₽**
  (сторнируется лишь 35 % положенного). Маркет — отдельно ≈98,8 тыс. ₽ за один июль.
- «Товарные» возвраты Озона без денежного сторно — **артефакт помесячной нарезки**: из 172 таких
  отправлений (acc1, продажа в отчётах есть) у 164 денежное сторно ЕСТЬ, у 30 — в более раннем
  месяце. Вывод: триггер сторно = ТОЛЬКО денежная операция (`accruals_for_sale < 0`), товарная
  (`OperationReturnGoodsFBSofRMS`) как триггер не нужна, дублирует. Сторно ложится в месяц
  денежного сторно. 8 отправлений без денег нигде — себест остаётся в COGS (выручку не вернули).
- **Рассинхрон `status='done'` ↔ выручка (фев–июл):** WB 0; **Ozon acc1 204 отгрузки / 404 662 ₽,
  acc2 61 / 74 950 ₽** (2,9 % и 2,5 % себеста без единого рубля выручки); Яндекс 5 CANCELLED +
  2 PICKUP / 8 624 ₽. Поэтому берём выручку отчёта, а не статус.
- Витрина Яндекса фев–июл: cogs 2 850 024 ₽ против 2 426 617 ₽ по отгрузкам с выручкой → −423 407 ₽.

**Схема (согласована):**

1. Себест отчёта = `Σ cogs` отгрузок из `wb_/oz_/ya_cogs_demand`, у которых в ЭТОМ отчёте есть
   начисление выручки, **+ FBO-импутация** (только WB: FBO ~11–12,5 % оборота, документа
   «Отгрузка» в МС не создаёт). Разрыв 11–12,5 % во всех месяцах — это ровно FBO, не возвраты.
2. Сторно — по строкам возврата САМОГО отчёта (WB `supplier_oper_name='Возврат'`,
   Ozon `accruals_for_sale < 0`), без гейта склада и без требования документа `salesreturn` в МС.
3. Клик по строке «Себестоимость» → таблица отгрузок отчёта (отгрузка / дата / штуки / наша цена /
   себест / метод / статус, фильтр по статусу) — тем же рендером, что `/reports/cost`
   (`reports/mp_cogs_page.py`), но выборка по месяцу ОТЧЁТА, а не по месяцу отгрузки.
4. Возвраты без моста к себесту отгрузки (187 шт) — фолбэк «себест/шт по истории SKU» (ОК Сергея).

**Мосты `demand_name` (проверены):** WB = `assembly_id` строк финотчёта; Ozon = постинг, первые
2 сегмента (`48742608-0134-2` → `48742608-0134`); Яндекс = `orderId` (НЕ `id`).

**Долить до внедрения:** `*_cogs_demand` декабрём-2025 (иначе январский отчёт WB недосчитает 520
отгрузок: acc1 284, acc2 236); `raw_yandex_order` за янв–май (сейчас с мая, до этого мост пуст).

**`other`/`unreported` — статус НЕ врёт:** из 341 залипшей отгрузки WB ни одна не имеет строки
«Продажа» в финотчёте, новое правило отсекает их само. Нужен не фикс статуса, а **флаг по
возрасту**: 85 отгрузок acc1 (82 481 ₽) и 60 acc2 (70 238 ₽) старше нормального лага 7 недель.

**Следующий шаг:** правка `reports/margin_by_sku.py`, `reports/margin_ozon_sku.py`,

## Себест Маркета переведён на FIFO (`7481a72`, 2026-08-13)

«Себестоимость» Маркета (`_ms_cogs_monthly`) брал Σ `products.cost_seb` × qty по позициям
МС-ЗАКАЗА — то есть среднюю себестоимость текущего остатка из карточки, а не стоимость
конкретного списания. Теперь читаем раздел «Себестоимость» (`ya_cogs_demand`, метод `ms_fifo`),
в расход идёт только `status='done'`. Месяц — по дате ЗАКАЗА (мост `demand_name` = `stats/orders.id`),
потому что по ней же нарезана выручка в `_fold_order`; нарезка по месяцу отгрузки роняла покрытие
до 69–115 %. `run_daily`: шаг `collectors.ya_cogs_demand` переставлен ПЕРЕД помесячной сборкой.

**Дельта COGS янв–авг 2026: −210 182 ₽** (чистая на столько выше). Покрытие drill-down 87–100 %,
`cogs_cov_pct` 100 %. Витрина пересчитана, 2026-01..07 переморожены, статика перерисована.
`_cost_map()`/`yandex_cost` (цепочка на `cost_seb`) остались в файле как аварийный фолбэк

- `reports/fifo_fallback.py` — общий модуль. `unit(article, day)` (себест/шт по артикулу площадки:

## Связи универсальных моделей в цепочке FIFO (`analog_fifo`, 2026-08-14)

Задача Сергея: один картридж продаётся под разными кодами (Q2612A = Canon 703). Покупатель заказал
5335, со склада ушёл 0002 — в приёмках/отгрузках МС кода 5335 нет, 0002 есть. Соседняя сессия
(поток **prc**, миграция 408) залила связи в `prc_tc_link` из каталога TheCartridge.

**Сделано** — в `reports/fifo_fallback.py` добавлен шаг **`analog_fifo`**:
`unit()`: товар → набор → аналог; `impute()`: позиция без своего FIFO ищется по связям (метод
документа тогда `analog_fifo`, правило полного покрытия сохранено); компоненты набора тоже добирают
FIFO по связям. Связи читаются **в обе стороны** (взаимозаменяемость симметрична); из нескольких
связанных кодов с FIFO берём **максимальный** себест — где не знаем точно, ошибаемся в сторону
расхода. Без миграции 408 модуль работает как раньше (проверка `to_regclass`). `prc_tc_link` —
чужая территория, только read-only. Ярлыки методов добавлены в три страницы себестоимости
(заодно закрыт пробел: `nabor_fifo` нигде не был подписан). CHECK-констрейнтов на `method` нет.

**Эффект в деньгах = 0 ₽, и это правильный результат.** Честный A/B (июль, пересборка подряд без
связей и со связями, 4 аккаунта): дельта ровно 0. Причина: в цепочке витрины первым стоит
`cpu_hist` — себест/шт по истории того же nm из НАШИХ отгрузок, и он перекрывает 140 из 141 позиции,
где связи вообще могли бы сработать (это тоже факт FIFO и он точнее аналога). Моя первая оценка
«219 шт ≈ 104 тыс ₽» мерила шаг `ff.unit` в изоляции, без учёта более раннего шага цепочки —
цифра неверна. Шаг остаётся страховкой: он сработает на новом SKU, проданном по FBO раньше, чем
у нас появилась своя отгрузка.

Дельта первого прогона (−87,7 тыс ₽ по 2026) — **дрейф данных** (июль/август добираются ночным
`run_daily`), не связи: A/B на одних данных дал 0. Статика вкладок сверена с витриной по всем
