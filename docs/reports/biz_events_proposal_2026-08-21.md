# Дневник управленческих событий + сторож изменений МП + сторож остатков поставщика

Черновик спецификации от 21.08.2026. Источник — три записки Натальи в бот Dropbox
(`dropbox/20260821_051933`, `_051937`, `_073128`). Статус: **дизайн согласован 21.08, код не писался.**

## 0. Зачем и почему это одна задача, а не три

Все три записки — про одно: **отчёты Пульта показывают ЧТО произошло, но не показывают ПОЧЕМУ.**
Провал выручки на Дисквэре 21.08 читается как «просадка», хотя 20.08 мы сами отключили Звёздные
товары. Рост ДРР читается как «реклама подорожала», хотя МП поднял комиссию. Пропажа продаж по
карточке читается как «упали позиции», хотя у поставщика кончился товар.

Значит нужен один слой — **лента событий, наложенная на цифры**. Разница только в источнике
события: наше решение (дневник), решение площадки (новости/тарифы), состояние поставщика (остатки).

## 0.1 Решения Натальи от 21.08.2026

1. **Ввод событий** — бот основной + форма на дашборде для правки и списков SKU.
2. **Новости МП** — WB по API. Ozon и Маркет — **через почтовые рассылки площадок**
   (проверено 21.08: письма уже приходят и приходят ЗАРАНЕЕ). Telegram-каналы — запасной вариант.
   Мониторинг «по факту изменения тарифа» Наталья отклонила: нужна новость заранее.
3. **Остатки поставщика** — следим за КОНКРЕТНЫМ кодом поставщика (`3804at`), у него один
   остаток. Не за суммой по всем поставщикам карточки.
4. **Объём слежки — только 4 кода из записки.** Следить за всеми остатками НЕ нужно: это
   огромный поток данных. Но просьбы такого рода будут повторяться, поэтому делаем через
   подписку (добавить код = строка в таблице), а не через список в коде.
5. **Первый шаг работ** — дневник + сторож этих 4 остатков.

## 1. Дневник событий

### Хранение — таблица `biz_events`

| поле | смысл |
|---|---|
| `id` | PK |
| `event_date` | дата события (обязательна) |
| `date_to` | конец периода, NULL для точечного события |
| `kind` | `own` — наше решение / `mp` — решение площадки / `supply` — поставщик |
| `platform`, `account` | площадка/аккаунт; NULL = весь бизнес |
| `scope_kind`, `scope_ref` | что затронуто: `all` / `sku_list` / `category` / `warehouse` |
| `title`, `details` | заголовок + текст |
| `expect` | чего ждём (гипотеза, свободный текст) |
| `review_at` | когда вернуться и померить эффект |
| `author`, `source` | кто завёл; `tg` / `web` / `auto_news` / `auto_tariff` |
| `created_at` | служебное |

Реальные события из записки для первичного заполнения:
- 20.08 — отключены «Звёздные товары», Ozon / Дисквэр (`own`, есть готовый расчёт: память `ozon-stars-program-verdict`)
- ~20.08 — переход на выплаты раз в 2 недели, Ozon / Цифровой + Дисквэр (`own`, влияет на кассу, не на маржу)
- 18.08 (вт) — запуск бандлов, Яндекс / Цифровой (`own`)
- начало августа — запуск бандлов, Ozon / Цифровой (`own`)

### Ввод — бот основной + форма (решено 21.08)

1. **Бот (основной).** Наталья уже пишет события естественным текстом. Разбор строки
   («20.08 отключили Звёздные товары на Дисквер Озон») в черновик события + кнопка «подтвердить».
   Никакой формы заполнять не надо — это и есть причина, почему бот главный канал.
2. **Форма на дашборде** — для правки и для событий со списком SKU.
3. **Авто** — из сторожей (разделы 2 и 3), с пометкой `source=auto_*`.

### Показ

1. **Главная, блок «🗓 Что мы меняли»** — 5 последних событий + те, у кого подошёл `review_at`
   («пора померить эффект»). Ставится между «Динамика по неделям» и «По площадкам».
2. **Маркеры прямо в цифрах** — 📌 у недели в таблице динамики и у точки на графике, тултип с
   заголовком события. Это и есть «читать отчёты с учётом событий».
3. **Вкладка «Дневник»** — полный список, фильтры по площадке/типу/периоду.

### Замер эффекта

Кнопка «эффект» у события: окно N дней до / N после `event_date` по метрикам выручка, заказы,
чистая прибыль, ДРР, показы — в границах `scope` события.

Обязательные предохранители (иначе получим красивую ложь):
- **Сравнивать одинаковыми днями недели** — у картриджей выходные проваливаются (память `weekday-comparability`).
- **Не мерить по неполному текущему месяцу на уровне SKU** — тонкий хвост даёт шум (память `incomplete-month-sku-trap`).
- **Показывать пересечение окон**: 4 события за 3 недели, окна наложены → это НАБЛЮДЕНИЕ, а не
  эксперимент. Подписывать «контекст», не «эффект X дал Y ₽». В проекте уже есть культура
  наблюдательных исследований — `docs/experiments/ozon_observational_studies.json`.

**Контур А — числовой сторож тарифов (главный, работает на всех трёх площадках).**

## 3. Сторож остатков поставщика

### Ключ слежки — поле «Код» в МойСкладе (уточнено 21.08)

Первоначальное прочтение было неверным: `3804at` — это НЕ наша карточка, а **код товара
конкретного поставщика**. Раскладка полей МС:

| поле МС | значение | что это |
|---|---|---|
| `code` | `3804at` | **код товара поставщика — за ним и следим** |
| `article` | `AT-F6T79AE Y` | артикул поставщика |
| `external_code` | `3804` | наша родительская карточка |

Поэтому связь строго `ms_product.code → ms_id → supplier_stock.ms_id`. Джойн по `external_code`
даёт 9–11 строк разных поставщиков и для этой задачи НЕ подходит.

### Факт на 21.08.2026, склад «Удаленный склад», поставщик ООО «ОДИССЕЙ» WB

| код | артикул | остаток |
|---|---|---|
| 3801at | AT-L0R95AE Bk (913A чёрный) | 23 (было 8 с 11.08, довезли 20.08) |
| 3802at | AT-F6T77AE C (913A голубой) | 9 (+1 на складе «Звездный») |
| 3803at | AT-F6T78AE M (913A пурпурный) | 14 |
| 3804at | AT-F6T79AE Y (913A жёлтый) | 14 |

Снимки ежедневные, история есть — сторож работает на готовых данных, ходить в API МС не нужно.

### Порог

`sold_30d` у этих строк **пустой**, поэтому порог «на сколько дней хватит» здесь не посчитать.
Принимаю простое и понятное правило (поправишь числом, если не то):

- **предупреждение** — остаток упал до **5 шт и ниже**;
- **алерт** — остаток **0**;
- порог хранится в подписке и задаётся на каждый код отдельно.

### Подписка вместо хардкода (подтверждено 21.08)

Таблица `prc_stock_watch`: `ms_code`, `store` (по умолчанию «Удаленный склад»), `threshold`,
`chat_id`, `active`. Команда в боте PRC: `/watch 3804at 5`, `/unwatch 3804at`, `/watchlist`.
Наталья подтвердила: сейчас следим ТОЛЬКО за этими 4 кодами, за всеми остатками следить не надо —
это огромный поток данных. Но такие просьбы будут повторяться, поэтому подписка, а не список в коде.

**Антидребезг:** одно уведомление на переход «ушёл ниже порога»; повторно — только после того,
как остаток поднялся выше порога. Механика уже отработана в `ops/tc_price_alert.py` (журнал в БД).

**Канал:** бот PRC (`TG_PRC_BOT_TOKEN` / `TG_PRC_NOTIFY_ID`), как и просили.

**Связь с дневником:** срабатывание пишется строкой `kind=supply` — тогда провал продаж по
карточке 913A будет объяснён прямо в отчёте, а не останется загадкой.

## 4. Потоки и границы

- **Новый поток `ev`** — дневник + сторож новостей/тарифов: таблицы `biz_events`, `mp_news`,
  `mp_tariff_snapshot`; вкладка «Дневник»; блок на главной. Миграции — новый диапазон (напр. 5xx).
- **Поток `prc`** — сторож остатков (`prc_stock_watch`), там уже живёт сторож прайсов и бот PRC.
- Чужого не трогаем: `margin_by_sku` только читаем; блок на главной — минимальная вставка в
  `web/static/home.html` + отдельный роутер, чтобы не лезть в тело `web/app.py` (4357 строк).

## 5. Порядок работ (предложение)

1. `biz_events` + ввод через бот + вкладка «Дневник» + 4 события из записки. **Даёт пользу сразу.**
2. Блок на главной и 📌-маркеры в недельной динамике.
3. Сторож остатков поставщика (быстро — данные уже в БД).
4. Числовой сторож тарифов WB/Ozon/Яндекс.
5. Новости WB в дневник + алерты по важному.
6. Письма Маркета и Ozon в дневник (транспорт уже есть; по Ozon нужен правильный адрес).
7. Кнопка «эффект» с предохранителями по дням недели и пересечению окон.
