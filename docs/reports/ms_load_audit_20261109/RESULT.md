# Нагрузка на МойСклад — аудит 09.11.2026

## Вывод

Подтверждён отказ по числу одновременных запросов, а не только по частоте.
09.11 в05:01:45UTC /08:01:45МСК fbs-ms-import.service получил HTTP429/code1073:
«Превышено ограничение на одновременное количество запросов». Traceback указывает
на _purchase_positions_snapshot → GET /entity/enter/<id>/positions, pool=3.
Одновременно работал customer-order-guard; после отказа стартовал confirmed-dispatch.
Полный состав конкурирующих запросов не виден: скрытые ретраи не журналируются,
другие интеграции, включая ТК, могут использовать тот же пользовательский бюджет.
Один найденный финальный429 не означает, что ограничений был только один случай.

Клиенты core.ms_api, invoice_bot.ms, collectors.moysklad, shipment_guard.ms и прямые
requests-клиенты не имеют общей координации. Локальные паузы отдельных процессов
не ограничивают сумму параллельных запросов. core.ms_api повторяет429 с паузами
1/2/4сек без чтения заголовков Retry; другие клиенты ведут себя иначе.

Документация поставщика: не более5 параллельных запросов от пользователя/решения,
20от аккаунта. Для токена пользователя с01.09.2026 вес обычного запроса3единицы,
то есть15/3сек; с01.12 вес4,11/3сек. stock/all и stock/bystore имеют вес5.
Источник: https://github.com/moysklad/api-remap-1.2-doc/blob/fb6d231b292de82379575e3176dd94347e36cf0c/md/_restrictions.md

## Предлагаемые изменения, по очереди

1. Общий диспетчер запросов по пользователю МС: не более3 одновременных наших
   запросов, фон не более1; заказы/приёмки/отгрузки имеют приоритет. Учитывать
   стоимость запросов и заголовки Retry/Reset, распространять backoff на все
   участвующие процессы. Включить все клиенты и прямые requests-вызовы, в том числе
   работающий из immutable runtime customer guard. Правка одного core.ms_api
   не охватит остальные клиенты и другие копии приложения. Нужны безопасные
   счётчики method/resource/status/duration/process/class без query/auth/payload.
   Не добавлять слепые повторы POST при неопределённом результате записи.
2. Общий версионный кэш полных позиций оприходований: ключ(id,updated), подтверждение
   полноты и сверка версии до/после первичного чтения. Заголовок документа читать
   свежим; при новой версии/замене прайса перечитать только новый документ.
   Ни ошибки/404, ни неполные страницы не считать достоверным отсутствием.
   Кэш хранить с источником/версией и использовать как в Пульте, так и в загрузчике.
   Действующий cache self.receipts в Пульте живёт только один проход; это причина
   повторного чтения между проходами.
3. Изменить инвалидирование закупочных прайсов в импортёре. prices_snapshot_all.json
   уже существует, но digest включает все документы: изменение одного сбрасывает
   весь price-map, после чего _purchase_positions_snapshot повторно скачивает
   позиции всех поставщиков. Нужен кэш каждого документа, затем пересборка общего
   map локально. Сохранять два контрольных списка/версии, защиту от замены прайса
   между чтениями и конфликтов цен. Возможность поставщика не ограничивать списком.
4. Группировать чтение метаданных товаров и заказов партиями по20, использовать
   позиции заказа/отгрузки из проверенного expanded-ответа, если они полны; иначе
   читать подресурс. Позиции допустимо переиспользовать только для той же версии
   заказа, с сохранением актуальных проверок перед действием. Существующие batch
   current_orders/demand_batches в отгрузчике переиспользовать, не создавать ещё
   один независимый обработчик. Свежие остатки, резервы и количество читать
   непосредственно для выбора/отгрузки; не заменять ночным снимком.
5. Разовую массовую историю карточек и другие архивные обходы вести одним фоновым
   потоком/в ночном окне с checkpoint. Ежедневные справочники и стабильные настройки
   обновлять пакетом и переиспользовать между процессами. Историю ручных изменений
   состава не отключать: подтверждённые защиты уже кэшируются, отсутствие ручного
   изменения нельзя считать доказанным после ошибки или без свежего аудита.

## Что уже оптимизировано и не нужно отключать

- FBO-traceability: подтверждения кэшируются24ч, поиск имеет бюджет50 попыток и
  общий срок150сек; свежих подтверждений153. Не выглядит первым источником нагрузки
  на фоне26.7тыс запросов/сутки Пульта. Слежение за ФБО сохранять.
- MS market status: metadata статусов уже кэшируется24ч, fast-скан использует
  updated-cursor; эти меры уже есть, их нельзя считать будущей экономией.
- Финансовый сбор FIFO пропускает уже сохранённые demand_id; нельзя выдавать его
  за повторный полный запрос FIFO по каждой отгрузке каждый день.
- Прайс-сторожи проверяют наличие нового прайса и не создают оприходование каждый
  получасовой запуск без нового файла.
- Восстановленные загрузчики ФТС/УПД используют API Ozon/WB и локальную БД;
  октябрь ФТС due0, текущие страницы не генерируют дополнительный поток GET в МС.

## Критерии внедрения

Сначала dispatcher+версионные позиции, затем batching. До записи сравнить старый
и новый расчёт на тех же снимках: позиции/поставщик/количество/НДС/сумма/остаток/
статус/дата и доказательства должны совпасть. Проверить смену версии, приёмку,
ручное изменение состава, замену/удаление оприходования и падение сети. На канарейке
сравнить requests/429/code1073, время обработки новых заказов и возраст очереди.
Экономию не принимать, если она получена увеличением задержки операционных задач.
Сокращение проверок перед резервированием/отгрузкой и историческая подмена FIFO
текущей закупкой не рассматриваются.
