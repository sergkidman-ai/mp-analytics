## Что исправлено

Для customer-order пилота: `docs/reference/ozon_postings_adapter.md`, commit
`513373c405e1f87df2e83eb91cfbcd001f03ccd6`. fetch_postings поддерживает точные UTC timestamps,
`limit=20, max_pages=10, window_budget=120`, optional FBS `statuses` и `sort_dir="DESC"`.
При несовпадении фильтра/сортировки или превышении бюджета — исключение, не partial.
По умолчанию остаются все статусы и legacy-вызовы по датам. Reader не пишет в БД.
Общий `account_lock` доступен из collectors.ozon_postings для point get; списки
берут его автоматически. Namespace Ozon отделён от MS lock 7348201701.


- `collectors/ozon_postings.py`: FBS `/v3/posting/fbs/list` → `/v4/posting/fbs/list`;
  FBO `/v2/posting/fbo/list` → `/v3/posting/fbo/list`. Корневые `postings`, `has_next`,
  `cursor` проверяются явно; старый `offset/result` не используется.
- Сторож отдельно подтвердил `filter.statuses` и `sort_dir="DESC"` (ссылка ниже).
  Финансовый сборщик сохраняет все статусы, без активного фильтра; старый `filter.status`
  и нижний регистр "desc" не использовать. Собираются все статусы
  в неизменном UTC-окне. Каждая дата ответа проверяется относительно точного окна
  00:00:00.000–23:59:59.999. Порядок сортировки для полноты не требуется.
- Курсор передаётся без изменений. Повтор/цикл курсора, дубли posting_number,
  пустая промежуточная страница, сломанная схема, неверные деньги, превышение
  размера/числа страниц дают ошибку. Конечная пустая страница с `has_next=false`
  разрешена; один только непустой cursor не означает продолжение.
- Повторы 429/5xx/timeout/connection error: максимум 5 попыток, 120 секунд на страницу,
  900 секунд на схему/окно, backoff 2/4/8/16 секунд, Retry-After учитывается, в том
  числе HTTP-date. Нулевой Retry-After не создаёт быстрый цикл. Слишком большая
  серверная пауза завершает сбор ошибкой, а не игнорируется.
- Запись в `raw_ozon_posting` — одна транзакция после успешного завершения обеих схем.
  Сбой страницы/FBO не оставляет успешно записанное неполное окно. Существующие
  source gates `run_daily` не менялись: при ошибке постингов маржа не перестраивается.
- `core/ozon_posting.py`: отдельная нормализация Decimal и SQL numeric. Схемы денег
  различаются явно по типу: legacy scalar + currency_code и Money {amount,currency}.
  Для Money валюта обязательна; для исторических scalar этих российских кабинетов
  сохранено прежнее соглашение RUB. Исходные payload не переписываются, миграция БД
  не нужна, история не перезагружается.
- У покупателей бывают **KZT при цене продавца RUB**. Такие Money принимаются в raw
  с валютой; в RUB-расчёт цены покупателя не попадают, не превращаются в 0 и не
  конвертируются выдуманным курсом. Отчёт buyer_price сообщает число исключённых
  строк; API экономики возвращает `buyer_price_excluded_qty`. Средняя цена покупателя
  делится только на количество с известной RUB-ценой.
- FBO v3 может не отдавать quantity в financial_data: количество берётся из products
  **по product_id/sku**, не по позиции массива. Цена за штуку умножается на quantity
  ровно один раз; payout, уже являющийся суммой строки, повторно не умножается.
- `shipment_guard/adapters.py`: чтение старого и нового products.price через общий
  Decimal-парсер; действующий `/v3/posting/fbs/get` сохранён. Сторож не запускался.
- Обновлены SQL-потребители: `reports/ozon_buyer_price.py`, `reports/ozon_margin_control.py`,
  `web/app.py`, `web/marketing_app.py` и 12 инструментов анализа: ozon_acc1_plan,
  ozon_acc1_plan2, ozon_acc2_plan, ozon_account_profile, ozon_bid_plan, ozon_dims_loss,
  ozon_halo_eval, ozon_hypo, ozon_lost_skus, ozon_ramp_effect, ozon_sku_scan,
  ozon_weekly_bids. Это совместимость чтения; сами инструменты не запускались для
  пересчёта данных/применения ставок. В изменённых инструментах убрана привязка
  импорта к общему checkout, чтобы проверки worktree использовали собственный код.
- Веб-расчёт цен соединяет products и financial_data по SKU, а не ordinality;
  промо-отчёт учитывает quantity FBO из products. Реальные SQL проверены на двух
  товарах с переставленными financial_data и количеством 3+2.
- `collectors/ozon.py`: неиспользуемый fetch_transactions теперь явно запрещает
  обращение к отключённому методу. Возвращать из него начисления вместо транзакций
  нельзя из-за разного контракта. Рабочий main уже использует by-day + прежний
  accrual_adapter и не изменён. В `ozon_orders_report` обновлены ссылки в описании.

Сплит выручка/баллы/партнёры остаётся из realization. Классификация начислений,
COGS, компенсации, месяцы сторно и правила витрин не менялись.

## Подтверждённый контракт ответов

| Поле | FBS v4 | FBO v3 |
|---|---|---|
| Контейнер/пагинация | postings + has_next + cursor в корне | Те же корневые поля, проверены отдельно |
| products.price | Money {amount,currency} | Money {amount,currency} |
| financial_data.products.price/old_price/payout | Числа в полученных примерах | Числа в полученном delivered |
| financial_data.products.customer_price | Money, наблюдались RUB и KZT | В непустом примере поля нет |
| financial_data.products.quantity | В примерах присутствует | В примере отсутствует, нужен мост к products |
| financial_data.products.commission | Объект amount/percent/currency | Объект amount/percent/currency |

Читателей старых posting commission_amount/commission_percent в рабочем коде не
найдено; комиссии финансовых витрин идут из отдельного источника начислений.
Отсутствующие необязательные цены/financial_data не выдумываются; отсутствие
обязательного контейнера страницы/продуктов/цены продавца даёт ошибку источника.

   поэтому это предел полноты сверки официальных уведомлений, не обещание полного
   аудита закрытой документации.
3. **fin/infra:** в других действующих коллекторах остаются старые неограниченные
   циклы 429 (например accrual/by-day и product list). Это отдельное укрепление

4. **rev:** ограничение комментирования пустых отзывов — изменение правил,
   не переименование review/comment/create; в autosend уже есть mark_no_text.
5. Новый worktree shipment_guard имеет собственные изменения адаптера. Перед его
   отдельным merge владелец должен сохранить вызов product_price для обоих raw-форматов;

## Production и безопасное внедрение

Последняя проверка записана в `runtime_state.json`: PID **2681936** жив, cwd общий
checkout, журнал всё ещё заканчивается `Ozon постинги oz_acc2 2026-10-01..2026-10-31`.
Размер журнала не изменился. Открытых `idle in transaction` в БД не было; длительный
простой находится в сетевом чтении/ожидании, а не незавершённой записи raw.
Старые загруженные Python-функции не заменятся от обновления файлов.
Процесс не останавливали; полный pipeline не запускали.

Подготовлен **deployment.patch** (25 Python-файлов, включая helper, lock и тесты).
`git -C /opt/mp-analytics apply --check <абсолютный путь патча>` вернул 0 при текущих
чужих изменениях; один из затрагиваемых файлов в общем checkout уже dirty, поэтому
замена файла копированием запрещена. Патч накладывает только конкретные проверенные
куски. Хэши общего checkout для повторной сверки: `deployment_check.json`.
Все пять защищённых исходных файлов передачи на момент завершения совпали с
предварительными SHA256; общий checkout остался на main, HEAD не менялся.

Последовательность внедрения, **ещё не исполнена**:

1. Повторить git status/HEAD, проверку SHA256 затрагиваемых исходников и apply --check.
   Сохранить текущий diff и резервные копии файлов. Накладывать только deployment.patch;
   не копировать web/app целиком, не stash/reset/clean чужие изменения.
2. Применить код; миграции/токены не нужны. Повторить тесты совместимости/SQL в новом
   контексте. Сторожи, вебхуки и уведомления не включать и не перезапускать.
3. Перед завершением старого процесса заново проверить PID + время старта + cmdline,
   фазу журнала и pg_stat_activity/транзакции. Если это тот же зависший процесс на HTTP,
   завершить его штатным SIGTERM, дождаться выхода и освобождения flock. SIGKILL без
   причины не нужен. Редактирование Python не продолжит уже импортированный старый код.
4. Продолжение — следующий штатный запуск с исправленным collector; не запускать полный
   run_daily и не пересобирать исторические витрины ради smoke. Если нужно ускоренное
   восстановление источника, отдельно выбрать только нужный период и кабинет и
   проверить фактическую полноту источников перед материализацией.
5. После штатного запуска проверить новые страницы, времена raw, отсутствие FAIL/skip
   по постингам и source gates. Для веб-читателей новое значение начнёт использоваться
   после их обычного согласованного deployment/reload; до этого raw нового формата
   массово не загружать.

Rollback кода: обратный проверенный patch/резервные копии только своих кусков.
Возвращать старый URL в работу нельзя: это снова зависание на отключённом методе.
DB rollback не требуется: в этой сессии записи данных не было.

Предыдущие задачи wb4c сохранены: исправление сопоставления WB названий файлов акций
с календарём и сбой Ozon actions/products. Отчёт 148 часов, банковские документы,
ценовые операции и прочие завершённые задачи повторно не выполнялись.
