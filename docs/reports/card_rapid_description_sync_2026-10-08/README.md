## Расписание

Установлен разовый systemd-таймер `card-rapid-description-20261008.timer`. Подтверждённый следующий запуск: **08.10.2026 23:15 UTC = 09.10.2026 02:15 МСК**. Это один запуск в ночь с 8 на 9 октября, не ежедневная синхронизация. На момент постановки таймер активен, сервис записи не запускался.

Единицы в репозитории: `tools/card-rapid-description-20261008.service`, `.timer`; установлены в `/etc/systemd/system/`. Исполнитель: `tools/card_rapid_description_sync.py --apply`. Для запуска после перезагрузки таймер включён; пропущенный запуск днём не догоняет (`Persistent=false`). Жёсткое окно записи 23:00–05:00 МСК.

Описание копируется дословно из `Name` API; пустые названия не затирают поле. Остаток API, остаток МС и наличие оприходования **не используются как фильтры**. Текущие совпадения не отправляются.

## Запись и проверка

Изменяемое поле — только `description`; в payload `id` и `description`. Наименование, Чип, артикул, внешний код, поставщик, остатки, закупочная и оприходования не меняются. Новые карточки не создаются.

Перед каждой записью перечитываются карточки, проверяются поставщик, артикул, внешний код, активность и отсутствие изменения описания с момента снимка. Сохраняются полные резервные копии изменяемых карточек. Партия 50, пауза не менее 60 секунд; при медленном ответе пауза 120 секунд. После первых 200 изменений — пауза 10 минут и контроль чтения операционного документа МС. Это технический контроль доступности, не доказательство доставки каждого вебхука. Вебхуки не подавляются; изменение считается значимым при отсутствии полного списка потребителей. Владелец предупреждён в рабочем диалоге.

Запуск не пишет, если параллельно работает существующий `prc-enter-buyprice.service`. Потолок исполнителя — 4 000 изменений за ночь; при большем плане стоп до записи. Журнал fsync сохраняет отправленные id до запроса, затем каждое изменение проверяется живым GET. При ошибке запись останавливается; автоматических повторов неоднозначной записи нет. Обычный повторный старт при существующем журнале запрещён. Явный `--resume` сверяет журнал с замороженным планом, исключает уже проверенные id, перечитывает оставшиеся и сохраняет отдельные резервные копии восстановления. Чтения в записи дополнительно замедлены до не более пяти в секунду.

Результат будет в `night/summary.json`, журнал — `night/journal.jsonl`, снимки — `night/ms_before.json`, `night/backup_batch_*.json`. Статус `complete` и `writes=verified` подтверждают завершение. Ошибка даёт `status=failed` и журнал сервиса; молчание не считается успехом.

Для возврата значения используются `old_description` из ночного плана/резервных копий; автоматического отката нет, чтобы не затереть последующие ручные изменения.

Проверены четыре теста: нулевой остаток включён; архив/чужой поставщик/неоднозначный артикул/пустое имя исключены; нормализация артикула не меняет артикул МС; изменения идентификаторов или описания между чтениями блокируют запись. Проверка systemd-единиц прошла. Ключ API хранится в `.env`, не в коде и не в отчётах. Коммитов/пушей нет.
