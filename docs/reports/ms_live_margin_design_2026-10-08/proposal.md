# Оперативный контроль маржи отгрузок МС — предлагаемая схема

Дата: 08.10.2026. Это проект решения; сервис, подписки МС, уведомления и цены не изменены.

Уточнённая задача для реализации после вопросов пользователя: [docs/TASK_SHIPMENT_GUARD.md](/opt/mp-analytics/docs/TASK_SHIPMENT_GUARD.md). При расхождении использовать её: цена/FIFO должны быть доступны сразу по рабочему процессу, отсутствие обязательных данных — видимая ошибка полноты, не обычное бесконечное ожидание.

## Охват
Общий обработчик всех demand обоих юрлиц. Для WB, Ozon и Маркета отдельные адаптеры заказа/полной цены/правила пола, общий FIFO и очередь. Возможность прямых/оптовых отгрузок заложена, но правила их пола должны быть определены отдельно; уточнение охвата отправлено пользователю. Неизвестный контрагент — «правило не настроено», не мнимая нулевая комиссия.

## Приём событий
CREATE/UPDATE/DELETE demand. Приёмник сохраняет событие в PostgreSQL и быстро подтверждает его; никаких запросов МС/площадок в HTTP-приёмнике. Дедупликация requestId, объединение событий одного документа за 10–20 секунд. Если изменение пришло во время расчёта, новая версия остаётся в очереди. Удаление отменяет актуальный сигнал.

## Обработка и нагрузка
Отдельный единственный worker, один одновременный запрос МС, потолок 1 запрос/с для нового сервиса. При нехватке Remaining он замедляется, при 429 учитывает Retry-After; повторения ограничены и проходят через ту же очередь. Это добавочный лимит, не лимит всей системы: существующие сборщики имеют собственные процессные throttle, поэтому перед включением нужны наблюдение общего потребления и координация; нельзя заявлять, что локальный limiter защищает все процессы.

На новый короткий документ ориентир 2–3 чтения МС: документ с позициями / позиции и FIFO byoperation. Сколько именно — зависит от expand и пагинации. При условных 200 новых документах 400–600 запросов плюс изменения, сверка и повторы. При одновременном поступлении 100 документов: ориентир 200–300 секунд на запросы при 1/с плюс задержки API и расчёта. Очередь сохраняется при рестарте; обычная задержка должна измеряться на реальных событиях, целевой ориентир 30–90 секунд после доставки вебхука при доступных источниках.

Повторный расчёт только при изменении влияющих полей (цена, позиции, количество, проведение, контрагент/юрлицо/склад/дата). Неизменённый FIFO можно переиспользовать, но изменения поступлений/даты/склада могут поменять FIFO — ограниченная последующая сверка фактической себестоимости обязательна. Справочники контрагентов/юрлиц кэшируются. API площадок имеют собственные очереди и лимиты; недоступность цены не блокирует остальные документы.

## Страховочная сверка
Каждые 30 минут получать только новые/изменённые demand по updated после сохранённого checkpoint с перекрытием. Пагинация до конца, checkpoint только после успешного завершения; пропущенные события ставятся в общую очередь. Сверка не пересчитывает всю историю. Краткий периодический контроль недавно рассчитанного FIFO выявляет изменения себестоимости без UPDATE самого demand.

## Точность сигнала
Полная цена берётся из проверенного источника соответствующей площадки; demand.sum не всегда включает компенсацию скидки. FIFO только реальный byoperation на документ, без карточного buyPrice/средних/импутаций. Пока документ не проведён или источник не готов, статус «расчёт ожидает данные» с повтором. Нет данных — не ноль.

Сигналы: подтверждённая цена ниже FIFO; цена ниже принятого пола по правилам конкретной площадки; ожидает данных. Маржа с ещё не начисленными услугами площадки всегда предварительная, окончательная уточняется по финансовым отчётам. Общий коэффициент удержаний не считается фактическими услугами заказа. Порог, дата финансовой базы и источник себестоимости сохраняются с расчётом.

В Пульте: документ/заказ, площадка/юрлицо, SKU/количество, полная цена, FIFO, порог, остаток, источники/статус и возраст очереди. Изменения цены/блокировка отгрузки не входят в эту задачу.

## Порядок реализации
1. Общая очередь, очередь повторов, limiter, адаптеры и карточка результата без исходящих сообщений.
2. Проверка на существующих реальных отгрузках: повтор события, UPDATE во время расчёта, задержка FIFO/цены, 429, рестарт, пропуск события, партия 100 документов, мультипозиционные заказы.
3. Приёмник и контрольная сверка; подключение подписок МС после готовности рабочего адреса.
4. Измерение задержек/добавочной нагрузки и расширение охвата без изменения общей архитектуры.
