# WB: безопасная цена входа в автоакции, 21.10.2026

Поручение выполнено для Цифрового и Дисквера. До начала новых автоакций
3038/3040 выполнена защита известных цен ниже пола и включено расписание.
Старт: **21.10 21:00 UTC = 22.10 00:00 МСК**. Фактическое участие после старта
на момент подготовки этого отчёта ещё не проверено.

## Что реально применено и проверено

| Проверка | Цифровой | Дисквер |
|---|---:|---:|
| Карточек в актуальном Prices API | 18 274 | 20 093 |
| Карточек в объединённом плане новых и осенних акций | 15 713 | 16 318 |
| Подъём ранее существовавшей цены ниже пола | **5** | **37** |
| Дополнительный пилот изменения скидки без изменения базы | **1** | **1** |
| Подтверждено отдельных изменений цен | **6** | **38** |
| Незавершённых заданий после пилотов | **0** | **0** |

Все 44 изменения подтверждены живым Prices API после обработки заданий ВБ.
У пилота уменьшения скидки цена только повышалась, не более чем на 15%;
проверялась действующая осенняя акция, будущее время в боевом режиме запрещено.
Повторные запуски по расписанию прошли успешно: среди контролируемых карточек
с полной рассчитанной себестоимостью цен ниже актуального пола не осталось.
Это проверка цены, **не официальное подтверждение выхода/входа в автоакцию**.

## Правила расчёта

- Единственный источник минимальной прибыли — `core/profit_floor.py`, версия
  `profit-floor-200-through-150-v1`. До 150 ₽ включительно на расчётную единицу:
  200 ₽ прибыли на единицу; выше: max(300 ₽ × количество; 10% полного себеста).
- Учёт наборов, универсальных моделей, кратности, доступности поставщика >=4 шт.
  и полная стоимость состава взяты из действующего `wb_promo_guard.cogs_map`.
  Источник себестоимости не заменён ценами из XLSX или частичным составом.
- Удержания сохранены из действующего WB-сторожа: 56,9% и 55,4%. Целевая цена
  проверяется после скидки продавца, до СПП. KPI 25% не подменяет пол прибыли.
- Выбирается **максимальный лимит цены** из подтверждённых выгрузкой действующих
  автоакций, затем минимальная целая скидка, позволяющая уложиться в этот лимит.
  После округления цена строго >= пола и <= выбранного лимита.
- Для обычного входа база не увеличивается. Если даже нулевая скидка не даёт
  нужный пол, отдельная защитная операция повышает базу до безопасного уровня.
- Если лимит ниже пола либо целая скидка не помещается в безопасный диапазон,
  цена для входа не отправляется. При фактическом снижении ниже пола цена
  поднимается независимо от baseline и работоспособности календаря.
- Снижение цены для входа разрешено только при свежем положительном остатке
  в WB Analytics и полной доступной себестоимости. Нет строки в аналитике
  не означает нулевой остаток: такая карточка не получает ручного снижения.
- У карточки без полной себестоимости после старта цена
  поднимается выше максимального известного действующего лимита; себест и
  прибыль для неё не выдумываются. Это защита от входа в известные акции,
  а не расчёт экономического пола неизвестного товара.
  Отсутствие строки остатков не отключает эту защиту.

## Источники и осенние акции

Прочитаны три XLSX из Dropbox 21.10 и Downloads.zip. В ZIP один файл принадлежит
Дискверу, другой дублирует файл Цифрового; кабинет определяется по бренду.
В WB-файлах ошибочный dimension=A1: чтение использует reset_dimensions(),
строковые числа с пробелами/запятыми преобразуются в Decimal.

Плановые цены «Осенних скидок» взяты из сохранённых выгрузок **08.10**,
относящихся к текущему поколению акции с началом 07.10 21:00 UTC.
Сентябрьские одноимённые выгрузки не используются. Даты в legacy-таблице
не переписывались. Для Дисквера 3010/3012 имеют одинаковые название и окно,
а два файла содержат непересекающиеся карточки: в манифесте сохранена группа
ID, индивидуальное membership не придумывается.

На ночной старт сравниваются 3038/3040 и 3012, у Дисквера также 3010.
Будущая 3053 с началом 26.10 и заканчивающиеся перед стартом большие распродажи
не учитываются как действующие ночью. Regular-акции 3126/2766 не регистрируются.
Манифест содержит исходные хеши и проверяется перед использованием; поколение
и окно каждого лимита сопоставляются со свежим календарём API.

Расчётные CSV и JSON — диагностический прогноз по доступным файлам и текущей
базе цен. Это не импортный шаблон WB и не список реально вступивших товаров.
При новых выгрузках с изменёнными лимитами нужен новый проверенный манифест.
API автоакций не даёт используемому инструменту достоверного текущего membership.

## Повторы и отказы

- До POST на диск записываются барьер и транзакционный intent в SQLite
  (WAL, synchronous=FULL). Принятый uploadID сохраняется отдельно.
- При рестарте сначала проверяется старое задание и реальные цены каждого
  товара. Частичный успех не превращается в успех всей пачки.
- HTTP 429 не считается принятием: возможен повтор в следующем ограниченном
  запуске. GET имеют ограниченное число попыток, учитываются заголовки WB.
- При таймауте POST, неоднозначном 5xx/408/409 либо падении между отправкой и
  сохранением uploadID **слепого повторного POST нет**. Кабинет остаётся под
  барьером до сверки задания. Без idempotency key нельзя обещать exactly-once
  после такого окна сбоя; это явный случай для ручного восстановления uploadID.
- После принятия опрашивается статус и перечитываются цены. Даже совпавшая
  цена не снимает барьер, пока само асинхронное задание ещё не терминально.
- Смена базы/артикула/скидки между расчётом и отправкой учитывается повторным
  чтением. Свежий провал ниже пола пересчитывается в том же запуске; обычное
  снижение по устаревшему снимку пропускается. Чужой новый vendor не переоценивается
  с себестоимостью старого товара.
- Два кабинета обслуживаются независимо в двух ограниченных рабочих потоках.
  Сбой одного не отменяет второй. Общий writer lock координирует проектные
  записи старого сторожа, plan_raise и WB-части выпуска из карантина.
- Старый `MIN(cap)` plan_raise не переоценивает карточки под управлением нового
  `MAX(active cap)` контроллера. Старые guard/quarantine POST направлены в общий
  надёжный writer; карантин дополнительно проверяет свежий полный себест и пол.
- Пределы времени, CPU/RAM и отсутствие вечных HTTP-циклов заданы явно.
  Ошибка/частичность остаётся в статусе, журнале systemd и журнале товаров.
  Новый канал Telegram-уведомлений не включался.

## Расписание и эксплуатация

- По уточнению пользователя: `wb-auto-entry.timer` запускает вход в **00:00 МСК
  22.10**, проверки в **00:30** и **01:00**. Других регулярных запусков нового
  контроллера нет. В **02:00 МСК** работает прежний плановый WB-сторож.
- Только при ошибке, незавершённом задании или недосланном остатке пачек —
  повтор через 2 минуты. systemd ограничивает частоту до 3 стартов за 20 минут;
  успешная волна повторов не вызывает.
- `wb-auto-entry-stocks.timer`: подготовка перед тремя волнами — **23:45,
  00:15 и 00:45 МСК**. Фонового обновления раз в 5 минут больше нет.
  WB Analytics читается отдельно,
  с интервалом около 21 секунды и возобновлением со следующей страницы.
  Аналитика не задерживает срочное восстановление пола.
- Тёплый кэш остатков живёт 30 минут. Полный проход выполнен: 15 868 и 16 690
  уникальных карточек аналитики; отсутствие остальных не приравнивается к нулю.
  Перед волной снимок старше 20 минут обновляется: новый проход собирается отдельно,
  ещё действующий полный снимок заменяется только после завершения нового.
  При холодном старте возможен частичный кэш: он не задерживает защитный подъём,
  но до подтверждения остатков часть ручных снижений остаётся отложенной.
- Цена: до 150 секунд на кабинет, общий systemd timeout 210 секунд,
  CPUQuota=60%, MemoryMax=768M. Остатки: 420 секунд на кабинет,
  timeout 900 секунд, CPUQuota=30%, MemoryMax=384M.
- Persistent-таймеры подхватывают пропущенный запуск после перезагрузки.
  Дублирующий запуск пропускается по flock; осиротевший PID не держит блокировку.

Основные команды из общего checkout:

```sh
./venv/bin/python -m ops.wb_auto_entry                   # только прогноз
./venv/bin/python -m ops.wb_auto_entry --recover-only    # сверка старых заданий, без POST цены
systemctl list-timers --all wb-auto-entry.timer wb-auto-entry-stocks.timer
journalctl -u wb-auto-entry.service -n 10 --no-pager
```

Состояние: `runtime/wb_auto_entry/latest/status.json`, `running.json`,
`journal.sqlite3`, `*.pending`; исходные ответы Prices API и календаря —
сжатые JSON с ограниченной ротацией в `runtime/wb_auto_entry/raw/`.
Цена/себест/причина/подтверждённые значения каждого отправленного товара
сохраняются в локальном журнале. Секреты там не сохраняются.

Для остановки сначала выключить оба таймера и дать активным заданиям завершиться.
Нельзя удалять барьер/журнал, пока задание WB может примениться позже. Откат цены
к исходной автоматически не выполняется: исходная цена могла быть ниже пола.
Резервные копии интеграции лежат в runtime/deployment_backups; целиком возвращать
старый guard поверх новых чужих изменений нельзя — отменять только свои хунки.

## Проверки и ограничения

**74 теста и 5 subtests прошли**: расчёт, граница дешёвых товаров, кратность,
истёкшие/будущие поколения, округление, отсутствие остатков, неоднозначный POST,
перезапуск, частичное применение, writer lock, карантин, сбой календаря,
снижение цены WB во время подготовки, независимость кабинетов.
Юниты systemd прошли `systemd-analyze verify`; реальные плановые прогоны успешны.

По прямому решению пользователя **нативные минимум/блокировки в ЛК пропущены**.
Поэтому ВБ может временно опустить цену до первой проверки или позднее вернуть
автоскидку. Контроллер исправляет обнаруженное, но не устраняет это окно атомарно
и не блокирует внешнюю переоценку ТК/ручную работу в ЛК. Подтверждение фактического
участия после старта потребует актуальной выгрузки WB.

Чужие изменения сохранены: в действующем guard заменён только writer и CLI hook,
в plan_raise — CLI hook, в карантине — только WB writer и его координация.
Общий сегодняшний `core/profit_floor.py` не изменялся. Работа ведётся в
`fin/wb-auto-entry-20261021`; коммит/публикация не выполнялись без новой команды.
Зависимость общей политики пола в shared checkout пока не отслеживается git:
при последующей публикации обязательно включить соответствующий commit владельца,
не присваивая его чужие изменения. Другие задачи wb4c сохранены в прежнем worktree.
