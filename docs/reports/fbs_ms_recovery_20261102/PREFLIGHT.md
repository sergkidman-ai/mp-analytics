Минимальная реализация: использовать customer_guard WB/Yandex клиенты и Ozon FBS v4, существующий remap MS-клиент и Planner для пула запасов; восстановить/подтвердить мост MP SKU→MS externalCode (суффикс не срезать вслепую). Обычные товары с подтверждённым мостом не блокировать из-за недоступности ТК. Наборы — по подтверждённому составу ТК: рекурсивный состав × количество, приоритет одной пары поставщик+бренд; при невозможности допустимо не больше двух разных пар поставщик+бренд (и не больше двух поставщиков и двух брендов), иначе оставить одной позицией для ручного разбора. Для такой позиции использовать существующую карточку МС с точным внешним кодом из заказа МП; статус «Ожидает подтверждения». Отсутствие CARTRIDGE_API_KEY не блокирует подтверждённые обычные товары; неподтверждённые наборы идут в ручной разбор. Если карточки МС с точным externalCode нет, не создавать вымышленный товар — исключение. При достаточном наличии использовать существующий Planner с пулом резервов; архив/брак исключать. При недостаточном наличии выбрать карточку по новой очереди поставщиков и минимальной положительной закупочной цене среди актуальных оприходований МС. Источник цены — `entity/enter` на «Удаленном складе», только последние действующие документы группы без `_old`, `positions.price` в копейках. Код `prices/unlinked.py` уже определяет актуальные документы; точечное чтение подтвердило наличие `price` в позициях. При неоднозначной или отсутствующей цене карточку не выбирать без подтверждения.

Статус обеспеченного: «Собирается», дата отгрузки текущая МСК до 16:00, затем следующий календарный день; необеспеченного: «Ожидает подтверждения», без плановой даты. Импорт создаёт только customerorder. Отдельный инструмент вправе затем обработать его и создать demand, по уточнению пользователя. Исторические аудиты показывают связанные отгрузки примерно через минуту после «Собирается»; импортер не вызывает demand API. Никаких статусов или поставок МП не менять. Сначала один тест на каждую площадку после согласования, затем ручная проверка, потом отдельное разрешение на партии.

Новое правило пользователя: при недостатке остатка искать точный externalCode по очередям. Очередь 1: «ООО ОДИССЕЙ WB», «ООО КВК ТРЕЙД OEM», «ТОНЕРОПТТОРГ (Изипринт) T2» для соответствующих товаров WB/OEM/T2. В первой очереди с подходящими карточками брать минимальную подтверждённую закупочную цену; к следующей переходить лишь если в предыдущей нет пригодной карточки/цены. При равенстве цены — стабильная сортировка по ID карточки, с журналом выбора. Маппинг юрлиц брать по ID из `invoice_bot/supplier_groups.py`, не по ИНН и не по похожему названию. Подтверждение соответствующей специализации WB/OEM/T2 брать из данных карточки/поставщика; при противоречии — исключение. Это правило не разрешает создавать новые справочники или карточки.
