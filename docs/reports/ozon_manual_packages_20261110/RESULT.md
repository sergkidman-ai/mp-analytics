# Ozon: ручное разделение отправлений, 10.11.2026

Включено в штатном обработчике без изменения его расписания20минут.
При сумме Ozon>30 000₽ либо сумме количеств всех SKU>8 перед автоматическими
GTD/exemplar/ship сохраняются MS«Кол-во грузовых мест»="2" и статус
«Не собран в ЛК Озон». Ровно30 000₽/8шт. не включают эту остановку.
Оператор сам разделяет, распределяет товары и нажимает«Собрать» в ЛК Ozon.

ops.ozon_manual_packages — первый этап ops.fbs_order_processor.
Группа строится исключительно по parent_posting_number/related_postings и order_id.
Ожидается готовность всех фактических отправлений; отменённый исходный posting
не превращается в дополнительный полный заказ. Проверяются сохранение SKU/qty/цен
и суммы каждого нового posting. Исходные id MSorder/demand переиспользуются для
одного места; остальные имеют стабильные UUID и точные номера Ozon. Поставщики,
товарные карточки, бандлы, скидки и НДС сохраняются в совокупности. После проверки
всей группы: по одному заказу/проведённой отгрузке на номер, поле мест="1", статус
«Собирается»; дальнейший жизненный цикл — обычный синхронизатор МП→МС.

Сначала распроведение исходного demand, уменьшение исходного order, затем прочие
пары. Перед каждой записью проверяются версии группы; перед проведением — свежий
физический stock−чужие резервы. Смена связанных MSсчётчиков/версий после собственного
проведения подтверждается отдельно с полным сравнением бизнес-полей. Никаких
автоматических замен товара. Для ручного состава разрешено лишь точное разделение
существующих строк; его защита наследуется новыми заказами. Ошибка аудита останавливает
перенос. Общий загрузчик пропускает производные контролируемой группы.

Журнал.private/ozon_manual_packages содержит исходные данные, план и одноразовые
намерения каждой PUT/POST. Таймаут не вызывает слепого повторения; результат
сверяется по фактическому документу. Все промежуточные заказы сохраняют ручной
статус до общей проверки. При несовпадении денег/товаров, чужом документе, связанных
финансовых документах, нехватке остатка или ручной правке операция останавливается.

Проверки:172pytest+34subtests PASS, включая строгие границы, два SKU×5,
3места, бандлы, сохранение/наследование ручных карточек, копеечное несовпадение,
ошибку аудита, нехватку свежего остатка, дубли, неполную семью и ожидание оператора.
Имитация смерти процесса после каждой из7мутаций подтверждает восстановление
без повторной записи; потерянный ответ тоже сверяется чтением. Общий загрузчик,
адаптер Ozon/WB/Маркета, отгрузки, обработчик после приёмок и ручная защита проверены.

После публикации main-чекаут не переключался; изменения других сессий сохранены.
ms-supply-fulfillment перезапущен только при отсутствии queued/runningjobs
(94done,15manual) и активен. Таймер fbs-confirmed-daily-dispatch активен.
Разовый --apply нового worker:checked0, без записей MP/MS. Боевой split ещё не
выполнялся: готовой ручной группы в новом журнале не было. На синтетике проверено
переименование исходного номера и совпадение количеств/сумм всех новых документов.

Read-only проба40Ozonpostings выявила3выше порога;2MS«В пути» с отгрузкой,
1«Неукомплектован» без отгрузки. Эти заказы ретроспективно не менялись. В историческом
импорте встречается разница между точной ценой Ozon и MSsum из-за округления процента
скидки. Такой случай новый перенос останавливает, а не корректирует вручную выбранные
цены. Исправление общей денежной формулы старого загрузчика в эту задачу не входило.

Ещё до изменений штатный oneshot возвращал exit1 из-за unresolvedзаказов,
хотя обе стадии выполнялись и таймер продолжал запускать его. Новый первый этап
не зависит от этого; check=False сохраняет выполнение последующих стадий.
