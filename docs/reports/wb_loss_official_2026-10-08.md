## Правила подбора и пределы результата

Возврат на склад ВБ обезличивается. Архив не содержит даты изменения статуса и склада последующего возврата.
Даже единственный кандидат не подтверждает партию потерянной физической единицы.

Состав ТК раскрыт через `set_cost.components` (повторы, вложенные наборы, старые строковые словари);
универсальные модели связаны через двунаправленный граф `prc_tc_link`.
Сохраняются ведущие нули. Точный код имеет приоритет; суффикс семейства допускает известный код первых четырёх
символов, но количество по X/Х не угадывается. Сравнивается весь состав фактических позиций МС.
Неизвестный внешний код фактически отгруженного товара не подменяется предположением.

Учитываются `canceled_by_client`, `defect` и финансовая операция «Возврат». Ранние/продавецкие отмены,
продажи без признака возврата и известный возврат продавцу вынесены в остальные проверенные документы.
Наличие дефекта само по себе не доказывает возврат именно на пострадавший склад.
Возвраты МС проверены по локальной таблице `ms_return_cogs`; отсутствие записи не доказывает отсутствие возврата.
Историческая применимость сегодняшнего справочника связей/составов отдельно не подтверждена.

Нельзя складывать количество кандидатов по складам или считать его покрытием утраченных единиц:
одна отгрузка может подходить разным строкам. Распределения партий нет.
Перед будущим расчётом нужен согласованный способ работы с неоднозначностью; фактическую себестоимость
брать из конкретной отгрузки МС, не из приёмок или `set_cost.cost`.

Кэш `ms_demand_cogs.moment` хранит местное время МС с меткой UTC (подтверждено сопоставлением документа 15.07
с живым API). В этой задаче время интерпретируется как московское; чужие таблицы не изменяются.

## Воспроизведение и проверки

Код: `ops/wb_loss_official.py`, миграция `512_wb_loss_official.sql`,
роутер `web/warehouse_loss_api.py`, страница `web/static/warehouse_loss.html`.
Таблицы `wb_loss_document`, `wb_loss_item`, `wb_loss_order_raw`, `wb_loss_search_page`,
`wb_loss_ms_lookup`, `wb_loss_analysis`. Сырьё и результаты раздельно; WB/MS только чтение.
Ответы API кэшируются: повторный запуск использует снимок обследования, не обновляет статусы автоматически.
Иной PDF для уже импортированного склада отклоняется и требует сверки версии — автоматически не суммируется.

```bash
./venv/bin/python -m ops.wb_loss_official import dropbox/20261008_184804_Natalie_Pro_natalya_Downloads.zip
./venv/bin/python -m ops.wb_loss_official fetch
./venv/bin/python -m ops.wb_loss_official match
./venv/bin/python -m ops.wb_loss_official fetch-ms
./venv/bin/python -m ops.wb_loss_official match
```

`fetch-ms` также перепроверяет отгрузки с отсутствующими/неподходящими локальными позициями из предыдущего `match`.
Состав/количество и стоимость из ТК не смешиваются: ценовые поля в подборе не читаются.
Подробный снимок результата: `data/wb_loss/analysis.json`, неразрешённые строки: `data/wb_loss/unresolved.csv`
(локальные служебные артефакты исключены из git).

Проверки: 8 модульных тестов (составы/эквивалентность/кратность/циклы/PDF), повторный импорт без дублей,
10 PDF через API, итог 362/329/10, отсечка дат всех кандидатов, отсутствие дублей по документу внутри строки.
Работающий Пульт: HTTP 200, браузер Chromium открыл 10 складов и детализацию отгрузок без ошибок JS.
