## Предложенная архитектура

Вебхуки demand CREATE/UPDATE/DELETE → транзакционное сохранение в существующий
PostgreSQL mp_analytics → постоянная очередь → один worker → результат/сигнал Пульта.
Контрольная сверка существующих документов каждые 30 минут восстанавливает события,
не доставленные вебхуком. Полный пересчёт всей истории не нужен.

### Где хранится очередь и когда подтверждать вебхук

В существующем PostgreSQL (контейнер mp-postgres, постоянный том pgdata),
не в памяти uvicorn, не во временном файле. Redis/RabbitMQ для этой задачи не нужны.
Предлагаемые отдельные таблицы (названия можно уточнить):
- ms_webhook_inbox: accountId, requestId, payload, received_at, processing/error;
- ms_shipment_jobs: accountId + demand_id, requested_generation, processed_generation,
  next_attempt_at, attempts, state, locked_until, last_error;
- ms_shipment_assessments: document/version, строки расчёта, цена/FIFO/пол/источники,
  status, calculated_at, бизнес-сигнал;
- ms_shipment_sync_state: сохранённые успешные границы сверки.

В одной транзакции принять inbox и поставить/обновить задания ВСЕХ events массива.
Только после COMMIT вернуть 200/204; при ошибке сохранения — 5xx.
requestId дедуплицирует уведомление целиком, но в нём может быть несколько событий:
не потерять остальные события первого запроса из-за уникального requestId.
Быстро подтвердить уведомление (МС ждёт 1500 мс); внешних API в приёмнике нет.
Уже сохранённый дубль подтверждать без нового расчёта/сигнала.
Зафиксировать фактическую политику хранения inbox/результатов и очистки завершённых
записей, не удалять pending/retry/error и не терять дедупликацию при очистке.

Worker: атомарное получение задания, lease и восстановление после падения.
UPDATE во время расчёта должен оставить новую generation в очереди: нельзя
сбросить её в done результатом старой версии. Ответы/события не обязаны приходить
в порядке создания. Читать актуальный документ, объединять его события 10–20 с,
проверять изменение влияющих полей. DELETE закрывает актуальный сигнал.

### Нагрузка и скорость

Один одновременный запрос МС, стартовый потолок НОВОГО сервиса 1 запрос/с.
Все пути — worker, retry, сверка и дополнительные чтения — под одним limiter.
Существующие collectors имеют процессные throttles: это не общий лимит аккаунта!
Учесть их одновременную работу и реальные RateLimit/Remaining/Retry-After;
оставлять запас квоты, снижать скорость, обрабатывать 429 с паузой, не запускать
полный run_daily ради сторожа. Не обещать безопасность по одному локальному limiter.
Строго ограничить параллелизм адаптеров площадок их собственными лимитами.

На документ ориентир 2–3 чтения МС (документ/позиции + byoperation), но замерить
реальный расход с учётом пагинации и повторов. При 200 новых документах ориентир
400–600 запросов без изменений/повторов; это оценка архитектуры, не факт нагрузки.
При пачке 100 документов 1 запрос/с даёт 200–300 с на запросы плюс задержки API.
Обычная целевая задержка 30–90 с после доставки события при доступных источниках;
не гарантировать её под массовым импортом. При всплеске очередь растёт, скорость
запросов НЕ растёт. Возраст очереди, запросы, 429, ошибки источников — видимы в Пульте.

### Потери событий и восстановление

Официально: после первой неудачи МС делает ещё 3 попытки, затем может удалить
неотправленное уведомление. Пропуск возможен при недоступности сервера/БД/сети;
уведомления также могут отключаться заголовком интеграции. Нулевая потеря не гарантируется.
- Приём сохраняет до ACK; рестарт не теряет уже принятые задания.
- Каждые 30 минут читать demand по updated от последнего успешного checkpoint,
  с перекрытием времени, полным обходом страниц и фиксированной верхней границей окна.
- Продвигать checkpoint только после успешного сохранения всех найденных заданий.
- Проверить часовой пояс дат МС, стабильность сортировки/пагинации и границы дат.
- Долгая авария: читать с сохранённого checkpoint, не только последние 30 минут.
- Пропущенный DELETE нельзя восстановить списком живых документов: отдельно
  предусмотреть проверку ранее отслеживаемых ID / доступные удалённые документы или
  audit, проверив реальные права и API. Быстро созданный и удалённый документ при
  полностью пропущенных событиях может быть невосстановим; не обещать обратного.
- Изменение прошлой приёмки может изменить FIFO без UPDATE самой отгрузки:
  ограниченный повторный контроль недавнего FIFO или подтверждённые события
  изменений поступлений, через ту же очередь и квоту. Не делать вечный кэш FIFO.

### Цена, FIFO и бизнес-правила

Основной источник — реальная отгрузка МС: sum в копейках, позиции/количество,
скидки/НДС по документу. Не подменять цену карточкой каталога/будущим платежом.
FIFO — report/stock/byoperation?operation.id=<demand_id>: фактическая стоимость
списания на дату документа. В стандартном JSON demand нет отдельного FIFO-поля;
его доступность в интерфейсе МС не отменяет отдельное чтение отчёта в API.
Проверено на недавних документах: custom attributes FIFO отсутствуют.
Стоимость byoperation уже включает количество: НЕ умножать её на qty второй раз.
quantity в byoperation — доступный остаток, НЕ число отгруженных единиц!
Количество брать из позиций отгрузки, как demand_positions_qty.
FIFO нулевой/неполный при ненулевых товарных позициях — видимая ошибка полноты;
ни cost_seb/buyPrice, ни средние, ни impute не применять. Короткий ограниченный
повтор разрешён для технической рассинхронизации; ошибку не скрывать до следующего дня.

У МС цена может быть заполнена, но не совпадать с полной базой площадки:
существующий ya_cogs_demand уже учитывает реальные номинальные суммы/компенсации
скидок Маркета. Начать с проверки полных цен документа на реальных примерах всех
площадок; в случае расхождения сохранять обе суммы и причину. Корректную полную
цену подтверждать адаптером заказа соответствующей площадки, не угадывать.
Это проверка смысла цены, а не утверждение, что цена в документе отсутствует.

Определение площадки/юрлица по реальным agent/organization и мостам заказа:
WB demand.name → assembly_id; Ozon → posting; Маркет → order_id.
Пол использует согласованное правило конкретной площадки/юрлица, сохранённую
дату и источник доли удержаний. Не применять расходы Маркета к другим площадкам.
В текущем стороже акций max(300 руб., 10% FIFO) — абсолютная цель,
не 25% маржи. Не менять бизнес-правило молча и не называть его 25%.
Для многопозиционных/многоколичественных отгрузок проверять и товар, и документ;
убыточная строка не должна скрыться за прибыльной. Повторяющийся ms_id и возвраты
не должны удваивать qty/FIFO. Если API даёт FIFO по товару в целом, не выдумывать
разнесение по неоднозначным строкам с разными ценами: показывать проверяемый уровень.
Прямые/оптовые контрагенты без заданного правила получают «правило не настроено»,
но цена/FIFO и проверка цены ниже FIFO сохраняются. Нет комиссии в данных ≠ комиссия 0.

Сигналы:
1. Подтверждённая полная цена ниже реального FIFO (даже до комиссий).
2. Цена ниже принятого пола с учётом согласованной базы расходов — предварительная
   экономика, не фактически начисленная комиссия этого заказа.
3. Ошибка обязательных данных / неизвестное правило — отдельный видимый статус.
Окончательную маржу после услуг площадки уточнять отчётами; не представлять оценку
расходов за фактический отчёт. Хранить источники, дату базы и версию правила.

## Порядок работы новой сессии и приёмка

1. Read-only preflight: HEAD/status, активные процессы/кроны, существующие вебхуки
   (GET без печати секретных URL), актуальные контрагенты/правила всех площадок.
   Общий checkout main грязный, не переключать/сбрасывать. На 08.10 HEAD d41f573,
   origin/main 959c6a3; это состояние при подготовке, проверить заново.
   Работать в .claude/worktrees/fin-shipment-guard, ветка fin/shipment-guard от
   актуального origin/main, симлинки .env/venv и .workstream=fin.
2. Реализовать отдельные миграции, очередь/worker/limiter/адаптеры, приёмник и UI;
   не писать margin_by_sku и не запускать финансовые пересборки для событий.
3. Проверить: много events в одном запросе; дубль requestId; БД недоступна до ACK;
   падение worker после claim; UPDATE во время расчёта; порядок событий; DELETE;
   пропуск вебхука и восстановление; неуспешная страница сверки; границы дат;
   429; пачка 100 документов; цена/FIFO отсутствуют; номинал МС; qty>1;
   несколько товаров/повтор одного ms_id; доли расходов разных площадок.
4. Подключать новые подписки только к уже рабочему, проверенному приёмнику;
   существующие подписки не удалять/изменять. При реализации этой задачи это
   техническая часть подключения сторожа, а не изменение торговых документов.
5. Измерить фактическую добавочную нагрузку/задержки. Рестарт не теряет очередь;
   запросы сервиса не превышают 1/с и не идут параллельно; ошибки обязательных
   данных видимы; пропущенный CREATE существующего demand восстанавливается;
   старый результат не затирает новую версию; цены/документы МС не изменены.
6. Обновить собственный бриф: код/миграции/сервис, установленная версия, созданные
   подписки, проверки и ограничения. Пользователю дать рабочий раздел Пульта.
