Дата: 28.07.2026. Аккаунты: `oz_acc1` (seller_id 217678, «Цифровой»), `oz_acc2` (seller_id 2523124).

## 0. Как это проверялось и чего в отчёте НЕТ

**Доступа к веб-интерфейсу личного кабинета Ozon Seller у меня нет** — ни сессии, ни кук.
Есть только программные доступы из `.env` проекта:

- Seller API (`api-seller.ozon.ru`) — пара Client-Id + Api-Key на каждый из двух аккаунтов;
- Performance API (`api-performance.ozon.ru`) — client_id + secret на каждый аккаунт.

Поэтому «пройти по кабинету глазами» я не мог. Вместо этого сделан более жёсткий тест:
**A/B-простукивание двух аккаунтов одними и теми же вызовами**. На `oz_acc2` часть методов
отдаёт `403 PermissionDenied: not available with existing subscription` — то есть Ozon сам
показывает, что закрыто без нужной подписки. Всего выполнено ~190 проб.

Официальную документацию Ozon (`docs.ozon.ru`, `seller-edu.ozon.ru`) с этой машины прочитать
не удалось: сайт отдаёт бесконечный редирект 307 и на curl, и на инструмент загрузки страниц
(анти-бот). Всё, что взято не из API, помечено как непроверенное.

Маркировка по всему отчёту:

- ✅ **ПРОВЕРЕНО** — лично выполнил вызов, вижу данные;
- ⛔ **ЗАКРЫТО** — вызов возвращает отказ по подписке;
- ❌ **НЕТ В API** — метода не существует (404);
- ⚠️ **НЕ ПРОВЕРЕНО** — только из вторичных источников или требует UI кабинета.

**Побочный эффект проб:** два вызова создали реальные файлы в разделе «Отчёты» на `oz_acc1` —
отчёт по товарам и отчёт по уценённым. Больше ничего мои пробы в кабинет не записывали,
всё остальное было чтением.

## 2. АНАЛИТИКА

### 2.1. Воронка продаж по каждому SKU ✅ ПРОВЕРЕНО

**Что даёт.** Полная воронка отдельно для поиска и для карточки товара — где именно теряются
покупатели. Доступные метрики (проверены поштучно, все отдают числа):

`revenue`, `ordered_units`, `delivered_units`, `returns`, `cancellations`, `hits_view`,
`hits_view_search`, `hits_view_pdp`, `hits_tocart`, `hits_tocart_search`, `hits_tocart_pdp`,
`session_view`, `session_view_search`, `session_view_pdp`, `conv_tocart`, `conv_tocart_search`,
`conv_tocart_pdp`, `position_category` (средняя позиция в категории).

Разрезы: `sku`, `spu`, `day`, `week`, `month`, `year`, `category1`, `category2`, `brand`,
`modelID`, `descriptionType`.

Ограничения (замерены): до **14 метрик** и до **4 разрезов** за раз, окно запроса **не больше
года** (`cannot get more than one year`), история есть минимум на 2 года назад, скорость —
**2 запроса в секунду**.

Устарели и больше не работают: `postings`, `postings_premium`, `adv_view_pdp`,
`adv_view_search_category`, `adv_view_all`, `adv_sum_all`, разрезы `category3`, `category4`.

**Где лежит.** `POST /v1/analytics/data`. В кабинете это «Аналитика → Воронка продаж» ⚠️ (сам
раздел не видел).

**Как забрать.** Только API, выгрузки файлом у метода нет. У нас уже есть каркас коллекторов
(`collectors/ozon_*.py`) — добавить сбор воронки в витрину рядом с `mkt_sku_economics`.

**Идеи для роста.**
1. Считать по каждому SKU связку «показов в поиске много → `conv_tocart_search` низкая»: это
   товары, которые Ozon уже показывает, а карточка не продаёт. Дешевле всего чинится
   контентом и ценой, без рекламы.
2. `position_category` в динамике по неделям — ранний сигнал проседания выдачи до того, как
   упадёт выручка.

### 2.2. Поисковые запросы по товарам ✅ ПРОВЕРЕНО

**Что даёт.** По каждому SKU — реальные запросы покупателей и позиция товара по ним. Поля
ответа: `query`, `query_index`, `position`, `unique_search_users` (сколько людей искали),
`unique_view_users` (скольким показали), `view_conversion`, `gmv`, `order_count`, `currency`, `sku`.

Живой пример с нашего `oz_acc1`:

| SKU | Запрос | Позиция | Искали | Показали | Конверсия |
|---|---|---|---|---|---|
| 2414969106 | `tk-5380` | 1 | 11 | 10 | 20% |
| 2509753251 | `принтер лазерный цветной` | 0 | 201 | 1 | 0% |
| 2509753251 | `картридж для принтера canon` | 271 | 146 | 3 | 0% |
| 1719404303 | `принтера` | 9 | 146 | 1 | 0% |

**Окно данных — 5 закрытых недель** (уточнено 30.07.2026 перебором по неделям, см. раздел 9.1:
отвечает всё с 22.06, с 15.06 — уже `getPremiumAnalyticsPeriod: There is no data for the
specified period`). Одинаково на обоих аккаунтах. `date_to` метод принимает, и он исключающий —
неделю можно брать чисто; без `date_to` подставляется «по вчера».

**Данные отстают на два дня.** Проверено 30.07 (четверг): `date_to=30.07` → 400, `date_to=29.07`
→ 200. Раз `date_to` исключающий, последний посчитанный день — позавчерашний. Практический
вывод: неделю, закрывшуюся в понедельник, в тот же понедельник забрать нельзя — регулярный
сбор поставлен на среду. Данные появляются только у товаров, у которых был поисковый трафик.

**Где лежит.** `POST /v1/analytics/product-queries` (сводка) и
`POST /v1/analytics/product-queries/details` (построчно по запросам). Формат даты — RFC3339
(`2026-07-20T00:00:00Z`), обычная дата не принимается. В кабинете — «Аналитика → Поисковые
запросы» ⚠️.

**Как забрать.** API. Так как окно всего 5 закрытых недель — **историю надо накапливать
самим**, еженедельным сбором в свою таблицу, иначе она безвозвратно теряется.
Сделано 30.07.2026: `collectors/ozon_search_queries.py` + таблицы `ozon_search_query` /
`ozon_search_product`, cron по средам.

**Идеи для роста.**
1. Ловить строки вида «искали 201 человек — показали 1 — позиция 0»: это спрос, который мы
   физически не забираем. Такие запросы → в заголовок/атрибуты карточки, а не в рекламу.
2. Запросы, где мы уже на позиции 1–5 с конверсией выше средней — сюда имеет смысл добавлять
   ставку в поиске: там окупаемость выше, чем на холодных запросах.

### 2.3. Цены конкурентов ✅ ПРОВЕРЕНО (но не то, что обещают блоги)

**Что даёт.** Ozon отдаёт список площадок-конкурентов для автостратегий цен: `market.yandex.ru`,
`wildberries.ru (после скидки постоянного покупателя)`, `ozon.ru` и ещё ~20 источников. Плюс
готовые стратегии (например «Следовать за самой выгодной ценой», тип `MIN_EXT_PRICE`) и по
каждому товару — `strategy_competitor_id`, `strategy_competitor_product_url`,
`strategy_product_price`, `price_downloaded_at`.

**Где лежит.** `POST /v1/pricing-strategy/competitors/list`, `/v1/pricing-strategy/list`,
`/v1/pricing-strategy/product/info`, `/v1/pricing-strategy/strategy-ids-by-product-ids`.
Доступно **одинаково на обоих аккаунтах**.

**Как забрать.** API. Сейчас у нас ни одна стратегия к товарам не привязана
(`products_info: []`, `is_enabled: false`).

**Идеи для роста.**
1. Подключить стратегию только на «красную» зону прайс-индекса (см. п. 4.1) — не резать маржу
   там, где мы и так в зелёной.
2. `strategy_competitor_product_url` даёт прямую ссылку на карточку конкурента по каждому
   нашему товару — это готовый вход для ручного разбора топ-20 позиций.

> ⚠️ Утверждение из блогов, что Premium Pro даёт «аналитику конкурентов через Seller API»
> (обороты конкурентов, лидер категории), **я подтвердить не смог**: методов
> `/v1/analytics/competitors`, `/v1/analytics/product/competitors` не существует — 404.
> Всё, что реально есть по конкурентам в API — это цены для стратегий, описанные выше.

### 2.4. «Что продавать на Ozon», тренды спроса, аналитика по категориям ❌ НЕТ В API / ⚠️ НЕ ПРОВЕРЕНО

### 2.5. Остатки, оборачиваемость, кластеры ✅ ПРОВЕРЕНО

**Что даёт.** Остатки по каждому складу (`promised_amount`, `free_to_sell_amount`,
`reserved_amount`), оборачиваемость, справочник кластеров и складов Ozon с типами
(`CROSS_DOCK`, `SORTING_CENTER` и т.д.).

**Где лежит.** `POST /v2/analytics/stock_on_warehouses`, `/v1/analytics/turnover/stocks`,
`/v1/analytics/stocks`, `/v1/cluster/list`. Работает на обоих аккаунтах.
Метода `/v1/analytics/manage/stocks` не существует — 404.

**Как забрать.** API (у нас уже есть `collectors/ozon_fbo_stock.py`, `ozon_stock_signals.py`).

**Идеи для роста.** Связать оборачиваемость с индексом локализации (п. 4.2): товары с высоким
спросом в дальних кластерах и нулевым остатком там — кандидаты на перераспределение поставки,
это одновременно и рост продаж, и снижение логистики.

### 2.6. Контент-рейтинг карточки ✅ ПРОВЕРЕНО

**Что даёт.** Оценка карточки (например 95.5 из 100) с разбивкой по группам (`Медиа` — 90 при
весе 45) и **списком конкретных условий**, что именно недозаполнено (например наличие
видео/видеообложки).

**Где лежит.** `POST /v1/product/rating-by-sku`. Работает на обоих.

**Идеи для роста.** Прогнать весь ассортимент, отсортировать по «вес условия × недобор» —
получится очередь на доработку карточек, отсортированная по влиянию, а не по вкусу.

### 2.7. Подписки покупателей на товар ✅ ПРОВЕРЕНО

`POST /v1/product/info/subscription` — сколько покупателей нажали «Узнать о поступлении».
У проверенных SKU — нули. Полезно как сигнал отложенного спроса по товарам, которых нет в наличии.

**Как забрать.** Схема одна: `create` → получаем `code` → `POST /v1/report/info` → в ответе

руками в кабинет ходить не нужно.

Разницы между аккаунтами нет.

### 3.2. География заказов ❌ НЕТ В API

В `/v1/analytics/data` **нет географических разрезов**: `region`, `oblast`, `warehouse`,
`deliverySchema` отклоняются как несуществующие. Косвенно география доступна двумя способами:
`/v1/cluster/list` + остатки по складам, и `localization_index` в рейтинге.

Полноценный отчёт «География заказов» ⚠️ по вторичным источникам есть только в веб-кабинете
(«Аналитика → География заказов», разрезы 30/60/90 дней). Не проверено.

**Идея для роста.** Пока API географии нет — выгружать этот отчёт руками раз в месяц перед
планированием поставки; он напрямую влияет на индекс локализации, а тот на стоимость логистики.

## 4. ПРОДВИЖЕНИЕ И РЕКЛАМА

### 4.1. Индекс цен — рычаг, который сейчас не работает ✅ ПРОВЕРЕНО

`/v1/rating/summary`, группа «Индекс цен» — фактическое состояние на 28.07.2026:

| Зона | `oz_acc1` | `oz_acc2` |
|---|---|---|
| Супервыгодная | 29% | 25% |
| Зелёная | 10% | 9% |
| Жёлтая | 14% | 18% |
| **Красная** | **47%** | **48%** |

Это важно, потому что буст в поиске (главная механика Premium по всем описаниям ⚠️) работает
**только у товаров с выгодным индексом цен**. У нас почти половина ассортимента в красной зоне —
то есть на этой половине подписка не даёт ничего, независимо от её уровня.

**Идеи для роста.**
1. Разобрать красную зону через нашу витрину `mkt_sku_economics` (медиана маржи 31.9%): где
   маржа позволяет — опустить цену до зелёной зоны, где нет — выводить из ассортимента.
2. Автоматизировать удержание зелёной зоны стратегией цен (п. 2.3) вместо ручных правок.

### 4.2. Прочие рейтинги и локализация ✅ ПРОВЕРЕНО

`oz_acc1`: оценка товаров **4.79** (порог Premium — 4.5, отдаётся в `/v1/rating/history` как
`premium_threshold`), жалобы FBS 0.99%, просрочек 0, индекс локализации **36%**.
`oz_acc2`: оценка 4.86, локализация 31%.

`/v1/rating/history` принимает окно не больше ~30 дней (`too wide range` на 90 днях) и имеет
параметр `with_premium_scores` — у нас массив `premium_scores` приходит пустым.

**Идея для роста.** Оценка 4.79 при пороге 4.5 — запас всего 0.29. Падение ниже порога снимает
привилегии сразу, поэтому мониторинг этого числа надо повесить на ежедневный прогон.

### 4.3. Реклама: Performance API ✅ ПРОВЕРЕНО, работает одинаково на обоих аккаунтах

| Что | Метод | Что отдаёт |
|---|---|---|
| Кампании | `GET /api/client/campaign` | id, title, `advObjectType` (у нас `ALL_SKU_PROMO` — «Оплата за заказ»), состояние, дневной бюджет, площадка |
| Расход по дням | `GET /api/client/statistics/expense` | CSV: ID;Дата;Название;Расход;Расход бонусов;Расход с абонентского счёта |
| Дневная статистика | `GET /api/client/statistics/daily/json` | по кампании и дню: `views`, `clicks`, `moneySpent`, `orders`, `ordersMoney` |
| **Лимиты ставок** | `GET /api/client/limits/list` | по каждой категории и типу размещения: `minBid`, `maxBid` (например SKU/CPC/поиск+категория: 7–200 ₽) |
| Отчёты статистики | `POST /api/client/statistics` → `/report` | ZIP с CSV по кампаниям |

Метод `/api/client/campaign/{id}/v2/products` для кампаний типа «Оплата за заказ» отвечает
«Кампания не найдена» — он работает для кампаний с товарными ставками (у нас это уже
используется в `collectors/ozon_bids.py`).

**Идеи для роста.**
1. `daily/json` даёт `moneySpent` и `ordersMoney` в одной строке — это готовый ДРР по кампаниям
   по дням; связав с `mkt_sku_economics`, можно резать кампании, где ДРР выше маржи.
2. `limits/list` показывает минимальную ставку по каждой категории — можно находить категории,
   где вход в поиск дешёвый, и заводить туда ассортимент прицельно.

> ⚠️ «Приоритет в поиске», бейдж продавца, повышенные лимиты на рассылки бонусов, скрытие
> рекомендаций конкурентов на своей карточке — этих сущностей в API нет ни в каком виде.
> Проверяются только в веб-кабинете.

| `sales_percent_fbs` / `rfbs` / `fbp` | 42% | 42% |
| Доставка до покупателя | 25 ₽ | 25 ₽ |
| Магистраль (мин–макс) | 99–415 ₽ | 99–448 ₽ (другой объёмный вес) |
| Первая миля | 0–10 ₽ | 0–10 ₽ |

**Комиссии идентичны.** Различия в магистрали объясняются объёмным весом товара, а не
аккаунтом. Никакой скидки на комиссию/логистику по подписке через API не наблюдается.
⚠️ Скидки на рассылки бонусов и прочие «денежные» бонусы подписки в API не представлены —
проверяются только в кабинете.

### 5.2. Что ещё отдаёт метод цен ✅ ПРОВЕРЕНО

`marketing_actions` по каждому товару — в каких акциях он участвует и на какую сумму. У нас
на обоих аккаунтах активен **«Эластичный бустинг. Без ограничения срока действия»**
(например 2 580 ₽ по одному SKU) и рассрочки 0-0-6 / 0-0-12. Плюс `acquiring` (эквайринг
в рублях на товар) и `price_indexes`.

**Идея для роста.** Эквайринг и участие в акциях по-товарно — это прямые входы в расчёт
реальной маржи; у нас в витрине они пока не учтены отдельной статьёй.

## 8. ТОП-5 возможностей с быстрым эффектом

### 1. Отзывы — единственная реальная привилегия подписки, и она недоиспользована

Факт: на `oz_acc1` **9 830 отзывов, из них 956 без ответа**. Это ровно тот функционал, за
который платим и который у `oz_acc2` закрыт наглухо. Движок автоответов на DeepSeek у нас уже
написан (ветка `eng/deepseek-answer-engine`).
**Действие:** добить движок до прода и разобрать очередь 956 отзывов. Ответы на отзывы влияют
на оценку товаров, а она (4.79 при пороге 4.5) удерживает саму подписку.

### 2. Красная зона прайс-индекса — 47% ассортимента

Половина товаров не получает буст в поиске ни при какой подписке.
**Действие:** прогнать красную зону через `mkt_sku_economics`, где маржа позволяет — снизить
цену до зелёной зоны, остальное вывести. Эффект виден в выдаче в течение недели.

### 3. Поисковые запросы — окно всего 5 недель, история теряется прямо сейчас

Данные `product-queries/details` живут ~5 недель и потом пропадают навсегда.
**Действие:** поставить еженедельный сбор в свою таблицу **на этой неделе**. Первый же отчёт
даёт список «спрос есть — показов нет» (как `принтер лазерный цветной`: 201 искали, показали
одному), это прямые правки заголовков и атрибутов.

### 4. Воронка по SKU — находит потери без затрат на рекламу

`/v1/analytics/data` с `hits_view_search` + `conv_tocart_search` + `position_category`.
**Действие:** отчёт «показов много, в корзину не кладут» → очередь на переделку карточек,
подкреплённая контент-рейтингом из `/v1/product/rating-by-sku`.

### 5. ДРР по кампаниям из Performance API

`daily/json` даёт расход и выручку в одной строке.
**Действие:** ежедневный ДРР по кампаниям против маржи из витрины; отключать то, где ДРР выше
маржи. Данные уже собираются коллектором `ozon_ads.py` — нужен только отчёт.

### С чего начать (первая неделя)

1. **Понедельник:** включить еженедельный сбор `product-queries/details` — иначе данные тают.
2. **Вторник–среда:** выгрузить красную зону прайс-индекса, свести с маржой, принять решения
   по ценам.
3. **Четверг–пятница:** довести автоответы на отзывы до прода и начать разбор 956 неотвеченных.

Пункты 4 и 5 — следующим спринтом, они требуют новой витрины, а не разовой выгрузки.

### 9.1. Поисковые запросы — ✅ РАБОТАЕТ НА ОБОИХ

**Сводка по товарам: `POST /v1/analytics/product-queries`**

Даёт по каждому SKU: сколько уникальных людей его искали, скольким показали, средняя позиция,
конверсия в показ, GMV с поиска.

Реальный ответ (`oz_acc1`, неделя с 20.07.2026), одна строка:

```json
{"sku": 652454637, "offer_id": "0960",
 "name": "Расходник для печати для струйного принтера Цифровой квадрат 711 DS, Пурпурный (magenta)",
 "category": "EPG", "unique_search_users": 28, "unique_view_users": "23",
 "position": 92, "view_conversion": 0, "gmv": 0, "currency": "RUB"}
```

Поля: `sku`, `offer_id`, `name`, `category`, `unique_search_users`, `unique_view_users`,
`position`, `view_conversion`, `gmv`, `currency`.

Самые полезные: **`unique_search_users` против `unique_view_users`** — разрыв показывает, что спрос
есть, а карточку не показывают; и **`position`** — средняя позиция в выдаче.

**Ловушка, из-за которой метод кажется нерабочим:** `skus` обязателен (1…1000 штук), но при
коротком списке метод молча возвращает `items: []` и `total: 0` — даже для SKU, по которым
детализация данные отдаёт. На 200 SKU он же вернул `total: 199`. **Слать нужно пачками по
несколько сотен SKU, а не по одному.**

**Детализация по запросам: `POST /v1/analytics/product-queries/details`**

Даёт конкретные поисковые фразы по каждому SKU. Реальный ответ (`oz_acc1`, неделя с 20.07.2026):

```json
{"sku": 651932253, "query": "картридж для принтера canon pixma", "query_index": 23,
 "position": 0, "unique_search_users": 15, "unique_view_users": 1,
 "view_conversion": 0, "gmv": 0, "order_count": 0, "currency": "RUB"}
```

Поля: `sku`, `query`, `query_index`, `position`, `unique_search_users`, `unique_view_users`,
`view_conversion`, `gmv`, `order_count`, `currency`.

Самые полезные: **`query`** (сама фраза — сырьё для заголовков и ключей), **`position`**
(`0` = по этому запросу товар фактически не показывается) и **`unique_search_users`** (объём
спроса на фразу). `query_index` — сквозной номер строки в ответе; сортировка идёт по убыванию
частоты, так что это же и ранг фразы.

**Ограничения, проверенные на живых вызовах:**

- `limit_by_sku` — только `(0, 15]`, больше 15 фраз на SKU не отдаёт;
- `page_size` — только `(0, 100]`;
- **`page` считается С НУЛЯ.** Это главная ловушка метода: при `page=1` ответ приходит `200`
  с данными, но это строки `16…30` — первые `page_size` строк молча пропущены, а там как раз
  верхушка выдачи. Видно по `query_index`: `page=0` даёт `1…15`, `page=1` — `16…30`.
  Проверено 30.07.2026 при постройке сборщика; в первом прогоне на `page=1` потерялось
  3 500 строк из ~10 000, и все — самые частотные;
- `date_to` **поддерживается и ИСКЛЮЧАЮЩИЙ**: `date_to=19.07` и `date_to=20.07` дают одинаковые
  цифры за 13–19.07. Значит неделю можно брать чисто: `[понедельник, следующий понедельник)`.
  `date_from` при этом не обязан быть понедельником — произвольная дата тоже принимается;
- если `date_to` не передать, метод отдаёт накопительный период `date_from … вчера`, а не неделю;
- **глубина: 6 недель.** На 30.07.2026 отвечают недели с 22.06, с 15.06 и раньше — уже
  `400 There is no data for the specified period`.

**Запросов по товарам конкурентов в API нет.** Проверено двумя способами. Первое — шесть
вероятных путей (`/v1/analytics/competitor-queries`, `/v1/analytics/product-queries/competitors`,
`/v1/analytics/search-queries/competitors`, `/v1/analytics/category-queries`,
`/v2/analytics/product-queries`, `/v1/analytics/search-query/top`): все `404` на обоих аккаунтах.
Второе, более показательное — подстановка чужих SKU в рабочий `details`: SKU другого нашего
аккаунта и произвольные SKU с витрины Ozon дают `404 {"code": 5, "message": "not found"}`.
**Метод жёстко ограничен своими товарами.** Если такая аналитика на Pro есть, она живёт только
в UI кабинета — ⚠️ проверить это без доступа к интерфейсу я не могу.

### 9.2. Отзывы — ⛔ ЕДИНСТВЕННОЕ, ЧТО ЗАКРЫТО ПОДПИСКОЙ

Единственная группа, где аккаунты расходятся. На `oz_acc2` все четыре метода отвечают одинаково:

```json
{"code": 7, "message": "Implementation.ReviewList: ReviewList error: rpc error: code = PermissionDenied desc = not available with existing subscription"}
```

На `oz_acc1` — рабочие данные. `POST /v1/review/count`:

```json
{"total": 9855, "unprocessed": 975, "processed": 8880}
```

`POST /v1/review/list` (`limit` обязателен в диапазоне 20…100), реальная строка:

```json
{"id": "019fb204-de41-779c-8cbb-47a48fb6ae69", "sku": 1339739383, "rating": 5,
 "status": "UNPROCESSED", "text": "", "published_at": "2026-07-30T07:54:51.531266Z",
 "comments_amount": 0, "photos_amount": 0, "videos_amount": 0,
```

`POST /v1/review/info` добавляет к этому `photos`, `videos`, `likes_amount`, `dislikes_amount`.

сначала 1–3), **`is_rating_participant`** (влияет ли отзыв на рейтинг магазина, то есть стоит ли

Методы записи (`comment/create`, `change-status`) я намеренно не вызывал, чтобы не писать в

### 9.3. Цены и ценовые индексы — ✅ РАБОТАЕТ НА ОБОИХ

**`POST /v5/product/info/prices`.** Реальный блок индексов (`oz_acc1`, товар `offer_id` 0227):

```json
{"color_index": "YELLOW",
 "external_index_data":          {"min_price": 1563,  "price_index_value": 1.03, "min_price_currency": "RUB"},
 "self_marketplaces_index_data": {"min_price": 1563,  "price_index_value": 1.03, "min_price_currency": "RUB"},
 "ozon_index_data":              {"min_price": 0,     "price_index_value": 0,    "min_price_currency": "RUB"}}
```

Три индекса сразу: **`external_index_data`** — против цен на других площадках,
**`self_marketplaces_index_data`** — против наших же цен на других маркетплейсах,
**`ozon_index_data`** — против других продавцов того же товара на Ozon. Самое ценное —
**`min_price`**: это фактическая минимальная цена рынка по товару, то есть цена конкурента
в рублях. Плюс в ответе идут `commissions`, `acquiring`, `volume_weight` и `marketing_actions`,
то есть себестоимость продажи считается из одного вызова.

`ozon_index_data` пуст (нули) почти везде — по нашему ассортименту сравнения внутри Ozon нет,
работает только внешний индекс.

| | SUPER | GREEN | YELLOW | RED | без индекса | всего | есть внешний индекс |
|---|---|---|---|---|---|---|---|
| `oz_acc1` | 5 035 (42%) | 1 395 (12%) | 1 473 (12%) | **2 634 (22%)** | 1 463 (12%) | 12 000* | 10 521 |
| `oz_acc2` | 3 782 (39%) | 1 198 (12%) | 1 584 (16%) | **3 088 (32%)** | 67 (1%) | 9 719 | 9 639 |

\* по `oz_acc1` выгрузка остановлена на 12 000 карточках (лимит проб), это не весь ассортимент;
по `oz_acc2` — полная выгрузка.

**Поправка к разделу 8.** Ранее в отчёте фигурировало «47% в красной зоне» — это была оценка по
первой странице выборки. Полная выгрузка даёт **22% RED по `oz_acc1` и 32% по `oz_acc2`**.
Приоритет остаётся (2 634 и 3 088 карточек без буста — это много), но масштаб вдвое меньше
заявленного, и планировать работу надо от реальных цифр.

**`POST /v1/pricing-strategy/competitors/list`** — 30 площадок, список идентичен на обоих

Отдельных методов под ценовой индекс не существует: `/v1/product/price-index`,
`/v1/analytics/price-index`, `/v1/analytics/competitor-price`, `/v1/product/info/price-index` —
все `404` на обоих аккаунтах. Вся «подробная информация о ценах» живёт внутри `info/prices`.

### 9.4. Что это меняет в работе

1. **Отзывы — единственное, за что подписка реально платится на уровне API.** Значит движок
   автоответов на DeepSeek (ветка `eng/deepseek-answer-engine`) — не просто удобство, а способ
   отбить подписку. 975 неотвеченных и +19 за два дня: нужен ежедневный автопрогон, а не разовый.
2. **Поисковые запросы забирать пачками по 200–500 SKU и складывать к себе еженедельно.**
   Глубина у Ozon всего 5 закрытых недель, своя история — единственный способ увидеть сезонность.
   Первый отчёт из данных: `position = 0` при заметном `unique_search_users` — спрос есть, товар
   не показывают, это правки заголовка и атрибутов.
3. **`min_price` из `external_index_data` — готовая цена конкурента по 10 521 карточке.**
   Свести с маржой из `mkt_sku_economics`: где мы выше рынка и маржа позволяет — опускать до
   зелёной зоны ради буста; где не позволяет — не трогать цену, а уходить в рекламу.

## Приложение: как воспроизвести пробы

Скрипты лежат в скретчпаде сессии
(`probe_common.py`, `probe1.py` … `probe7.py`, результаты в `probe*.json`; раздел 9 — это
`probe6.py`, `probe7.py` и результаты `probe8.json`, `probe9.json`), запуск —
`/opt/mp-analytics/venv/bin/python`. Креды берутся из `/opt/mp-analytics/.env`
(`OZON_CLIENT_ID_ACC*` / `OZON_API_KEY_ACC*`, `OZON_PERF_CLIENT_ID_ACC*` / `OZON_PERF_SECRET_ACC*`).

Важно при повторе: Seller API держит **2 запроса в секунду** на клиента, при превышении
приходит `429` — между вызовами нужна пауза не меньше 1.5 с, иначе часть проб ложно выглядит
как отказ.
