# Обработка заказов МС при сбое вебхуков

Источник: прямые согласования Натальи 22.10.2026 в задаче восстановления обработки заказов;
отдельная команда сохранить эти правила в общей памяти. Это сохранение утверждённых
пользователем правил, а не автоматическое продвижение наблюдений агента.

При новом сбое получить свежее поручение и свежие заказы в согласованном статусе ожидания.
Фактический статус проверять через metadata: «Ожидает подтверждения» пользователь также
называла «Ожидает обработки». Старые списки заказов/разрешения не запускать повторно.
Штатную обработку не дублировать; фоновый аварийный процесс автоматически не включать.

## Остатки и замены

- Склад заказа сохранять. Все позиции должны физически присутствовать на этом складе
  в достаточном количестве. Приход в пути не считать наличием.
- Чужие резервы недоступны. Собственный резерв зачесть не больше количества строки:
  `stock >= need` и `stock - reserve + min(own_reserve, need) >= need`.
  Нескольким заказам один остаток не обещать: общий пул либо последовательный резерв.
- Доступный исходный товар сохранять. При отсутствии — товар **другого поставщика
  с тем же точным внешним кодом**. Ведущие нули значимы. `code` — код поставщика,
  `externalCode` — наша номенклатура. Иной внешний код без подтверждённого соответствия
  не подставлять. Архив/Брак не использовать.
- Набор определять по свежему справочнику и составу ТК `catalog/mix_data`, раскрывать
  рекурсивно по внешним кодам с сохранением количеств.
- Для набора приоритет: один поставщик **и** один бренд; затем один бренд у разных
  поставщиков; затем доступный смешанный комплект. Неподтверждённый состав не угадывать.
- Обрабатывать только полностью обеспеченный заказ. При нехватке оставить без изменений,
  подготовить список недостающих кодов. Частичную отгрузку не создавать.

## Статус и отгрузка

Сохранять склад, организацию, контрагента, сумму, скидки и НДС до копейки. При разборе
набора распределять существующую цену между компонентами; проверить округление суммы и НДС.
Готовому заказу поставить «Собирается» и плановую дату отгрузки = сегодня по МСК.
Выдержать не менее 5 минут; проверить связанные отгрузки. Корректная уже существующая
отгрузка исключает повторное создание. Не откатывать заказ с более позднего этапа.

Если документа нет — повторно проверить товары, наличие и связи; создать отгрузку
из шаблона связанного заказа: **номер = номер заказа, дата/время = текущие МСК**.
`PUT /entity/demand/new` возвращает шаблон; документ создаёт `POST /entity/demand`.
Проверять номер вместе с организацией и `customerOrder`, а не только номер глобально.
Несколько/частичные отгрузки и параллельное изменение заказа требуют отдельного разбора.

Запись сущности — одна попытка с сохранённым intent/response. После сбоя сети сначала
GET-сверка, не слепой повторный POST. Итоговый GET должен подтвердить проведение,
связь, товары/количества/цены/скидки/НДС/сумму и исходный склад.
МС возвращает даты с миллисекундами `.000`, нормализовать сравнение.

## Где взять готовую заготовку

Инструкция и ограничения: `/opt/mp-analytics/docs/MS_ORDER_RECOVERY.md`.
Основной модуль: `tools/customer_order_fresh_fulfillment_20261022.py`:
`collect` — только чтение в новый каталог; `apply` — подбор/резерв/замены/статус/дата;
`shipments` — проверка через 5 минут и создание отсутствующих документов.
Алгоритм: `tools/customer_order_stock_plan_20261022.py`; регрессии:
`tests/test_customer_order_stock_plan_20261022.py`. Старые датированные волны не переигрывать.
Ключи брать из `.env`, в архив и отчёты не включать.
Объём более ~50 изменяемых сущностей — сначала локальный skill ms-mass-change.

Доказательства: `/opt/mp-analytics/docs/reports/customer_order_stock_plan_20261022/`.
Текущее состояние сервиса хранить в `docs/BRIEF_INV.md`, не превращать эту карточку
в постоянно устаревающий отчёт о сбое.
