# Правила: перенос полей ТК → карточки МойСклад (поток prc)

Свод решений Сергея по задаче «Модель / Доп. название модели / Цвет / Чип / Ресурс (поставщика)».
Источник правил — переписка 18–20.08.2026. Реализация: `tools/prc/tc_fields.py` (заливка полей),
`tools/prc/recard.py` (архив старой + новая карточка). Меняем правило — правим ЭТОТ файл.

## 0. Общее

1. **Ключ связи** — `externalCode` карточки МС ↔ `prc_tc_model.external_code` (снимок каталога ТК,
   берём только живые строки `gone_at is null`).
2. **Один внешний код = одна модель товара.** Цвет и чип у всех карточек с одним внешним кодом
   обязаны совпадать. Артикул у них РАЗНЫЙ — это норма (у каждого поставщика свой).
3. **Работаем только с обычными карточками.** Архивные не трогаем ни по одному полю и не выносим
   в файлы на проверку (`filter=archived=false`).
4. **Внешнего кода нет в каталоге ТК → карточку не трогаем вообще**, ни по одному полю.
5. **Явное противоречие ТК ↔ название поставщика** (цвет ИЛИ чип) → поле НЕ заполняем, карточка
   идёт в файл на проверку; заполним после разбора.
6. **Запись в МС — только по явной команде.** Перед любой правкой — слепок карточки в `backups/`.
7. Файлы на проверку — XLSX в бот PRC всем участникам.

## 1. Поля

| Поле МС | Источник | Правило |
|---|---|---|
| **Модель** | ТК `title` | как есть |
| **Доп. название модели** | ТК `additional_title` | OEM-код как есть |
| **Цвет** | ТК | русские слова **строчными**; наборы — как есть; существующее значение перезаписываем |
| **Чип** | ТК | формулировки затираем; в ТК пусто → пишем **«не указан»** |
| **Ресурс (поставщика)** | название товара **поставщика** | числом; в названии нет → оставляем пусто |
| Название ВБ | — | **вне этой задачи** (там ресурс из карточки ТК, а не поставщика) |

**Цвет.** Конфликт «цвет ТК ≠ цвет в названии поставщика» → не пишем, на проверку. Проверенные
человеком расхождения — в белом списке `docs/prc_color_approved.csv` (по коду карточки), они
конфликтом больше не считаются.

**Чип.** Три вида холда, все — на проверку, поле пустым не оставляем силой:
- *в ТК нет данных, а поставщик чип в названии указал* — «не указан» НЕ пишем;
- *противоречие* — «с чипом» vs «без чипа», а также «с чипом» vs «с чипом без счётчика»;
- написания поставщиков разбирать по словарю: Blossom `W/chip` = **без** чипа; «чип безлимит» =
  чип **без счётчика**; «б/ч» = без чипа.

**Ресурс.** «N к.» = N копий, множитель ×1000 НЕ применяем: у фотобарабанов поставщики пишут
полное число («300000 к.»), проверено на базе — 1253 совпадения один-в-один с ТК и ноль случаев
«ТК = N×1000». Для справки, ресурс фотобарабанов в ТК есть: 419 моделей, медиана 40 000,
максимум 600 000.

## 2. Идентификаторы карточки

1. **Код и внешний код расходиться НЕ МОГУТ.** Код = внешний код + суффикс поставщика:
   `3588` + `sk` = `3588sk` (cs, sp, bs, ct, pl, sf, sk, wb…).
2. **`code128` принадлежит ТОВАРУ, а не карточке**: `DS` + 3 буквы товара + внешний код с нулями
   (`DSDQM0003588`). У всех карточек с одним внешним кодом он один и тот же. **Сами мы его НЕ
   генерируем** — копируем готовый у карточки с таким же внешним кодом. Такой карточки нет →
   штрихкод оставляем на ручное заведение, автоматом не выдумываем.
3. **`ean8`/`ean13`** — свои у каждой карточки, переносим со старой.
4. **Код в МС НЕ уникален** (у одного кода бывает несколько карточек). Искать карточку — по коду
   + наименованию, а если и этого мало — добирать текущим внешним кодом.

## 3. Как убирать карточку в архив

1. **Только при нулевом остатке на НАШИХ складах** (Звездный, Дисквер и прочие свои).
   «Удаленный склад» — виртуальный остаток поставщика, «Транзит» — товар в пути: **не наши штуки**.
   Есть остаток — карточку не трогаем, она идёт отдельной строкой отчёта.
2. Слепок карточки в `backups/prc_recard_<дата>/` — ДО первой правки.
3. Снимаем **артикул, код, внешний код и штрихкоды** (они уникальны и нужны новой карточке;
   МС подставит вместо внешнего кода свой случайный) и ставим `archived: true`.
4. **Архив без замены** — когда правильной модели в ТК нет вовсе. Новую не создаём: товар
   вернётся сам «новинкой» при следующем оприходовании, там его и привяжут.

## 4. Как создавать новую карточку

1. Наполнение переносим со старой: `name`, `description`, `article`, `vat`, `uom`, `country`,
   `supplier`, `productFolder`, `weight`, `volume`, `buyPrice`, `minPrice`, `salePrices`,
   `trackingType`, `paymentItemType`.
2. `externalCode` = правильный код ТК; `code` = внешний код + суффикс поставщика со старой;
   `barcodes` = ean старой + `code128` товара (п. 2.2).
3. Поля Модель / Доп. название / Цвет / Чип / Ресурс — по правилам раздела 1, уже от НОВОЙ
   карточки ТК.
3а. **Все ОСТАЛЬНЫЕ доп. поля переносим целиком** — Код поставщика, Название WB, Гарантия/Срок
   службы, Бренд, габариты, Стоп лист, Ссылка, Изображение, ячейки складов. Новая карточка —
   тот же товар, терять их нельзя (20.08.2026 первый прогон создал 19 карточек без них,
   восстановлено из слепков).
3б. **Ячейки складов сверять с соседями по внешнему коду.** У карточки, стоявшей на ЧУЖОМ коде,
   ячейка бывает от чужого товара: у 2651sf было `XEROX-03`, а у остальных карточек внешнего
   кода 2651 — `RICOH`. Чужую ячейку снимаем (`value: null`, простой PUT без поля её НЕ убирает).
4. **Порядок шагов обязателен:** слепок → освободить уникальные поля у старой и убрать её в архив
   → создать новую. Иначе МС ответит «уже занято». Если создание упало — старая карточка
   автоматически возвращается из архива со всеми полями.

## 5. Почему не правим внешний код у живой карточки

Внешний код — ключ, по которому карточка связана с ТК, площадками, оприходованиями и продажами;
правка задним числом переписывает, чем карточка была. Поэтому только архив + новая карточка
(решение Сергея 20.08.2026).
