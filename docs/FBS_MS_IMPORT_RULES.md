# Правила восстановления импорта FBS-заказов в МойСклад

Поток `inv`. Действующие решения пользователя 02–03.11.2026 и подтверждённые примеры МС.
Этот документ относится к **созданию заказов покупателей**. Обработка существующих заказов
и создание отгрузок описаны отдельно в `docs/MS_ORDER_RECOVERY.md`.

## Источники и ключ

- Только FBS Ozon, WB и Яндекс Маркета; Ozon/WB по два бизнеса, Маркет только ACC1.
- Цифровой: организация ООО «ЦИФРОВОЙ КВАДРАТ», склад «Звездный»; Дисквер:
  организация ООО «ДИСКВЭР», склад «Дисквер». Кабинет и бизнес подтверждать API,
  не выводить из одного только номера заказа.
- Один документ МС на полный `posting_number` Ozon (разделённые отправления отдельно),
  `assembly order id` WB или `businessId/campaignId/orderId` Маркета. Перед созданием
  искать полный номер МС **по всем статусам**. При нескольких совпадениях остановиться.
- Создание — только однократный POST после повторной проверки площадки, МС, цены и товара.
  До POST — журнал намерения; при таймауте сначала поиск и чтение МС, без слепого повтора.
  При частичном выполнении остановить этот заказ и сохранить состояние.
- Отменённые и уже созданные в МС заказы не импортировать. Неоплаченный
  Яндекс Маркет `UNPAID / WAITING_USER_INPUT` импортировать в статусе МС
  «Ожидает оплаты», без плановой даты отгрузки. После оплаты ранее созданный
  документ этот импортёр автоматически не переводит: он создаёт только новые.

## Товар и склад

- Внешний код из заказа МП сопоставлять по первым **четырём цифрам**: `00191 → 0019`;
  это подтверждённое пользователем правило семейной карточки. Требовать существующую
  карточку МС с этим **точным** внешним кодом; по похожему названию не сопоставлять.
- Проверять физический остаток на складе заказа: `stock - reserve`, с учётом резерва
  собственных уже созданных заказов при повторной обработке. Между новыми заказами
  не обещать одну единицу дважды. МС сам резервирует новые заказы; поле `reserve`
  в payload не передавать, затем читать фактический резерв.
- При полном наличии выбирать подтверждённый вариант поставщика с достаточным количеством.
  При нехватке собственного остатка выбирать среди карточек с достаточным доступным
  наличием на «Удаленном складе» и подтверждённой положительной текущей закупочной ценой.
  Приоритеты берутся из таблицы Dropbox от 03.11.2026 (`20261103_101748_..._photo.jpg`),
  реализация — `ops/ms_supplier_priorities.py`, связь с группами — по ID поставщика:
  - 10: Жухай; 15: отдельные юрлица «Одиссей WB» и «ТОНЕРОПТТОРГ T2»;
  - 20: Одиссей, Суперфайн (включая OEM), Изипринт, Sakura, Спринт МСК;
  - 30: Колортек, Профилайн, Булат, Кактус;
  - 40: Спринт, НВ-Принт, Юнитон, Блоссом, ВТТ.
  Внутри одного приоритета — минимальная подтверждённая цена, при равенстве — ID.
  Приоритеты рассматриваются по возрастанию числа: более низкий приоритет заменяет
  текущий выбор, если текущая цена **строго больше** дешёвой цены × 1,20.
  Процент считается от дешёвой цены; ровно 20% сохраняет высокий приоритет.
  Собственный полный физический остаток используется первым с учётом резервов.
  Строки «Микс» 999 не являются поставщиками; неизвестный ID не угадывать по имени.
- Закупочная цена — из **актуального** оприходования МС на «Удаленном складе»,
  позиция `price` в копейках. Читаются последние действующие документы **всех** групп,
  включая Sakura, без фиксированной нижней даты и без `_old`; общий digest сбрасывает
  старый снимок четырёх групп. Снимок допустим только если он существует и доказуемо
  относится к текущим оприходованиям. Поле `buyPrice` карточки может быть устаревшим.
  Нет подтверждённой цены при нехватке остатка — заказ исключить до выяснения.
- Набор раскладывать только по подтверждённому составу ТК, количество компонентов
  умножать на число наборов. Предпочитать одну пару поставщик–бренд; допустимы не более
  двух разных пар. Неизвестный состав или невозможный подбор не выдумывать.
- Если товарную часть нельзя достоверно разобрать, но есть существующая карточка МС
  с подтверждённым базовым внешним кодом, оставить исходную позицию для ручного разбора
  и поставить «Ожидает подтверждения». Если даже карточки нет — исключить заказ.
- По прямому уточнению пользователя известные наборы `6624`, `1222`, `6418` до
  восстановления состава ТК записаны цельными существующими карточками
  `6624msk`, `1222msk`, `6418msk` соответственно, без выдуманного разложения.
  Остальные позиции заказа сохраняют отдельными строками.

## Поля и суммы МС

| Поле | Правило |
| --- | --- |
| Номер | Полный устойчивый ID отправления/сборочного задания МП |
| Момент | Время создания/начала обработки МП в МСК, до минуты |
| Организация, склад | По бизнесу, как выше |
| Контрагент | Существующий общий для обоих бизнесов: «Покупатель Озон», «Покупатель ВБ», «Покупатель Маркет» |
| Проект | «Озон», «Wildberries», «Яндекс.Маркет» соответственно |
| Источник заказа | «ОЗОН», «ВБ Вайлдберриз», «Яндекс.Маркет» соответственно |
| Доставка | «Озон», «WB», «FBS Маркет» соответственно |
| Способ оплаты | «Банковской картой» |
| Ответственный | Пользовательское поле «Шаров А.», не `owner` |
| НДС | 5% в каждой позиции; `vatEnabled=true`, `vatIncluded=true`, без прибавления 5% к итогу |

- WB: сначала полная стоимость продавца `statistics.priceWithDisc`, связка по
  `rid/srid`. Пример `6175782363`: МС 1689 ₽, WB ЛК 1375 ₽. Если WB не передаёт
  строку полной цены для заказа, по отдельному уточнению пользователя брать
  текущую цену из WB Orders API (`price` в копейках при `currencyCode=643`),
  сохранив в журнале источник и факт отсутствия `priceWithDisc`. Для
  `6176952570` это 1898 ₽ из ЛК/Orders API. Не заменять доступную полную цену
  ценой покупателя.
- Ozon: исходная `old_price` и `total_discount_percent` в штатных полях цены и скидки
  МС. Не подгонять итог под округлённую Ozon `price`. Пример `27409962-0191-1`:
  МС 3816,15 ₽ против Ozon 3816 ₽.
- Маркет: сумма позиций `payment + subsidy + cashback`, без выплаты после комиссии
  и без произвольного добавления доставки. Проверять итог до копейки.
- При разложении набора распределять цену/скидку по компонентам детерминированно
  с проверкой общего итога до копейки; произвольной корректировки цены нет.

## Статус и граница действий

- Если состав подтверждён и всё количество доступно, плановая дата отгрузки
  определяет статус: дата сегодня — «Собирается», дата позже сегодня — «Подтвержден».
  Сегодняшняя граница — 15:00 МСК; для последующих дней — 16:00 МСК. При переносе
  плановой даты на следующий день заказ остаётся в «Подтвержден».
- При неполном наличии или неподтверждённой товарной части: «Ожидает подтверждения»,
  плановую дату не заполнять.
- Импорт создаёт **только customerorder**. Demand/отгрузку делает отдельный инструмент;
  статусы Ozon/Маркета и поставки WB импорт не меняет. Массовые партии — только после
  ручной проверки тестов и в согласованном размере.
- По прямой команде пользователя 02.11.2026 регулярный импорт новых заказов запускается
  раз в 30 минут таймером `fbs-ms-import.timer`. Каждый проход перечитывает площадки
  с перекрытием курсора, сверяет неизвестные номера с МС независимо от статуса,
  создаёт не более пяти заказов и продвигает курсор только после разрешения
  всей очереди окна. Журнал намерения и API-ответа обязателен для каждого POST.
- Сразу после успешного импорта вызывается статусный шаг только для ещё
  «Ожидает подтверждения». Он не создаёт отгрузки и не меняет уже обработанные
  документы. Полное физическое наличие с учётом резервов → «Подтвержден»;
  нехватка при доказанном выборе карточки по закупочной цене → «Неукомплектован»;
  прочие варианты остаются без изменений. Плановые даты и журнал этого шага —
  `docs/reports/fbs_ms_recovery_20261102/SCHEDULED_IMPORT.md`.

## Состояние временного VPS

`CARTRIDGE_API_KEY` и локальный `DATABASE_URL` отсутствуют. Текущий справочник составов
ТК недоступен; обычный товар нельзя объявлять набором или не-набором по одному названию.
Тестовые импорты и документы восстановительной партии создавались в «Ожидает подтверждения»
для ручного разбора по согласованному правилу; сотрудники затем могли менять их статусы.
Ночной файл со свежими ценами в доступном
проекте не найден; `buyPrice` карточек расходится с текущими оприходованиями для части SKU.

### Обновление 02.11.2026: подключён справочник наборов

Локальный `set_cost` теперь содержит подтверждённые составы ТК, включая
вложенные наборы. Загрузчик читает компоненты по точному базовому коду,
рекурсивно разворачивает вложенный состав и умножает количества на число
наборов в заказе. Для производной карточки требуется явное подтверждение,
что она обозначает набор; неоднозначная производная остаётся на ручной разбор.

Для полного состава сначала ищется план из имеющихся компонентов на складе
заказа, затем недостающие карточки с наличием на «Удаленном складе» и
подтверждённой текущей ценой оприходования. Предпочитается одна пара
поставщик–бренд, допускается не более двух; внутри допустимого плана
применяются приоритеты таблицы и порог 20% по стоимости закупаемого состава
при одинаковой обеспеченности собственным остатком и числе пар. Собственный
и чужие резервы учитываются. Локальное обещание остатка передаётся между
заказами одного прохода, пока МС создаёт свой резерв.

Стоимость набора распределяется поровну по физическим единицам компонентов,
с сохранением исходной общей цены, процента скидки, НДС 5% и итога после
скидки до копейки. Если целый состав, наличие или денежное распределение
не подтверждены, исходная существующая карточка остаётся в заказе для
ручного разбора в статусе «Ожидает подтверждения».

После создания отдельный штатный статусный шаг проверяет все компоненты
заказа и собственные резервы. Полное наличие → «Подтвержден» и согласованная
плановая дата; нехватка при ценовом выборе → «Неукомплектован» и дата по
текущему правилу. Он не создаёт отгрузку и не меняет статусы площадок.
Старая запись о недоступности `CARTRIDGE_API_KEY` выше относится к началу
восстановления; на текущем VPS справочник доступен.

### Обновление 03.11.2026: доказательство выбора поставщика

Новые журналы содержат `selection_policy=supplier-priority-20pct-v1`, `supplier_id`,
числовой `priority`, `supplier_available` и `stock_store_id`. Перед созданием заказа
повторно проверяются состав/наличие и digest оприходований. Локальные обещания
остатка поставщика передаются между обычными товарами и компонентами наборов.
Статусный шаг не перечитывает остатки: принимает сохранённое доказательство,
проверяет ID/приоритет/цену и количество; для повторных строк учитывает сумму.
Старые журналы без версии остаются совместимыми по прежним tier1–3.
Неверная новая версия или неполное новое доказательство не откатываются к tier.

### Обновление 03.11.2026: наборы Дисквера с производными артикулами

Для `acc2` артикул вида `<4-значный код><8 заглавных букв/цифр>` с хотя бы
одной буквой в суффиксе считается копией набора только при полном подтверждённом
составе ТК и единственной существующей неархивной карточке `<код>dsk` с точно
тем же внешним кодом. Слова «набор»/«комплект» в названии не требуются:
на площадке такие комплекты называются «Картриджи». Существующая точная карточка
обычного товара остаётся противоречием и запрещает такое распознавание.
Правило не распространяется на `acc1`, числовые и произвольные суффиксы.
Далее используется тот же `_kit_lines`: полный состав, текущие складские остатки,
приоритеты поставщиков и максимум две пары, точное распределение цены/скидки/НДС,
затем штатное решение статуса и даты. При отсутствии полного подбора — ручной разбор.
