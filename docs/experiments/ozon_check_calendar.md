# Календарь сверок экспериментов Ozon (только чтение, НИЧЕГО не включено)

Расписания нет: ни cron, ни systemd-таймера под эти команды не заведено и заводить не нужно —
каждая строка запускается руками в назначенный день. Все команды только читают БД, ни одна
не ходит во внешние API и не меняет ставки. Каждый прогон сам сохраняет отчёт с датой в
`docs/reports/`, повторный запуск в тот же день перезаписывает свой файл и ничего больше.

| дата | что проверяем | команда | куда ляжет отчёт |
|---|---|---|---|
| 20.08 | первый корректный снимок состава групп после возврата | `venv/bin/python tools/ozon_exp_eval.py snapshot --exp E8` | `docs/experiments/cohorts/E8_*_2026-08-20.csv` |
| 21–24.08 | G6: не задавил ли возвращённый хвост ядро по бюджету и показам | `venv/bin/python tools/ozon_exp_eval.py g6` (ежедневно) | `docs/reports/ozon_g6_<день>.md` |
| 26.08 | E6 — acc2 после снятия и понижения ставок | `venv/bin/python tools/ozon_exp_eval.py eval --exp E6` | `docs/reports/ozon_exp_E6_eval_<день>.md` |
| 02.09 | E7 — возвращённые конвертеры (контроля нет → только описание) | `venv/bin/python tools/ozon_exp_eval.py eval --exp E7` | `docs/reports/ozon_exp_E7_eval_<день>.md` |
| 08.09 | E5 — core_push против core_control | `venv/bin/python tools/ozon_exp_eval.py eval --exp E5` | `docs/reports/ozon_exp_E5_eval_<день>.md` |
| 09.09 | E8 — A/B возврата волны 1 | `venv/bin/python tools/ozon_exp_eval.py eval --exp E8` | `docs/reports/ozon_exp_E8_eval_<день>.md` |

Разрезы оценки: по умолчанию `--mode itt` — назначенный SKU остаётся в своей группе,
даже если площадка не приняла действие; `--mode pp` (per-protocol) только как вторичный
разрез, в отчёте ITT он и так печатается сравнительной таблицей. Переносить назначенный
SKU в другую группу нельзя ни в одном разрезе.

Пороги G6 (только сообщения, автоостановки нет):
доля расхода хвоста E8-A от расхода аккаунта — YELLOW >15 %, RED >25 %;
показы ядра к baseline — YELLOW <90 %, RED <70 %. Порог 35 % отменён: исторически
хвост съедал 32 % бюджета, то есть худший известный случай проходил бы как норма.

Два ядра считаются раздельно и не смешиваются:
`E5_CORE_SAMPLE` — 40 SKU выборки эксперимента E5 (не ядро аккаунта);
`ACCOUNT_STABLE_CORE` — широкая когорта acc1, определённая только по данным до 19.08
(`docs/experiments/cohorts/ACCOUNT_STABLE_CORE_2026-08-20.csv`, состав заморожен).
Пересобрать состав можно только явно: `... ozon_exp_eval.py build-core --force`.

Полезное вне календаря:
`... ozon_exp_eval.py list` — состояние всех экспериментов и даты сверок;
`... ozon_exp_eval.py balance --exp E5|E6|E8` — сопоставимость групп до вмешательства;
`... ozon_exp_eval.py eval --exp E8 --as-of 2026-09-02` — оценка по данным на прошлую дату.

Условия, при которых прогон не даёт вердикта (это норма, а не поломка):
окно короче полной недели → `NO_SIGNAL`; заказов в treatment меньше 10 → `NO_SIGNAL`;
у эксперимента нет контроля (E7) → `NO_CAUSAL_CLAIM`. Прибыль не считается нигде:
`BLOCKED_BY_CANONICAL_MARGIN`, денежный итог называется «выручка минус расход».

Витрина `mkt_ozon_ads_sku_daily` за день N приезжает на следующее утро (~09:2x UTC),
поэтому оценка по умолчанию идёт «на вчера». Запускать проверку раньше полудня по Москве
смысла нет — вчерашние конвертеры будут выглядеть нулевыми.
