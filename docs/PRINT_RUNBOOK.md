## Пользователи и организации

Вход `print` видит Цифровой и Дисквер. Отдельный вход `tolkachev`
видит только Дисквер (oz_acc2, wb_acc2) на той же странице; она занимает
один столбец во всю ширину. Учётные данные tolkachev хранятся только в
`.private/print_web_access/tolkachev/.env`, вне Git. Они переданы владельцу
через Dropbox-бота для самостоятельной передачи сотруднику. Для проверки
другого входа удобно использовать приватное окно браузера.

Область доступа — `print_service/access.py`; проверяется для страницы,
списка заказов, счётчиков, заданий, готовых пар, запросов формирования
и скачивания. Прямой URL чужой пары не даёт скачать PDF. Неизвестные
пользователи в отдельном приложении запрещены; одного добавления хеша
в Basic Auth недостаточно, нужно явно назначить область доступа.

Caddy обязан перезаписывать X-Pult-User именем вошедшего пользователя;
входящий заголовок клиента не является удостоверением личности.
Отдельное приложение слушает только loopback 8095, без этого заголовка
известного пользователя API/страница отвечают 403. Для внутренних
диагностических GET с сервера указывать X-Pult-User: print. Публичный
доступ проверять через HTTPS с реальными учётными данными и тестом
невозможности подменить этот заголовок.

Синхронизация и очередь общие. Новый пользователь не получает отдельного
учёта уже сформированных пар; повторное открытие своих готовых файлов
идёт из прежнего хранилища. При диагностике прав не нажимать действующий
счётчик: положительные действия и скачивание между организациями
проверяются тестами во временной схеме, с сохранёнными тестовыми PDF.

## Поведение

Служба синхронизирует заказы каждые 30 минут и при смене даты МСК.
Во время обновления видны этап, число обработанных отправлений и таймер;
список заменяется после полного завершения. Контрольный запуск 05.11:
128 заказов за 33 с (предыдущий последовательный запуск: 124 за 93 с).
Время зависит от числа заказов и ответа площадок. Ozon posting/get
проверяется в 4 потока с ограничением до 4 запросов/с на кабинет;
прочие методы этикеток сохраняют прежний бюджет. Свежесть не заменяется
кешем направлений. Прогресс — необязательные закрытые JSON-файлы
`PRINT_DATA_ROOT/sync_progress/`, привязанные к ID задания; не содержат
учётных данных. Они не участвуют в учёте готовых пар.

При ошибке отдельного HTTP-запроса через 15 с страница сообщает о ней
и продолжает проверять статус; это не предел длительности самой
синхронизации. Перед повторным действием учитывать, что задание могло
уже поступить на сервер. Активная синхронизация в очереди одна.
Частоту запросов Ozon выбранную для печати держать ниже общего бюджета
Client-Id с учётом остальных интеграций. Справка площадки:
https://dev.ozon.ru/community/2373-HTTP-429-na-finansovykh-metodakh-Seller-API-pri-redkikh-zaprosakh/

Кнопка запускает ту же синхронизацию. GET страницы и синхронизация не
экспортируют товарные чеки. После успешного обновления отдельный слот
worker заранее получает недостающие этикетки; список публикуется сразу,
полученные ЭТ постепенно отмечаются галочками. После перезапуска worker
продолжает последний актуальный снимок. Ошибка одной этикетки не мешает
обновлению или остальным заказам; повторная попытка — на следующей
синхронизации. Запрошенные пары формируются в собственном слоте.
Если ранее была ошибка доступности ЭТ, свежая успешная проверка того же
заказа/отгрузки снимает именно её из отображения, сохраняя историю.
Валидный кеш при такой ошибке не заменяет повторную проверку статуса МП.
Более новая ошибка и ошибки ТЧ не снимаются успешной загрузкой ЭТ.

Фоновая загрузка использует тот же закрытый label cache и блокировку
заказа, что подготовка по клику, и не создаёт ТЧ/пары/claims, не уменьшает
счётчик и не меняет отметку печати МС. Берутся заказы без своих claims;
готовые пары и корректно сохранённые этикетки
не запрашиваются повторно. Штатные лимиты API и защита uncertain intent
сохранены. Закрытые ошибки загрузок — PRINT_DATA_ROOT/errors/.

Крестик в колонке ТЧ означает отсутствие единственной связанной отгрузки
МС. Серые часы — отгрузка есть, ТЧ будет получен при формировании файлов.
Зелёная галочка означает фактически полученный документ. В «Готовности»:
«Готово к печати» — есть отгрузка и получена этикетка; «Не готов ТЧ»,
«Не готова ЭТ», «Не готовы ТЧ и ЭТ» — указано, чего не хватает.
Другая блокирующая ошибка тоже не помечается как готовность. При
подготовке показано «Готовится», у опубликованной пары «Файлы готовы».
ТЧ выгружается
только после клика на счётчик или отдельную кнопку ТЧ + ЭТ в строке;
в этот момент МС может установить printed. До клика он остаётся без
изменений со стороны страницы. Нижняя таблица содержит все заказы пяти
кабинетов: «Собирается», плановая дата отгрузки сегодня по Москве.
Под номером каждого заказа показан статус МС из последней синхронизации,
например «МС: Собирается», независимо от наличия связанной отгрузки.
Текст ошибки отсутствующей/неоднозначной отгрузки в строке скрыт;
проверка связи и блокировка формирования остаются. Прочие ошибки
продолжают показываться, все заказы остаются в списке.

Список заказов и «Готовые файлы» разделены по организациям: Цифровой
слева, Дисквер справа. На узком экране они идут друг под другом. Поиск
и фильтр статусов применяются к обеим таблицам заказов; готовые пары
и задания подготовки отображаются у соответствующей организации.

05.11.2026 по решению пользователя сверка с `printed` МС отключена.
Счётчики ведут только собственный учёт готовых пар. Если оба файла на
нашей странице ещё не опубликованы, заказ входит в счётчик независимо
от отметок заказа или отгрузки МС. Пометки и фильтра «Напечатано в МС»
на странице нет; старые отметки не используются и в резервировании.
Отметки в МС этим решением не сбрасываются. ТЧ + ЭТ можно сформировать
отдельно в строке; у готового заказа там ссылки на сохранённые файлы.

Счётчик фиксирует запрошенную пачку. Каждый заказ проверяется отдельно:
проблемные исключаются и остаются в счётчике с номером и причиной ошибки,
для остальных формируются ТЧ и ЭТ в одном и том же исходном порядке.
Это касается и заранее известных ошибок/отсутствующей отгрузки.
Исключения сохраняются как failed child jobs с parent-связью; исходный
состав запроса и причины сохраняются в metadata родительского задания.
В карточке файлов показано «Не вошло: N». Если не готов никто, пустой
пары нет, все заказы остаются в счётчике. После сохранения обоих PDF
только включённые в них заказы исключаются, строки становятся зелёными. Подтверждения
кладовщика нет. Это учёт сформированных пар, а не физических действий
принтера. Готовые файлы открываются из локального хранилища без API.
Для отдельного явного списка из файла внутренний Queue.reserve_orders
собирает одну пару через несколько счётчиков одного аккаунта. Порядок
списка общий для ТЧ/ЭТ; обязательны свежий снимок, одна организация,
отсутствие чужих claims/активных групп и уникальный request_key. Остальные
заказы групп не добавляются. Готовые включённые заказы списываются
каждый из своего исходного счётчика. Выборка защищена теми же правами.
Отдельная печать заказа резервирует только его; остальные заказы не
включаются. Повторное открытие одного заказа из общей пары извлекает
его страницы по сохранённому манифесту, без экспорта МС, запросов
этикеток, новой пары и повторного списания счётчика. Исходные размеры
и содержимое PDF этикеток сохраняются. Права организации проверяются
также для отдельных маршрутов /api/print/orders/{id}/pair и
/api/print/orders/{id}/files/{receipts|labels}.
Во время подготовки общей пары заказ остаётся учтённым в строящемся
счётчике до готовности обоих PDF.
Если один заказ не подготовился, полученные документы сохраняются,
остальные продолжают формироваться. Исключённые строки остаются красными,
причина показана в строке и в ошибках; у них можно повторить подготовку.
При общем сбое публикации полученные документы также сохраняются. Неясный
результат export МС требует разбора сохранённого журнала: повторный
экспорт автоматически запрещён. Известный URL скачивания возобновляется.

Ошибки в «Готовых файлах» содержат номер конкретного заказа, на котором
прервана подготовка. Если старое задание не сохранило этот контекст или
ошибка возникла при сборке общей пары, показаны номера его актуальных
участников. Сообщение скрывается после готовности пары или выхода заказа
из сегодняшнего фильтра. Отметка печати в МС на сообщение не влияет.
Во время новой подготовки старая ошибка не показывается. Повторные
ошибки одного заказа сворачиваются до последней. Это фильтр отображения:
история заданий и готовые файлы сохраняются без повторных экспортов.

ТЧ — A4. Этикетки сохраняют исходные размеры, страницы и содержимое.
Количество больше 1 выделяется жирным. Рамка используется, если есть
место без наложения на соседние ячейки; иначе остаётся только жирный текст.
Нехватка места для рамки не блокирует заказ.
Повтор одного артикула в нескольких строках ТЧ допустим. Проверяется
сумма количеств этих строк против отгрузки; выделяется реальное количество
каждой строки больше 1. Строки МС не объединяются и не умножаются на
суммарное количество. Повтор кода в описании не считается ещё одной строкой.
PDF площадки не масштабируются; PNG WB 580×400 вложен в PDF 58×40 мм
без изменения пикселей. Неожиданный формат блокирует пару.

У некоторых исходных QR-этикеток Ozon поле scanit пусто. Если оба поля
barcodes.upper_barcode/lower_barcode содержат один и тот же допустимый
код, адаптер использует его и для cache этикетки, и для кода ТЧ. На
реальной этикетке этот код проверен декодированием QR. Непустой scanit
не заменяется; разные/неполные коды не угадываются из номера заказа.
Исходные ответы API и байты PDF сохраняются без изменений.

Сырые ТЧ и export journals хранятся отдельно от render profile, в
orders/.../receipt_sources/<hash>. Смена оформления не запускает новый
экспорт тех же данных. Старые исходники импортируются только при точном
совпадении прежнего source_key и order/demand; неопределённый export
нельзя повторять и после смены оформления.

## Перед включением

В тестовом режиме экспорт разрешён только для отгрузок с
`printed=true`, проверенным свежим GET. Для боевой выгрузки новых
чеков согласование получено 03.11.2026: API МС может поставить отгрузке `printed=true`.
Обратного сброса флага нет. Статусы заказов МС и площадок не меняются.

После согласования перенести проверенные изменения из worktree в основной
чекаут обычной процедурой проекта, установить `requirements.txt` в venv.
Проверить наличие `pdftotext` и шрифтов DejaVu. Секреты берутся из `.env`.
До записи проверить состояние (команда ничего не устанавливает):

```bash
./venv/bin/python -B -m ops.print_setup
```

Затем отдельным явным действием установить только собственную схему:

```bash
./venv/bin/python -B -m ops.print_setup --install
```

Шаблон службы — `web/mp-print-worker.service`. Его значение
`PRINT_EXPORT_UNPRINTED=0` сохраняет тестовый guard; для согласованной
боевой выгрузки установить `1` в конфигурации службы. Проверить переменные
`PRINT_SCHEMA` и `PRINT_DATA_ROOT`, затем установить unit, выполнить
`systemctl daemon-reload`, включить `mp-print-worker` и перезапустить
`mp-dashboard`. При развёртывании 03.11.2026 эти команды выполнены после согласования.

Проверить heartbeat, полную синхронизацию и отображение всех пяти кабинетов.
Согласовать первую реальную пару со складом и выполнить физическую проверку
сканирования. Исходные этикетки печатать в масштабе 100%.
Начальная история содержит только пары этой системы; прежние распечатки
из других программ автоматически восстановить по флагу МС нельзя.
Момент перехода со старого способа печати согласовать со складом.

## Эксплуатация

Данные — `PRINT_DATA_ROOT`: исходные ответы API, документы отдельных
заказов, неизменяемые пары с manifest и контрольными суммами. Каталог
закрытый, права файлов 0600; не публиковать его как статику. БД в схеме
`PRINT_SCHEMA` хранит очередь, историю, состав пар и пути к файлам.
Резервировать БД и этот каталог вместе; не удалять историю/claims для
обнуления счётчиков. Общие финансовые таблицы печать не меняет.

Один процесс защищён advisory lock; после перезапуска восстанавливает
незавершённую работу. Синхронизация и подготовка пары выполняются в двух
отдельных слотах. При остановленной службе новые задания запрещены,
готовые файлы доступны. Остановка `mp-print-worker` прекращает новые
синхронизации/подготовку; уже сохранённые данные сохраняются.

## Локальная проверка

```bash
./venv/bin/python -B -m unittest discover -s tests -p 'test_print_*.py'
```

Тесты очереди используют свои временные `print_test_*` схемы и удаляют их.
`ops.print_local_preview` использует сохранённые проверенные образцы,
собственную временную схему и loopback-порт, без внешних API. Даты/статусы
образцов адаптированы только для демонстрации; на странице есть отметка.
Ctrl+C завершает сервер и удаляет его схему. Нужны приватные образцы:

```bash
./venv/bin/python -B -m ops.print_local_preview \
  --source /opt/mp-analytics/.private/print_handoff_20261103 \
  --output /opt/mp-analytics/.private/print_handoff_20261103/ui-preview
```
