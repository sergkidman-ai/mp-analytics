# Задача wb4c: обновить API финансового сборщика Ozon и проверить остальные вызовы

Дата: 20.10.2026. Передано по прямому поручению пользователя из сессии сторожа.
Поручение: «поправить финансовый сборщик на новый метод апи. и пусть проверит
где еще нужно поменять метод».

## Цель и результат

Исправить получение постингов Ozon в финансовом сборщике, устранить бесконечные
повторы на 429, проверить остальные используемые методы Ozon на устаревание.
Сохранить совместимость raw-данных и downstream-финансовых расчётов.
Это поручение на исправление, а не только диагностику.
Текущую работу wb4c не отменяет; выбрать безопасную последовательность задач.

Начать с актуальных AGENTS.md, CLAUDE.md, своего брифа и правил fin/ozon/data-layer.
Общий checkout /opt/mp-analytics остаётся на main, чужие изменения сохранить.
Работать в собственном worktree/ветке; не редактировать worktree сторожа.

## Уже проверенные факты

- collectors/ozon_postings.py: FBS_URL=/v3/posting/fbs/list,
  FBO_URL=/v2/posting/fbo/list. FBS использует offset, result.postings.
- 20.10 v3 FBS list возвращал 429/code=8, Retry-After=0, remaining=0.
  Существующий цикл ждёт 1 секунду и повторяет запрос без предела попыток.
- Тем же ключом OZON_API_KEY_ACC2 актуальный /v4/posting/fbs/list вернул 200:
  две страницы по 10, 20 уникальных отправлений, без дублей.
  has_next=true и cursor — в корне; cursor нужно передавать точно из ответа.
- products.price в v4 — объект {amount,currency}; старый v3 get отдаёт строку.
  Нельзя просто заменить URL, оставив старый разбор.
- Проба filter.status=[awaiting_packaging,awaiting_deliver] НЕ сузила ответ:
  вернулись delivering. Проба sort_dir=desc вернула ascending-последовательность.
  Эти параметры не считать проверенными; уточнить актуальную схему и проверить.
- FBS get /v3/posting/fbs/get работает. Не менять все версии «по номеру»:
  у каждого метода отдельный жизненный цикл.
- Официальное объявление Ozon 10.07.2026, отключение с 31.08:
  FBS list v3→v4; FBS unfulfilled/list v3→v4; FBO list v2→v3.
  https://t.me/OzonSellerAPI/666
  https://t.me/s/OzonSellerAPI?before=669
- Живой сборщик run_daily PID 2681936 при нашей проверке был запущен
  19.10 19:07 UTC; последний этап — постинги oz_acc2 за октябрь.
  mtime run_daily.log был 20.10 11:51:34 UTC. Ранее три 502 от старого FBS list.
  Утренний запуск пропущен из-за flock. PID/состояние обязательно перепроверить.
  Мы процесс не останавливали и рабочий код не меняли.

## Работы

1. Проверить актуальную документацию и контракт FBS v4/FBO v3, включая страницы,
   фильтры, направление сортировки, цены, статусы, валюты и financial_data.
2. Обновить финансовый collector. Проверять наличие обязательных полей ответа:
   отсутствие postings/result не превращать молча в успешную пустую выборку.
   Курсорная пагинация: повтор курсора/зацикливание, дубли, последняя страница,
   постоянные границы окна. Для FBO не предполагать одинаковую схему с FBS.
3. Ограничить количество/суммарное время повторов 429 и временных 5xx, учитывать
   Retry-After, добавлять возрастающую паузу. Retry-After=0 не создаёт быстрый
   бесконечный цикл. Ошибка страницы не должна записывать неполное окно как полное.
   Учитывать существующие гейты run_daily, сохраняющие витрины при сбое источника.
4. Проверить весь repo: collectors, adapters, reports, ops, tools, cron/services,
   notebooks/one-off scripts при наличии, тесты и документацию с инструкциями запуска.
   Для каждого устаревшего вызова указать путь, рабочий/исторический статус,
   замену, затронутые потребители и фактическое исправление.
   Сопоставить реальные вызовы с официальным списком deprecated; не ограничиваться
   тремя известными методами. Архивы не запускать и не переписывать без пользы.
   Пересекающиеся изменения в акциях/маркетинге согласовать со своей текущей работой.
5. Проверить потребителей raw_ozon_posting: shipment_guard/adapters.py,
   финансовые адаптеры/отчёты и другие обращения к payload.products.price,
   payload.financial_data. Новые и старые сохранённые payload должны обрабатываться
   явно по схеме/версии. Сырьё сохранять как есть; нормализацию отделить.
   Цена через Decimal, currency обязательна; qty учитывать один раз.
   Не менять смысл выручки/баллов/компенсаций и финансовые правила.
6. Тесты: несколько страниц FBS, пустое окно, повтор курсора, неправильная схема,
   новые/старые цены, валюты, 429 с нулевым Retry-After, временные 5xx и предел
   повторов, ошибка после первой страницы, FBO. Узкий live read-only smoke
   на oz_acc2, затем проверить доступность второго кабинета без массовой выгрузки.
7. Оценить восстановление текущего финансового прогона после исправления.
   Перед любым воздействием перепроверить процесс и текущую фазу/транзакции.
   Не запускать полный run_daily или пересборку исторических витрин ради теста.
   Подготовить безопасное внедрение по правилам проекта с сохранением чужих правок.
8. Отчитаться: исправленные файлы/методы, результаты тестов и live smoke,
   совместимость финансовых данных, что ещё осталось/требует отдельного владельца,
   состояние текущего прогона и внедрения.

## Границы

- Не менять цены, акции, статусы заказов или документы МС/МП.
- Не перевыпускать токены и не менять действующие подписки/адреса вебхуков.
- Не включать сторожа заказов и его уведомления: это другой поток.
- Новый сторож использует выделенный SHIPMENT_GUARD_MS_TOKEN; не трогать его.
- Не применять целиком коммиты сторожа к main; диагностические файлы — справочно.
- Никаких секретов в выводе, коммитах или сообщениях.
