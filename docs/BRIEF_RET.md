## Задача

Отдельный Telegram-бот раз в день присылает полный список висящих FBS-возвратов по
Ozon / Яндекс / WB: сгруппировано по ПВЗ, с адресом, составом возврата, сроком забрать
и штрихкодом получения (картинкой — там, где площадка его отдаёт).

## Правила классификации — только в `returns_bot/pending.py`

Стадии `pickup` (забрать) / `transit` (едет) / `attention` (потерян/утилизация) / `closed`.
WB: статус приходит русской строкой, гейт — `isStatusActive` (0 = история при любом статусе);
`Готов к выдаче` → pickup, `В пути в пвз` → transit, живой неизвестный статус → `attention`
(в сводке не виден, `SHOW_STAGES` — только pickup; заметить можно прогоном `collect`).
Ozon `Utilized`/`WriteOff` и Яндекс `EXPIRED`/`RECEIVED_FOR_EXPROPRIATION` — **closed**:
товара уже нет, действия невозможны, в ежедневный список они шум. Правка правил — только здесь.

**Что бот показывает — `pending.SHOW_STAGES`, сейчас только `pickup`** (решение Сергея 02.08.2026).
Убраны из показа: «в пути» (Едет к вам / Едет на склад Ozon / Ожидает отправки / Привезёт курьер)
и «разобраться» (Ищем товар / потерян / готовится к утилизации) — действия по ним всё равно нет.
**Собираем и храним по-прежнему всё**, вернуть показ = добавить стадию в `SHOW_STAGES`.
«Привезёт курьер» (`ReturningToSellerByCourier`) Сергей отложил «возможно, понадобится позже» —
возвращать отдельной стадией, а не всем блоком `transit`.

**Фаза 4 — WB (02.08.2026), подключён.** Возвраты WB живут **в Аналитике**, а не в Marketplace API:
`GET seller-analytics-api /api/v1/analytics/goods-return`, **базовый** токен (скоуп «Аналитика»).
`returns_bot/sources/wb.py`. Окно ≤31 дня по `orderDt` → тянем тремя окнами назад (93 дня),
дедуп по `shkId`. Ключ возврата = `shkId` (физическое место), номер в сводке = `stickerId`.

Тупики, чтобы не искать заново: `/api/v3/supplies/returns` **не существует** — слово `returns`
подставляется как `{supplyId}`, отсюда 400 `IncorrectParameter` при любых параметрах (контроль:
`/api/v3/supplies/zzz-not-a-supply` даёт ту же ошибку). Прежняя 401 «token scope not allowed»
была ложным следом: авторизация WB отвечает ДО маршрутизации. `returns-api /api/v1/claims` —
заявки покупателей на брак, без адреса/срока/стикера, для забора непригодно (ближе к `rev`).
Выданные `WB_TOKEN_RETURNS_ACC1/2` (маска `2064` = «Маркетплейс»+«Возвраты», до 31.01.2027)
в итоге **не нужны** — лежат в `.env` про запас. Базовый токен не трогали.
Открытые копии токенов из `dropbox/*.txt` удалены 02.08.2026 (`shred`), строки вычищены из
`dropbox/index.log`; в `dropbox/` JWT больше нет.

**Номер в сводке (04.08.2026, `e0c374d` в main).** Печатаем `orderId` — это номер сборочного
задания WB, он же **имя отгрузки в МойСкладе** (проверено живьём: orderId 5275090801 = demand
5275090801 от 06.07 на 2152 ₽; он же `assembly_id` в `raw_wb_report`). Стикер `shkId`/`stickerId`
(например 55828115139) в МС не ищется — это ШК наклейки на коробке; **строку «штрихкод» убрали
по всем площадкам** (для получения не нужна; PNG-код получения Ozon по-прежнему картинкой).
`orderId=0` бывает ровно у возвратов **со склада ВБ** — «Возврат брака» (37), «неверного
вложения» (27), «по инициативе продавца» (5); у «приехал по МП» (81, наш склад) он есть всегда.
Такие строки помечаются «ФБО (со склада ВБ), номера заказа нет» + тип возврата, чтобы склад не
искал несуществующий заказ. Метка — `render._number_label`.

Чего WB не даёт: **срока «забрать до»** (`expiredDt` у живых строк пуст) и **картинки штрихкода**
(аналога `giveout/get-png` нет). Стикер печатаем текстом.

**Код выдачи в ПВЗ у WB — из ПОКУПАТЕЛЬСКОГО приложения, не из API** (проверено 02.08.2026 по
официальной инструкции WB Partners «Возврат товара со склада Wildberries продавцу»): «Когда у
возврата будет статус „Готов к выдаче“, его можно будет забрать по QR-коду из приложения», профиль
на wildberries.ru должен принадлежать владельцу кабинета WB Partners, возврат виден в его разделе
«Заказы». То есть продавец получает свой товар как обычный покупатель. Публичного покупательского
API у WB нет; `shkId`/`stickerId`/`srid` из `goods-return` — идентификаторы коробки и наклейки, а
НЕ код выдачи, свой QR из них не рисуем (см. запреты). Вывод: бот отвечает на «что и где лежит»,
код открывает человек в приложении WB — потолок автоматизации по WB здесь.

**Фаза 5 — две дыры по Ozon (06.08.2026).** `/v1/returns/list` отдаёт ТОЛЬКО схемы Fbs и Fbo;
ни Real-FBS, ни коробки вывоза со склада в нём нет (проверено живьём: возврат 100264955 в списке
отсутствует). Отсюда два новых источника, оба пишутся в `platform = 'ozon'`:

- `sources/ozon_rfbs.py` — **Real-FBS (экспресс)**: `POST /v2/returns/rfbs/list`
  с `filter.group_state = ["delivering"]` (у acc1 64 строки, у acc2 10 — влезает в один запрос),
  дальше `POST /v2/returns/rfbs/get` по строкам стадий pickup/transit ради
  **`ru_post_tracking_number`** — трека Почты России, по которому возврат и получают в отделении.
  В списке трека нет, только в деталях. `offset`/`last_id` в списке НЕ работают (limit 100 и 1000
  дают одно и то же), фильтр `state` строкой молча игнорируется — держаться `group_state`.
  Статусы: `ArrivedAtReturnPlace` = «В пункте выдачи» → pickup; `MovingToYou`/`WaitingShipment`
  → transit; адреса точки API не даёт вовсе (только `warehouse_id`), в сводке точка —
  «Почтой России», ехать по треку.
- `sources/ozon_removal.py` — **вывоз со склада FBO**: `POST /v1/removal/from-stock/list`
  (+ `from-supply`, у нас пусто). Окно обязательное, ≤3 месяцев, YYYY-MM-DD; тянем 2 окна = полгода;
  пагинация строковым `last_id` из ответа (`offset` в теле есть, но не работает; `last_id: 0`
  числом = 400). Единица показа — **коробка** (`box_id`), не заявка: в заявке их несколько, едут
  из разных РФЦ порознь. Ключ строки `rm-<заявка>-<коробка>`, в сводке печатается номер заявки
  (по нему ищут в ЛК: FBO → Вывоз и утилизация). Стадию решает `box_state`: «В пункте выдачи» →
  pickup, «В пути»/«На СЦ»/пусто → transit, «Получена»/«Утилизирована»/«Компенсировано продавцу»
  → closed; `return_state` («Можно забирать всё/часть») — только подпорка, у одной заявки часть
  коробок уже забрана. Срока «забрать до» в выдаче нет (`given_out_date`/`utilization_date`
  пустые даже у полученных), цены товара тоже.

Миграция `301_mp_returns_source_track.sql`: `mp_returns.source` (ozon | ozon_rfbs | ozon_removal |
yandex | wb) и `mp_returns.track_number`. **`source` обязателен**: пометка «пропал из выдачи»
(`gone_at`) теперь считается в пределах одного источника, иначе упавший или незапущенный
(`--only`) источник Ozon гасил бы живые строки двух соседних.

Дисквэр 1) и 2 возврата Почтой России (по одному на юрлицо, с треком). Штрихкод получения Ozon

## Запреты

- Только **чтение** API площадок. Ничего не согласовываем, не оспариваем, не заявляем на вывоз,
  в кабинеты не пишем.
- Витрины fin (`margin_by_sku`, `ms_return_cogs`) не трогаем: там деньги, здесь физика.
- **Свой QR из номера возврата не рисуем.** Только коды, которые площадка отдала сама
  (Ozon PNG/`logistic.barcode`). Если ПВЗ сканирует другой код — картинка вводит в заблуждение.
- Мерж в `main` — только по явному «ок» Сергея.
