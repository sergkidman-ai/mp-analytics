## Задача

Отдельный Telegram-бот раз в день присылает полный список висящих FBS-возвратов по
Ozon / Яндекс / WB: сгруппировано по ПВЗ, с адресом, составом возврата, сроком забрать
и штрихкодом получения (картинкой — там, где площадка его отдаёт).

`returns_bot/sources/wb.py`. Окно ≤31 дня по `orderDt` → тянем тремя окнами назад (93 дня),

**Фаза 5 — две дыры по Ozon (06.08.2026).** `/v1/returns/list` отдаёт ТОЛЬКО схемы Fbs и Fbo;
ни Real-FBS, ни коробки вывоза со склада в нём нет (проверено живьём: возврат 100264955 в списке
отсутствует). Отсюда два новых источника, оба пишутся в `platform = 'ozon'`:

- `sources/ozon_rfbs.py` — **Real-FBS (экспресс)**: `POST /v2/returns/rfbs/list`
  с `filter.group_state = ["delivering"]` (у acc1 64 строки, у acc2 10 — влезает в один запрос),
  дальше `POST /v2/returns/rfbs/get` по строкам стадий pickup/transit ради
  **`ru_post_tracking_number`** — трека Почты России, по которому возврат и получают в отделении.
  В списке трека нет, только в деталях. `offset`/`last_id` в списке НЕ работают (limit 100 и 1000
  дают одно и то же), фильтр `state` строкой молча игнорируется — держаться `group_state`.
  Статусы: `ArrivedAtReturnPlace` = «В пункте выдачи» → pickup; `MovingToYou`/`WaitingShipment`
  → transit; адреса точки API не даёт вовсе (только `warehouse_id`), в сводке точка —
  «Почтой России», ехать по треку.
- `sources/ozon_removal.py` — **вывоз со склада FBO**: `POST /v1/removal/from-stock/list`
  (+ `from-supply`, у нас пусто). Окно обязательное, ≤3 месяцев, YYYY-MM-DD; тянем 2 окна = полгода;

  числом = 400). Единица показа — **коробка** (`box_id`), не заявка: в заявке их несколько, едут
  из разных РФЦ порознь. Ключ строки `rm-<заявка>-<коробка>`, в сводке печатается номер заявки
  (по нему ищут в ЛК: FBO → Вывоз и утилизация). Стадию решает `box_state`: «В пункте выдачи» →
  pickup, «В пути»/«На СЦ»/пусто → transit, «Получена»/«Утилизирована»/«Компенсировано продавцу»
  → closed; `return_state` («Можно забирать всё/часть») — только подпорка, у одной заявки часть
  коробок уже забрана. Срока «забрать до» в выдаче нет (`given_out_date`/`utilization_date`
  пустые даже у полученных), цены товара тоже.

**Фаза 6 — формат сводки (06.08.2026, по замечаниям Сергея на живой рассылке).**
Правки только в `render.py`, коммит `fix(ret): сводка — товар с новой строки…`, влит в main
fast-forward, сервис перезапущен, исправленная сводка отправлена:

- **тип содержимого коробки вывоза** («Доступно к продаже») из строки убран — складу не нужен;
- **название товара — с новой строки** под номером, по товару на строку (было: через `·`
  и `;` в одну строку с номером);
- **пустая строка между возвратами** внутри точки и **между точками** (📍) — сплошной блок
  глазом не разбирался, особенно на WB, где на одном адресе висит по 5–6 штук.

Блок возврата теперь: номер → товары → трек Почты (если есть) → хвост (висит N дн, сроки,
хранение, сумма). Отступы: `     • ` у номера, `       ` у всех подчинённых строк.

**Фаза 7 — кнопка «Обновить» (07.08.2026).** Под каждой сводкой inline-кнопка: тот же
`/obnovit`, но не набирая команду. Обработчик живёт в `returns-bot.service`, поэтому кнопка
под ночной рассылкой тоже рабочая.

- **сбор быстрый** (`gather(quick=True)`): у WB одно окно вместо трёх, у вывоза FBO одно
  вместо двух — 8 с против 40 с. Старую закрытую историю (3900 из 4000 строк) кнопка
  не перечитывает, её освежает ночной полный прогон;
- **`store(mark_gone=False)` при быстром сборе обязателен**: при узком окне «нет в выдаче»
  ≠ «пропал», иначе быстрый сбор похоронит всё, что не попало в окно;
- в итоге вместо бессмысленного «обновлено 4036, позиций 4100» — **сколько получено нами
  с прошлого обновления** (`collect.received_since`, считается по `status_raw`, см. ниже);
- параллельный сбор заблокирован флагом `_busy`: вторая нажатая кнопка получает отказ,
  а не встаёт в очередь и не идёт в API площадок второй раз.

**Фаза 8 — правки по живой эксплуатации (07.08.2026).**

- **Яндекс `RECEIVED` — не «забрать», а «в пути».** Означает «принят в пункте выдачи»
  логистикой, а не «лежит и ждёт нас». Сергей проверил заказы 58716444738 и 59558307072:
  в ЛК у них «Готов к отправке», к выдаче их нет. Признак реальной готовности —
  `pickupTillDate`: по базе заполнен ровно у `READY_FOR_PICKUP` и пуст у всех `RECEIVED`.
  Забрать: 20 → 17;
- **штрихкод Ozon шлём файлом** (`sendDocument`), не фото: `sendPhoto` перегоняет PNG
  784×144 в JPEG, тонкие штрихи плывут и сканер в пункте выдачи код не берёт;
- **срок жизни штрихкода в подписи.** В API его нет нигде: `/giveout/barcode` отдаёт одно
  значение, `/giveout/info` и `/giveout/list` по обоим аккаунтам пусты. Дата напечатана
  только на бланке PDF (`/giveout/get-pdf`) — разбираем оттуда через `pdftotext` (шрифты
  подмножеством, свой парсер врёт). Код живёт сутки, повторными запросами **не продлевается**,
  у аккаунтов сроки разные. Печатаем по Москве (сервер в UTC), истёк — «⛔ обновить в кабинете»:
  сами обновить не можем, `/barcode-reset` пишет в кабинет;
- **сам печатный бланк не отправляем** (решение Сергея: лишнее), но запрашиваем — ради срока.
