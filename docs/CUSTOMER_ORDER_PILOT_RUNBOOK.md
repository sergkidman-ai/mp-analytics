# Заказы покупателей: пилот Ozon Дисквэр

Поток fin, 20.10.2026. Раздел `/warehouse/customer-orders`, API `/api/customer-orders`.
Пилот запускается явно, без cron, вебхуков и периодического опроса МС.
Чтение таблицы и истории обращается только к локальной БД.

## Состав

- Миграция `073_customer_guard.sql`: восемь отдельных таблиц.
- `customer_guard.domain`: ревизии, нормализация цен через общий адаптер,
  количество продаваемых наборов, полнота FIFO, состав по справочнику ТК и пол.
- `customer_guard.store`: атомарное получение окна, неизменяемый first_seen,
  очередь, аренда задания, история и инциденты отсутствия в МС.
- `customer_guard.sources`: только GET МС, выделенный токен yunusov@dsquare,
  источник закупочной цены из проведённого оприходования Удалённого склада.
- `customer_guard.service`: однократные команды sync/work/refresh.
- UI: фильтры, цены Ozon/МС, выбранный состав, склад, стоимость, пол,
  отклонение, источник оценки и история проверок.

Общий адаптер wb4c: исходный коммит `513373c`, интеграция в нашу ветку `4069230`.
Общая блокировка кабинета: `5fbfda1`, интеграция `040fbc1`.
Пилот не копирует финансовый collector, использует его публичный fetch_postings
и core.ozon_posting.product_price. Нормализация совместима с v3 scalar и v4 Money.

## Запуск

Из собственного worktree с `.env`, `venv` и применённой миграцией:

```bash
./venv/bin/python -m customer_guard.service sync --days 2
./venv/bin/python -m customer_guard.service work --limit 3 --budget 60
./venv/bin/python -m customer_guard.service work --posting 0142557324-0141-1 --limit 1 --budget 15
./venv/bin/python -m customer_guard.service refresh --limit 5
```

`sync`: все статусы в фиксированном окне, до 10 страниц по 20 отправлений,
до 120 секунд. Параметр days ограничен диапазоном 1–7. Это не утверждение
полноты старых активных заказов за пределами окна.
Окно сохраняется только целиком. Частичная выдача не сдвигает checkpoint.

`work`: только наступившие задания. Первая проверка не раньше first_seen+10min.
Ни даты площадки, ни raw.loaded_at не используются для ускорения этого срока.
До МС проверяется свежий статус точечным Ozon get. Новая ревизия отменяет старую
аренду и получает своё задание. Черновик МС существует, но экономика не считается.
В конце чтения состава проверяется, не изменился ли сам MS-заказ.
Флаг --posting ограничивает выбор конкретным номером и не обходит due_at.
Версии прочитанных отгрузок/оприходований также проверяются после получения стоимости.

`refresh`: явная точечная проверка наиболее давно наблюдавшихся активных
отправлений, в том числе за пределами окна создания. Отмена завершает работу,
изменение значимых данных ставит пересчёт. Этот вызов не имеет расписания.
Неизменный MP-ответ сам по себе не ставит периодический пересчёт МС.

## Ограничение нагрузки

Один advisory lock `7348201701` общий со сторожем отгрузок: два исполнителя МС
не работают одновременно. Используются тот же persistent cooldown и метрики
ms_shipment_metrics. Минимальная пауза МС в пилоте 2,1 секунды.
Бюджет по умолчанию 60 GET на весь запуск, жёсткий предел аргумента 100;
до 240 секунд до начала последнего запроса (плюс timeout этого запроса).
После 429/ошибки прав/исчерпания бюджета запуск прерывается.
Повтор задания — не раньше 10 минут и не раньше Retry-After, максимум 5 попыток.
Повторы ошибок не являются согласованной частотой штатного опроса заказов.

Списки и позиции читаются страницами по 20, максимум 10 страниц; для поиска
единственного заказа/оприходования/склада — одна страница. Кэш оприходований
действует только внутри запуска, с ключом UUID+updated. Старая закупочная цена
не используется молча при удалении или замене документа.

Список и точечный get используют общий account_lock адаптера wb4c,
отдельный от MS-lock. Проверка владения выполняется перед каждой HTTP-попыткой.
Старый финансовый процесс, ещё не перезапущенный с новым кодом wb4c, эту
блокировку не использует. До регулярного запуска нужно завершить его миграцию.

## Финансовый кэш и расчёты

По умолчанию `ingest(..., mirror_raw=False)` сохраняет собственные неизменяемые
снимки входных полей. Общий raw_ozon_posting не меняется, пока финансовые
потребители не переведены на v4 Money в рамках wb4c. Поддержка атомарного
зеркалирования реализована и проверена, но через CLI не включается.
Исходные значения полей снимков сохраняются без преобразования формата.

Стоимость всего заказа не выдаётся за доказанную стоимость каждой его строки.
Зелёный результат допустим только для одной строки площадки с подтверждённым
составом/количеством по локальному справочнику ТК. В остальных случаях итог
показывается с предупреждением о распределении. Выбор товара ТК не повторяется.
При неполных отгрузках или неопределённом FIFO пол и отклонение остаются пустыми.
Закупочная оценка и предварительный FIFO помечены явно, без обещания фактической прибыли.

## Уведомления и следующий этап

Успешно подтверждённое отсутствие рабочего отправления в МС создаёт один
инцидент на полный номер. Ошибка API или неоднозначность поиска не создаёт
сигнала «нет в МС». Появление заказа или терминальный MP-статус закрывает инцидент.

Рассылка в этом этапе не подключена. Транспорт будет prc, личный адресат
Наталия; общий список получателей prc не использовать. Перед отправкой нужно
повторно подтвердить актуальность источников, обрабатывать неоднозначный
таймаут Telegram как uncertain и не обещать exactly-once.

Остаётся согласовать ритм получения новых MP-заказов и повторной проверки МС,
перевести финансовый процесс на общую блокировку, проверить покрытие старых активных заказов,
подключить отправитель и автоматический исполнитель первой проверки.
Пилот не включает эти службы автоматически.

## Откат

Отключить новые маршруты/ссылку и не запускать однократные команды.
Новых systemd/cron-заданий нет. Таблицы можно оставить для истории;
откат не требует удаления данных и не меняет документы МС/Ozon.
