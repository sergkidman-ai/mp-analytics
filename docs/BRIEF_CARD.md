## Зона ответственности
Контент карточек пишет **ТК** (внешняя система, ей управляет человек); после её апдейтов часть
карточек нестабильно падает в «Ошибки» и «На доработку». Поток `card` отвечает за **здоровье**:
видеть состояние, классифицировать причину и **дотолкивать до продажи те, которым нужна только
повторная отправка**. Мы не авторы контента — мы «дожиматель». Сюда же — целостность самого
списка карточек: строка в БД без карточки в кабинете такой же дефект здоровья.

## Границы
- **Контент карточки принадлежит ТК.** Шлём ровно то, что уже в карточке; текст/атрибуты не
  генерируем и не правим — иначе первый же пуш ТК затрёт правку.
- `margin_by_sku`, витрины fin/mkt — read-only. `collectors/ozon.py` — общий, правки только
  по согласованию (беру оттуда `_headers` и URL).

## Запреты потока
1. **Изменение контента карточек запрещено.** Только повторная отправка существующего значения.
2. **Постоянное разрешение на классы A и W** (A — 22.08.2026, W — 23.08.2026 командой
   «расширяй автомат»): дожиматель ходит по торгующим карточкам сам, включая крон. Разрешение
   покрывает ТОЛЬКО повтор существующего значения. Любое другое действие — снова разовый вопрос.
4. Признак успеха — **не HTTP 200**, а `status` задачи `imported` + очистившийся `status_failed`.
   `skipped` = попытка не засчитана, HTTP 200 при этом приходит.

## Техника (проверено на живых вызовах)
- `POST /v1/product/attributes/update` — точечно, карточку целиком не шлёт. **`task_id`
  возвращается в КОРНЕ ответа**, не в `result` — на этом первый прогон потерял все id.
- Статус задачи: `/v1/product/import/info` → `imported` / `skipped` / `failed`. HTTP 200 успехом
  не является. Атрибуты карточки — `/v4/product/info/attributes`, ключ `id`, не `attribute_id`.
- Безопасные атрибуты для no-op: `9024` Артикул → `4389` Страна → `10400` Гарантия.
- Витрины `/v3/product/list`: рабочие — `STATE_FAILED` и `PARTIAL_APPROVED`; `BANNED` и
  `IMAGE_ABSENT` возвращают весь каталог и непригодны.

## Автомат (построен 22.08, влит в `main` 23.08; детали — `docs/handoff/archive/card_2026-08-24.md`)

**Миграция 600.** `card_status` — состояние по ключу площадка+аккаунт+`offer_id`; после лечения
строка закрывается (`is_open`+`healed_at`) — видны рецидивы. Журнал попыток `card_push_log` возобновляем.

**Детектор `collectors/ozon_card_status.py`** — только чтение: витрины `STATE_FAILED` и
`PARTIAL_APPROVED` → `/v3/product/info/list` → класс A/W/C/O → upsert; кого площадка больше не
считает проблемным — закрывает. Крон 07:41, лог `card_health.log`; ругается на A/W старше недели.

**Дожиматель `tools/ozon_card_push.py`** — классы A и W, ступень 1 (no-op по атрибуту
`9024`→`4389`→`10400`); отправка только с `--apply`. Крон 08:14, оба аккаунта подряд, партия 500.
Ограничение 50 осталось в СТРАЖЕ (`tools/hooks/guard_side_effects.py`, `is_mass`): РУЧНОЙ вызов
с `--limit >50` режется в DENY; крон через хук не идёт.

**Признак успеха у классов РАЗНЫЙ:** у A — очистившийся `status_failed`, у W — исчезнувший код
замечания; вылеченная W строку не закрывает, класс меняется на `O`. Предохранители: 3 попытки,
backoff 20 ч, пропуск карточки со свежим (<2 ч) апдейтом ТК, живая перепроверка перед записью,
ворота после первых 20 (<50 % — стоп), стоп при `declined` или уходе из продажи, `skipped` →
`needs_human`. **Ступень 2 (round-trip импорт) НЕ реализована** — шлёт карточку целиком.
