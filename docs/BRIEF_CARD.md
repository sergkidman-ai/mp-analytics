## Зона ответственности
Карточки товара на площадках находятся в чужих руках: контент в них пишет **ТК** (внешняя
система, ей управляет человек — каждый перепрогон это постановка задачи, исполнение, контроль).
После апдейтов ТК часть карточек падает в «Ошибки» и «На доработку», причём нестабильно: один
и тот же товар то проходит, то нет. Поток `card` отвечает за **здоровье** этих карточек:
видеть их состояние, классифицировать причину и **дотолкивать до продажи те, которым нужна
только повторная отправка**. Мы не авторы контента и не редакторы — мы «дожиматель».

## Границы
- **Контент карточки принадлежит ТК.** Мы отправляем ровно то, что уже лежит в карточке, и
  никогда не генерируем и не правим текст/атрибуты. Иначе первый же пуш ТК затрёт правку.
- `margin_by_sku`, витрины fin/mkt — read-only.
- `collectors/ozon.py` — общий, правки только по согласованию (беру оттуда `_headers` и URL).

## Запреты потока
1. **Изменение контента карточек запрещено.** Только повторная отправка существующего значения.
2. **Торгующие карточки не трогать без отдельной прямой команды Сергея.** Разрешение разовое:
   команда «делаем волну 2» от 22.08.2026 закрыта прогоном, на следующий раз — новый вопрос.
3. Отправка на площадки — по прямой команде, разрешение разовое (CLAUDE.md, правило gab-7).
4. Признак успеха — **не HTTP 200**, а `status` задачи `imported` + очистившийся `status_failed`.
   `skipped` = попытка не засчитана, HTTP 200 при этом приходит.

значения. **C** — контентный ERROR модерации: повтор бесполезен, правится только в ТК.

к исполнению; текста причины не существует в природе.

Класс C acc1 — 25 карточек «Не создан», новый товар вообще не попал в продажу. Это прямые

## Техника (проверено на живых вызовах)
- `POST /v1/product/attributes/update` — точечно, не шлёт карточку целиком.
  Тело: `{"items":[{"offer_id":..,"attributes":[{"id":9024,"complex_id":0,"values":[...]}]}]}`.
- **`task_id` возвращается в КОРНЕ ответа** (`{"task_id": N}`), не в `result` — на этом
  первый прогон канарейки потерял все id, хотя отправка прошла.
- `POST /v1/product/import/info` с `{"task_id": N}` → `status`: `imported` / `skipped` / `failed`.
- Чтение карточки для среза: `/v4/product/info/attributes` (атрибуты в поле `id`, не
  `attribute_id`) + `/v1/product/info/description`.
- Безопасные атрибуты для no-op, по приоритету: `9024` Артикул → `4389` Страна → `10400` Гарантия.
- Фильтры `BANNED` и `IMAGE_ABSENT` в `/v3/product/list` возвращают весь каталог — не пригодны.

## Автомат (построен 22.08.2026, ветка `card/ozon-health`, коммиты `fb037c2`, `52b50e8`)

**Миграция 600.** `card_status` — состояние проблемной карточки по ключу
площадка+аккаунт+`offer_id`. Строка **не удаляется** после лечения, закрывается флагом
`is_open` + `healed_at`: так видно рецидивы (карточка, которую ТК роняет раз за разом, —
сигнал программисту) и «сколько висит» — цифру, которой у площадки нет вообще.
`card_push_log` — журнал попыток, строка на отправку, прогон возобновляем.

**Детектор `collectors/ozon_card_status.py`** — только чтение. `STATE_FAILED` →
`/v3/product/info/list` → класс A / C / O → upsert; кого площадка больше не считает
проблемным — закрывает. Ругается, если карточки класса A висят дольше недели (значит,
дожим не работает). **В cron: ежедневно 07:41**, лог `card_health.log`.

**Дожиматель `tools/ozon_card_push.py`** — класс A, ступень 1 (no-op по атрибуту
`9024`→`4389`→`10400`). `--tk-report` выгружает класс C для программиста ТК.
**Отправка по умолчанию выключена**, нужен `--apply`; в cron дожиматель НЕ поставлен.

Предохранители: потолок 3 попытки на карточку и backoff 20 ч; пропуск карточки со свежим
(<2 ч) апдейтом ТК — иначе гонка; живая перепроверка статуса перед записью (в БД мог
устареть); ворота после первых 20 карточек (вылечилось <50 % — прогон стоп); стоп при
`declined` или уходе из продажи; `skipped` → карточка сразу помечается `needs_human`.

**Ступень 2 лестницы (полный round-trip импорт) сознательно НЕ реализована.** Она шлёт
карточку целиком, то есть может утащить её на повторную модерацию — ровно тот риск, от
которого мы весь день уворачивались, а проверить его не на чем: кандидат ровно один
(`3463`). Такие карточки уходят в список для человека.

**Проверено:** миграция применена; детектор отработал по обоим аккаунтам; сухой прогон
дожимателя — по обоим; SQL-пути (пул → журнал → попытка → лечение → выход из пула) прогнаны
self-check'ом на синтетической строке. **Боевой путь `--apply` в составе автомата ещё не
запускался ни разу** — см. «Следующий шаг».
