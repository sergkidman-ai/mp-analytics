# Слой данных

1. **Сырьё отдельно от расчётов.** raw-слой (JSONB) хранит ответы API как есть; любой расчёт
   пересобирается из сырья **без повторного обращения к API**. Новый расчёт — новый проход по raw,
   а не новый сбор.
2. **Идемпотентность.** Повторный сбор за период не плодит дублей — `upsert` по натуральному ключу.
3. **Узкие запросы.** К МС и API площадок ходить точечно: `limit=10–20`, только нужные поля через
   `expand`/фильтры, коллекции целиком не тянуть. Ответ или файл **>1 МБ** — сохранять на диск,
   не в чат; разбирать `jq`/`grep`, а не `cat` целиком.
4. **Миграции по потокам:** `0xx` — `fin`, `1xx` — `mkt`. Номер не переиспользовать.
5. **Секреты только в `.env`** (gitignored): не хардкодить, не логировать, не выводить в чат.

## Известные особенности площадок

- **WB:** период = дата формирования отчёта; COGS из отгрузок МС по `assembly_id`. Каждая единица
  товара в заказе = отдельный заказ/отправление, поэтому «штуки» и «заказы» у ВБ совпадают.
  Старый эндпоинт остатков отключён 20.07.2026 — только асинхронный `warehouse_remains`
  (разрыв данных `wb_stocks` 15→23 июля — это факт, а не баг сборщика).
  Недельные ряды сравнивать только одинаковыми днями недели (пн–чт к пн–чт).
- **Яндекс:** выручка и возвраты — из closure-детализации (`INCOME`), эталон до копейки.
  `yandex_monthly --light` пересобирает витрину из сырья без похода в API.
- **МойСклад:** в аккаунте **две организации** — антидубль платежей обязан фильтровать по организации.
  «Код» = товар конкретного поставщика (`3804at`), «Внешний код» = наша карточка (`3804`).

Массовое изменение сущностей в МойСкладе (>~50 карточек/заказов) — Skill **`ms-mass-change`**,
вызывать ДО прогона.
