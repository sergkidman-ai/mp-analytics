# Push при приёмке «Принят/ на оплату»

Публичный адрес: `https://89-207-255-54.sslip.io`. `/health` возвращает только
готовность хранилища. POST `/hooks/ms-supply/<secret>` доступен по секрету из
`MS_SUPPLY_WEBHOOK_SECRET` в проектном `.env` (0600). Секрет не входит в этот
файл, Caddyfile, сообщения или журналы регистрации.

Официальный формат МС проверен по
[первоисточнику JSON API — вебхуки](https://github.com/moysklad/api-remap-1.2-doc/blob/master/md/dictionaries/_webhook.md):
`events[].accountId` — UUID учётной записи; `updatedFields` — массив строк;
он передаётся для `action=UPDATE` при `diffType=FIELDS`.
`auditContext.moment` содержит дату изменения. При повторной доставке МС
сохраняет query-параметр `requestId`. Receiver проверяет UUID учётной записи,
`action=UPDATE`, `meta.type=supply` и точный API href приёмки.
Если `updatedFields` присутствует без `state`, уведомление подтверждается
без задания. Если список отсутствует, задание сохраняется, а worker проверит
фактический статус приёмки точечным чтением.

Схема: Caddy на публичных TCP 80/443 → `127.0.0.1:8094` → SQLite → отдельный
worker. Uvicorn access log выключен; Caddy не журналирует HTTP requests/errors,
которые могли бы раскрыть секретный путь. Другие HTTP-пути дают 404.
Бесплатный сертификат Let's Encrypt получает и продлевает Caddy; установка
выполнена из [официального подписанного репозитория Caddy](https://caddyserver.com/docs/install#debian-ubuntu-raspbian).
Старые вебхуки МС, домены и службы не изменяются.

Очередь: `.private/ms_supply_fulfillment/runtime.sqlite`, директория 0700,
БД 0600, WAL + synchronous FULL. ACK 204 выдаётся после фиксации транзакции.
Доставка дедуплицируется по `accountId/requestId`, обновление — по приёмке и
моменту события. Новый event во время обработки повышает generation и
сохраняется для следующего прохода. Claim атомарный; lease продлевается
каждые 30 секунд, после сбоя процесса задание доступно по истечении lease.

Контракт бизнес-обработчика:
`fulfill_receipt(receipt_id, event_timestamp, apply=True, event_id=...)`.
`done/manual` завершают задание, `retry` использует backoff, `continue` заново
планирует его с `delay_seconds/not_before`. Ожидание пяти минут не удерживает
worker: он может обрабатывать другие приёмки.

Проверки перед включением:

```bash
./venv/bin/python -m unittest tests.test_ms_supply_receiver tests.test_ms_supply_fulfillment
systemd-analyze verify ops/ms-supply-receiver.service ops/ms-supply-fulfillment.service
caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
```

После готовности бизнес-обработчика регистрация выполняется одной командой:

```bash
./venv/bin/python -m ops.ms_supply_queue --register
systemctl enable --now ms-supply-fulfillment.service
```

Регистрация добавляет только собственный `supply/UPDATE/FIELDS` webhook и
сохраняет intent до POST. Неопределённый POST не повторяется вслепую.
Журнал `.private/ms_supply_fulfillment/webhook_registration/` не содержит URL
с секретом. Команда идемпотентно распознаёт уже существующую свою подписку.

Добор пропущенных push активируется с момента регистрации, без исторического
импорта. Раз в пять минут worker читает только `supply` со статусом
`5c76771e-dd9b-11e2-e25d-7054d21a8d1e` и `updated` между checkpoint и текущим
временем, страницами по 20. Перекрытие двух минут ограничено датой активации;
дубликаты подавляет очередь. При ошибке checkpoint сохраняется прежним.
Остатки, резервы и широкие списки заказов этот добор не читает.

Текущее состояние развертывания фиксируется в безопасном журнале регистрации
и `systemctl is-active ms-supply-receiver ms-supply-fulfillment caddy`.

## WB: поставка на плановую дату заказа

Общий для обоих обработчиков `ops/wb_fbs_supply_policy.py` подбирает открытую
совместимую FBS-поставку по дате в имени и кабинету, либо создаёт её при отсутствии.
Основание создания — прямое поручение пользователя 03.11.2026. Примеры имён:
`05.11.2026 Цифровой FBS`, `05.11.2026 Дисквер FBS`. Дата из `deliveryPlannedMoment`
МС; фактическая дата создания WB-поставки может быть раньше планового дня.
Точки API сверены с [официальной документацией WB](https://dev.wildberries.kg/docs/openapi/orders-fbs).
Рабочий host остаётся marketplace-api.wildberries.ru; ключи не менялись.

Общая блокировка кабинета действует и при создании, и при первом добавлении
заказа. Намерение и API-ответ создания сохраняются, после таймаута проверяется
фактическая поставка; автоматического повторного POST без подтверждения нет.
Несколько подходящих открытых поставок требуют ручного выбора. Выбранный ID
сохраняется на кабинет/дату, следующие проходы читают его точечно. Реестр
`.private/ms_supply_fulfillment/wb_supplies/` исключён из Git. Старые разрешённые
поставки03.11 используются только для заказов с планом03.11.
