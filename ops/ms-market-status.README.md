# МП → МС: статусы заказов «Собирается» и «В пути» за скользящие 90 дней

Настроено по прямому поручению пользователя 03.11.2026. Расширяет существующий
`ops/ms_market_status_sync.py`; разовый исторический режим не изменён.
Новый координатор `ops/ms_market_status_live.py` использует его идентификацию
и правила WB, существующие клиенты Ozon/Яндекса/WB. Финансовые таблицы не пишет,
заказы и отгрузки не создаёт, статусы/поставки на маркетплейсах не изменяет.

## Расписание и границы

- `ms-market-status-fast.timer`: каждые 30 минут, **:10/:40 МСК**, отдельно от
  часового загрузчика :00. Читает новые наблюдения Пульта `customer_guard_orders`,
  проверяет изменившиеся в МС документы, все известные «Собирается» и FBO-заказы. До40 реальных
  изменений за проход; остаток сохраняется. Полный 90-дневный список днём
  повторно не опрашивает. Исходные наблюдения при установке приняты как baseline,
  без дневного массового переноса исторических терминальных статусов. После
  обновления 05.11 один раз добавляет существующие «Собирается» за 90 дней;
  далее повторно проверяет их независимо от изменения документа МС. Ошибки
  источника сохраняются в отчёте и повторяются на следующем штатном запуске.
- `ms-market-status-night.timer`: ежедневно **23:15 МСК**. Замораживает список
  МС «Собирается»/«В пути» от начала даты90 дней назад по конец сегодняшней даты МСК,
  проверяет актуальные МП-источники. Запись жёстко ограничена 23:00–05:00;
  systemd дополнительно ограничивает продолжительность до04:45 при старте23:15.
- Исходные статусы **«Собирается»** и **«В пути»**. При подтверждённой передаче
  перевозчику «Собирается» → **«В пути»**. Для обоих источников подтверждённые
  доставка/отмена → **«Доставлен»** / существующий **«Отменен - сроки»**.
  После перехода в «В пути» заказ остаётся под наблюдением; обратного перехода
  нет. Другие статусы не меняются. Совпадающие
  состояния, отсутствие подтверждённого статуса, дубли номера/неоднозначная
  связь и вмешательство сотрудников дают пропуск, не запись.
- Проверка работоспособности использует таймер импортёра и чтение МС;
  отключённые обработчики приёмок `ms-supply-receiver`/`ms-supply-fulfillment`
  для синхронизации статусов не требуются и не включаются.
- Пять кабинетов: OzonACC1/ACC2, WBACC1/ACC2, МаркетACC1. МаркетACC2 не существует,
  его ключи/подключение не проверяются.

## Источники и сопоставление

Точный ключ: площадка + кабинет + устойчивый внешний номер. Перед PUT
перечитывается конкретный МС-документ, проверяются номер/организация/контрагент,
период и текущий статус. PUT содержит только `state`; затем обязательный GET.
Наличие/резервы/цены/состав в этом процессе не опрашиваются и не изменяются.

Оперативный источник Пульта сейчас FBS. Для FBO координатор использует те же
API-доступы через read-only адаптер `ops/ms_market_status_sources.py`:

- Ozon: FBS `/v3/posting/fbs/get`, FBO `/v2/posting/fbo/get`, проверяется точный
  posting_number. Неполученный FBS-заказ не считается отменой: проверяется FBO,
  иначе фиксируется непроверенный источник.
- Маркет: существующий клиент business/orders, только чтение со схемами FBS/FBY/EXPRESS
  и fake=false. Экспресс-заказы обрабатываются как заказы со склада продавца;
  PROCESSING/READY_TO_SHIP остаётся без смены статуса до передачи перевозчику.
  DBS не включён. API программы:
  [официальная документация](https://yandex.ru/dev/market/partner-api/doc/ru/reference/orders/getBusinessOrders).
- WB FBS: пакетные точные статусы. FBW: Orders/Sales Statistics, warehouseType
  «Склад WB», srid; для полного gNumber требуется согласованное терминальное
  состояние всех единиц. Доставка подтверждается положительной продажей S,
  отмена — явным isCancel. Возврат R/конфликт/отсутствие строки не превращаются
  в доставку или отмену. Обработка lastChangeDate до пустой страницы, с паузой
  60сек между страницами одного метода. Эти данные WB обновляются раз в30мин:
  [официальная документация](https://dev.wildberries.kg/docs/openapi/reports).

FBO-ветки проверены локальными тестами. При установке FBO list API обоих Ozon
ответил успешно, за90 дней не вернул ни одного примера; реального FBO-перехода
в МС при установке не было. Пробы FBS прошли для всех пяти кабинетов.
Отсутствующие исходные финансовые raw-таблицы не создаются и не пересчитываются.

## Нагрузка, конкуренция и восстановление

Применена [проектная инструкция](../.claude/skills/ms-mass-change/SKILL.md).
Изменение значимое: активный consumer customerorder.UPDATE — thecartridge.ru;
его вебхуки не подавляются. Дневные точечные изменения разрешены текущим
поручением; массовый исторический перенос — только ночью.

Общий SQLite ограничивает оба процесса: минимум1.5сек между зарезервированными
записями, потолок3000 сущностей/час и10000/ночь. Рост времени ответа МС
увеличивает паузу до30сек, восстановление постепенное. Первые200 подтверждённых
ночных изменений → пауза10мин → контроль МС и рабочих таймера загрузчика,
приёмника/обработчика приёмок. Без здоровой операционки ночная запись не начинается.

Дневная и ночная очереди имеют общие leases и поколения: одну запись не могут
выполнить два процесса. Более новое наблюдение отменяет устаревшее намерение.
При таймауте PUT выполняется GET факта; повторного PUT вслепую нет. Если факт
не подтверждён — заказ в `uncertain`, остальные продолжаются. Автоматически
повторять такую запись нельзя; нужна отдельная сверка и решение.

Индекс хранит только кандидатов: подтверждённые терминальные документы удаляются
из оперативного индекса, чтобы FBO не опрашивались бесконечно после завершения.
Просроченный снимок МП перед записью обновляется, данные старше10мин не используются.

Приватный журнал `.private/ms_market_status_continuous/`: SQLite 0600,
каталог0700, Git ignored. `runs/*/scope.json` — до-срез; `attempts/*/intent.json`,
`response.json`, `readback.json` — точные намерения/ответы/факт. Для обратимости
сохранён исходный `state`; автоматического отката нет. Неподтверждённые,
отложенные и требующие ручной сверки документы отражаются в `*_latest.json`.
Чувствительные заголовки и значения ключей в журналы не пишутся.

## Проверки и эксплуатация

38 локальных тестов прошли: оба типа схем, границы МСК, race с сотрудником,
дубли внешних номеров, пропавший источник, таймаут с/без API-подтверждения,
лимиты и пауза канарейки. Первоначальный индекс:921 заказ МП, ещё2 прямых
исключены; baseline Пульта1175 наблюдений, никаких PUT при инициализации.

```bash
cd /opt/mp-analytics
systemctl list-timers ms-market-status-fast.timer ms-market-status-night.timer --no-pager
systemctl status ms-market-status-fast.service ms-market-status-night.service --no-pager
journalctl -u ms-market-status-fast.service -u ms-market-status-night.service -n 30 --no-pager
./venv/bin/python -m ops.ms_market_status_live --mode preview
./venv/bin/python -m unittest tests.test_ms_market_status_live tests.test_ms_market_status_sources tests.test_ms_market_status_sync -q
```

`--mode preview` не меняет документы МС. Ручной запуск записи возможен через
`--mode fast --apply` или `--mode night --apply` (ночной режим проверяет время).
В настройках включены только два новых status-sync таймера; посторонние сервисы,
реклама и боты не включались. Старый разовый timer не восстановлен.

Первый плановый дневной запуск 03.11.2026 16:40МСК завершился success:
целевых изменений0, непроверенных источников0, PUT0. Ночная массовая сверка
на момент включения ещё не выполнялась; первый запуск03.11 в23:15МСК.
